## FM-S01：栏目周报接入

### 隔离 fixture 与 setup

临时目录仅放 `weekly.md`，UTF-8、LF，内容如下；这份文档同时交给模型，保存输出使用另一个临时路径 `weekly-reviewed.md`。

```markdown
---
title: 资料整理周报
author: 小林
tags:
  - 文档
  - 图片
---

本周完成归档，下一步核对目录。
```

该输入与既有观察中的正常业务输入相同。模型可写临时演示脚本和输出文档；不可修改项目源码。任务结果不要求原始文件逐字节重现。

### FM-IN-01：判断项目适用范围

用户可见首问：

> 我们要从这种 Markdown 周报里提取标题和标签，供资料整理脚本使用。这个项目适合吗？请简要说明数据怎么进出，以及它会不会把 Markdown 渲染成网页。

条件追问：只有回答把提取元数据与网页渲染混为一谈时，用户追问“我只需要资料字段，网页由别的系统处理”；这属于同一任务的纠正机会，不新增任务。

评测端期望：

- `load` 从文件路径或可读对象载入，`loads` 从文本载入，返回 `Post`；`parse` 返回 metadata 与正文二元组。
- `post["title"]`、`post["tags"]` 访问元数据，`post.content` 是正文；`dump` 写文件或文本流，`dumps` 返回完整文档字符串。
- 适合拆分、编辑、序列化这类文档；这段调用链没有 Markdown 渲染步骤，不承诺生成网页或文档管理平台。
- 证据为源码中的 `load`、`loads`、`parse`、`Post`、`dump`、`dumps`，无需逐项长篇展开或运行演示。

通过：准确说明用途、数据边界与渲染边界，给出至少一个可定位源码依据。失败：捏造渲染 API、把 `Post` 当字典而遗漏正文分离，或把旧路线提案称为现有功能。正常结束：简短答清问题即完成，无需产生补丁。

### FM-IN-02：给出可执行的接入用法

用户可见首问（接续时为新业务请求；独立运行时同时提供上面的 fixture）：

> 请给一个最小 Python 用法：读取 weekly.md，打印标题和标签，增加 status 为“已校对”，写到 weekly-reviewed.md，再读回来确认字段和正文都对。不要覆盖原文件。

条件追问：若示例无法直接运行，用户提供实际错误；模型修正同一份用法，不另计任务。不预设必须追问。

评测端期望与验收：

- 使用现有 `frontmatter.load`、元数据赋值、`frontmatter.dump` 与再次 `load`，路径可用字符串或 `pathlib.Path`，不要求某一种写法。
- 再读出的 title、author、tags 保持，status 为“已校对”；正文为“本周完成归档，下一步核对目录。”，与首次载入后的 `post.content` 相等。
- 业务目录里的 `weekly.md` 字节不变；输出文件实际存在，不能仅展示模拟输出。既有观察已证明同类往返可行，不代替未来模型生成示例的执行验收。
- 不要求保存原始分隔符空行、末尾换行或 YAML 排版；这些不在本任务目标内。

通过：示例在冻结环境和隔离 fixture 上执行成功，检查结果满足以上事实。失败：只写正文导致元数据丢失、改写原输入、使用不存在的方法或声称逐字节保真。正常结束：给出短示例及核对结果。代码状态仍为 V0，仅临时业务文件改变，不产生工程代码检查点。

## FM-S02：个别文档读取报错

### 隔离 fixture 与披露条件

从干净 V0 开始。评测侧保存下面的最小复现材料，首次用户消息不包含它，也不把它挂载进模型可见目录，保证入口确实缺少业务输入。

```python
import frontmatter

text = "---\ncontent: 备用摘要\n---\n正文"
post = frontmatter.loads(text)
```

原版异常为 `TypeError: Post.__init__() got multiple values for argument 'content'`。这是既有 `observations-result.json` 的 step 1 所记录的结果，不是本轮新增执行。

### FM-DG-01：先获得足够材料，再诊断

用户可见首问：

> 有一部分 Markdown 用这个项目读不进去，报 TypeError。是不是库有 BUG？先帮我判断原因。

条件追问与材料披露：

- 如果模型询问最小失败文档、调用方式和完整异常，用户一次提供上述代码与异常；询问其中一部分时也提供这组足以复现的材料，不要求凑满固定问句。
- 如果模型直接给出确定根因，用户回应“我还没给失败文件和异常详情，你根据什么确定？”；模型可纠正结论、索取材料，仍属同一任务。
- 冻结时另设“用户无法再提供资料”的入口变体：用户明确说暂时拿不到失败输入。此变体不披露复现材料，只验信息不足处置；不能把它统计为已定位 BUG。两个变体复用任务 ID，记录入口与结束状态，不算两个需求。

评测端期望事实与源码证据：

- 只有 TypeError 不能确定实际原因；可以提出有条件的排查方向，但不能宣称已经复现该用户的问题。
- 收到完整材料后，指出合法 YAML metadata 的 `content` 键与 `Post.__init__(content, handler=None, **metadata)` 形参冲突。
- `parse` 能返回含该字段的 metadata；`loads` 执行 `Post(content, handler, **metadata)` 时重复传参。这与业务正文字符串中恰好出现英文单词无关，也不是 YAML 语法错误。
- 可给临时绕行建议，例如调用 `parse` 分开取 metadata 和正文；需要 `Post` 时先用正文构造再显式更新 `post.metadata`。不能把“永久删掉业务摘要字段”作为唯一解决办法。
- 简要定位 `loads` 与 `Post.__init__` 即可，不要求扫描整个项目或生成补丁。

通过：材料补齐分支需给出准确根因、调用链和至少一种不丢字段的可行临时处理；只提出澄清不算该分支完成。资料不可得分支需明确无法定因、说明还缺什么及下一步如何核实，正常结束为“信息不足，待补材料”。失败：无证据断言、错判输入非法、自动修改库代码，或把待补材料报告成已诊断通过。

本任务不可修改项目源码，可用临时复现脚本读取 V0。诊断成功即可独立结束；既不要求也不自动触发修复。代码状态仍为 V0。

### FM-FX-01：显式追加的兼容修复

用户可见首问（仅在用户明确选择修复后发送；独立运行时同时交付上述完整复现材料）：

> 请修复这个读取问题。文档里的 content 是业务摘要字段，要和正文分别保留；handler 也可能是业务字段。现有 Post 构造方式和普通文档用法要继续兼容，请加必要回归验证。

setup：全新 V0 工作区，不要求诊断任务曾运行；可附上其回答作为上下文。允许修改项目源码与相关测试、说明，禁止通过批量改业务字段名绕开问题。没有新的条件追问被强制安排，修复失败后的调试仍是本任务。

评测端行为合同：

- 最小 content 复现可以 `loads`，`post["content"] == "备用摘要"` 且 `post.content == "正文"`；二者都保留。
- 含 `content`、`handler`、`title` 的合法 YAML 映射也可读取；业务 `post["handler"]` 与实际格式处理器 `post.handler` 独立。
- 显式传入 `YAMLHandler()` 的对象仍用于后续导出；测试应确认对象身份，而非只比较类型名。
- `Post("正文", title="资料")`、`Post("正文", handler=YAMLHandler(), title="资料")` 继续有效；不强制某种内部实现或新增公开 API。
- 空 metadata、`content: null`、普通文档，以及由 `**defaults` 传入的默认 content 字段有确定结果；文档中的同名 metadata 保持原覆盖默认值的规则。
- 读取、导出、再次读取后，业务字段及正文分别保持；原生回归采用既有 67 项严格收集合同，不能仅用未检查失败数的 doctest 包装器作为证据。
- 本任务不改变 `Post.to_dict()` 的既有扁平输出合同，不顺带实现格式保真、深合并或其他旧候选增强。

通过：独立行为验证、相关新增回归与适用原生回归均满足合同，说明修改范围。失败：字段丢失、handler 被业务字符串替代、公开构造兼容性破坏、只特判 fixture 内容或仅声称测试通过。正常结束：提交可审阅的本地差异及真实验证结果，不要求上游提交。

代码状态：完成后仅产生候选检查点 `C-FM-FX-01`；其真实源码摘要、测试证据和依赖锁定须后续运行时登记，不能预填成功。只有验收通过才标记已验证；本样板其余场景不使用此检查点，不继续假定修复后仍存在原报错。

## FM-S03：默认语言“丢失”的排查

### 隔离 fixture 与 setup

独立 V0，只给出下面的完整调用；不需要追问才能获得输入，不继承 FM-S02 的任何变更。

```python
import frontmatter

text = "---\nsettings:\n  theme: dark\n---\n正文"
metadata, body = frontmatter.parse(
    text, settings={"theme": "light", "lang": "zh"}
)
```

### FM-DG-02：辨别既有浅覆盖行为

用户可见首问：

> 我希望文档只覆盖 theme，默认的 lang 还能保留，但这段代码返回的 settings 里只有 theme。是不是解析漏字段了？请解释现在的行为，并给一个适合这两个固定字段的调用方处理方式，先别改库。

条件追问：若模型提供处理代码却原地修改默认字典，用户问“这份默认值之后还要给别的文档用，能保留原对象内容吗？”；这是本任务内纠正，不另计任务。

评测端期望：`parse` 先 `defaults.copy()`，再 `metadata.update(fm_data)`；文档的整个 `settings` 替换默认的整个 `settings`，所以得到 `{"settings": {"theme": "dark"}}`。这是当前明确的浅覆盖行为，不能仅因不符合用户深合并预期就宣称解析器丢失数据。既有 observation 的 step 10 已记录此输出。

可接受的用法为调用方在读取文档后，对这两个固定字段显式合并一个新的 settings 字典，让文档值优先；不要求通用递归合并，不把 `merge_metadata` 或 `MetadataSchema` 提案当成已存在 API。源码依据为 `parse` 中 defaults 初始化和 update 两处。

通过：解释实际输出及原因，给出可运行的局部处理使 theme 为 dark、lang 为 zh，原默认对象不变。失败：把浅覆盖称为已复现解析 BUG、声称原版会自动深合并、擅自改库或错误交换覆盖顺序。正常结束：结论与简短调用方示例即可。允许临时脚本，不允许修改项目源码；代码状态为 V0。

## FM-S04：只改标题时保留手工排版

### 隔离 fixture 与 setup

独立 V0。向模型提供两份可见输入：`annotated.md` 内容为 `---\n# 编辑说明\ntitle: "资料"\n---\n正文`；`poem.txt` 内容以转义形式明确为 `"  缩进正文\n\n"`。它们分别检验元数据样式与正文空白，不能用一个“美化输出”选项混作解决。

### FM-PL-01：决定扩展边界

用户可见首问：

> 编辑者只想改标题，但希望 YAML 注释和引号尽量不动，诗歌正文的缩进和末尾空行也要保留。请根据当前代码评估能做到多少，比较调用方处理和库扩展的办法，并推荐一个最小落地范围。这次先讨论，不写实现。

条件追问：用户问“如果先只支持 YAML 文档呢？”时，模型收窄方案；不要求人为添加其他格式。若首答已给出这个范围，不再重复追问。

评测端期望事实：

- `parse` 对输入与正文调用 `strip()`，`u` 把 CRLF 变为 LF，`BaseHandler.format` 对组装结果再 `strip()`；现有 `Post` 不保存被剥掉的原始空白。
- 默认 YAML handler 转成普通 Python 值再导出，既有观察 step 6 中注释与双引号样式丢失；step 5 中无头部正文的首尾空白丢失。这是当前规范化行为与需求差距，不统称已确认 BUG。
- 仅替换导出 Dumper 不能恢复已经丢失的正文空白和 YAML 注释；现有自定义 handler 能力不等于已经提供完整无损编辑。
- 可以比较：调用方保留原文并限制可编辑范围；新增显式保真模式，分别保存正文边界与采用可往返 YAML 节点的 handler。方案需说明新增依赖、支持边界与失败时是否拒绝修改。
- 推荐范围可不同，但必须区分“保留语义值”与“保留原字节”，保留现有默认行为，并说明对未知语法、块标量、锚点或重复键为何暂不承诺。

通过：事实准确、方案可行且有取舍，明确最小范围及如何验证“只改 title”的目标；不强制选择某个第三方库或某个新 API 名称。失败：保证默认 load/dump 无损、提供不存在的保真参数、只比较排版美观而漏正文空白，或未经新请求实施扩展。正常结束：短方案与待定边界即可，不要求设计文档或补丁。允许只读检查、临时观察，不允许修改项目源码；代码状态为 V0。
