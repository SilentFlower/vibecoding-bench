## 内容单位与数量

| 单位 | 含义 | 计数规则 |
| --- | --- | --- |
| 项目 | 固定真实仓库版本及运行依赖 | 同源副本和不同场景不增加项目数 |
| 业务场景 | 一项具体工作，如排查“配置为什么没生效” | 有不同用户目标、输入和完成条件才单独计数 |
| 对话任务 | 可以独立判断是否解决的一次用户请求 | 稳定 ID；有明确输入、期望与验收；不要求改代码 |
| 对话轮次 | 首问、澄清、提供材料或约束变更 | 不按一条消息新增一个成功任务 |
| 尝试 | 对同一任务的执行、修正或重试 | 累计成本，不增加任务覆盖数 |
| 代码检查点 | 被独立接受的实际代码状态 | 问答任务通过只推进任务进度；代码变更通过后才发布新代码状态 |

理解和用法咨询可以同属一个业务场景，也可以各自独立结束。诊断结论可以作为后来修复的上下文；修复必须有显式用户请求。实现、测试、说明与失败修正共同构成一次工程交付。

每个项目不设置统一任务数、轮次数或类型比例。整个试点覆盖五种使用方式；逐项目根据职责选择有实际内容的组合。每种方式应有可以判断对错的样例，单纯出现一个类型标签不算覆盖。

## 任务编排与代码状态

1. 每个独立业务场景从表中固定提交开始，使用隔离目录和依赖。项目样板要指出用户应用文件与库源码各自在哪里；用现有 API 实现业务需求也可以是工程任务。
2. 只在确实需要前一步回答、诊断产物或已接受代码时声明依赖；独立场景之间没有人为前后置关系。首轮试点采用固定清单，不让模型现场扩题并给自己计分。
3. 同一业务场景内可以保留真实会话；跨场景是否保留会话由执行配置提前确定。同一比较中固定这一选择、上下文范围和任务顺序，不能把某次获得的额外提示默默提供给另一模型。
4. 问答绑定当时的源码与 fixture。修复通过后，后续任务若使用新代码，记录基线提交、已接受差异摘要和应用文件摘要；此状态不是新的上游 commit。原版缺陷不自动沿用到修复后的任务。
5. 用户未授权改源码的解释、诊断和方案任务，可以在临时目录运行复现与例子；被评测的库源码和用户应用源码保持原状态。缓存、临时文件和测试输出与源码变更分开识别。
6. 任务完成、代码能力接受、场景完成与整个项目完成分别判定。因前置失败无法运行的任务记为受阻或未执行，不当作模型回答错误，也不算已完成。

样板中的条件追问属于同一个任务的预先定义分支。说明可提供哪些材料、什么情况下提供，以及什么结果可以结束；不要求机械走满所有分支。

## 用户输入与评测依据

项目文档将用户可见问题和评测端依据分开书写。投放时只发送用户问题、其可获得的材料以及当前轮需要披露的信息；参考结论、评分规则、其他隐藏样例与修复目标实现留在评测端。

每个任务至少明确：用户目标、代码状态、已给材料、允许的改动、必要依赖、自然结束条件和验收依据。用户首问可以很短，准备材料与隐藏验收可以更完整，模型不需要输出研究报告式的长答复。

信息不足的场景必须真实缺少能影响判断的输入，并预先准备可披露材料。合理澄清、正确指出结论边界是有效行为；泛称“资料不足”不直接通过。若材料随后提供，按该任务的完整结束条件继续判定；若用户明确只要确定缺少什么，则按这个较窄目标验收。

## 按任务类型验收

| 使用方式 | 核心依据 | 明确失败的例子 |
| --- | --- | --- |
| 项目理解 | 固定版本的用途、边界、实际入口与关键调用关系；事实能定位到源码或文档 | 编造 API、把增强提案当现有能力、泛谈语言而未回答项目问题 |
| 使用咨询 | 在指定业务输入与依赖下可运行，能得到所需结果；允许等价实现 | 示例使用不存在的参数、正确语法却没有解决给定业务需求 |
| 问题诊断 | 输入到实现的证据链，区分缺陷、正常行为、调用错误与信息不足；在可复现条件下验证 | 只凭现象断言 BUG、把缺少依赖当产品缺陷、已有足够材料仍重复索要同一信息或提出无关追问 |
| 方案讨论 | 覆盖用户的必需约束、说明适用条件与关键取舍，现有能力与新增能力区分准确 | 对无法满足的条件作保证、遗漏必须保留的数据、只有选择名词没有落地路径 |
| 工程修改 | 隔离候选的真实行为、独立冻结用例、适用原生回归和既有能力保持 | 自报通过、仅退出码为零、删除测试、实际导入了另一份安装代码 |

问答以关键事实和证据判断，方案允许多解；不按与参考答案字面相似度或回答篇幅验收。试点先人工核查事实型规则与结果，再校准可自动执行的用例及需要评审的部分；当前没有声称已建成自动问答评分器。

修改任务在冻结时先证明目标在起始代码上未满足，并验证候选能达到目标。业务应用增强验用户应用，库缺陷修复验候选库；两者都核对真实加载位置。纯诊断的复现成功，不等于修复验收通过。

验收使用的源码事实来自已核对的固定版本。若项目样板提出新的 fixture 或断言，仍需独立准备和验证；旧观察里没有出现的执行结果不能写成已经实跑。

## 成本与比较

首要观察结果是用户问题是否解决，再按理解、咨询、诊断、方案和修改分别记录输入 token、输出 token、缓存用量、耗时以及尝试数。缺少可信用量时标为未知，不按字符数估算成真实 token。

同一任务的累计成本包括澄清、补充材料、重试和修正。若验收过程另外调用模型，单独记录评测成本；固定上下文、模型及运行配置后再做比较。只比较最终一轮回复会漏掉真实使用成本。

总结果同时展示逐类型和逐项目数据。跨项目汇总时使用事先确定的权重或分层平均，并公布样本量，避免任务多的项目自然获得更大权重。样板的任务分布不是已验证的真实流量占比，首轮不声称加入问答一定节省 token。

用户要求简洁时，以足够解决问题的事实、示例和证据为完成标准。轮次或运行预算只作为执行上限，超过上限记录未解决或受限；不为了减少输出而接受不完整结论。数值预算和汇总权重在模型试点前另行冻结，本轮没有付费推理或模型成本实测。

## 设计完成与运行就绪的边界

本轮应完成：三份逐项目场景样板、用户问题及条件追问、事实证据、验收草案、状态与依赖、旧需求池取舍，以及跨项目覆盖复核。

进入真实模型试点前仍须完成：

1. 将起始源码、用户应用、输入文件与依赖制成可复建的 fixture，并验证每种合法分支。
2. 把回答的必需事实、允许的等价答案和工程行为断言独立冻结，证明不存在答案泄漏及错误版本引用。
3. 确定会话延续、失败重试、分支披露、运行预算与汇总权重，并接通分类验收和真实用量记录。
4. 以相同配置运行样本，报告解决率与实际累计成本；依据结果调整内容，再决定扩展哪些项目。

本轮状态与复核入口见 [三项目复核](./REVIEW.md)。
