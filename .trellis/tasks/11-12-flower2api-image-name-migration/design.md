# 单部署名称切换设计

## 边界与责任

本任务集中交付一次发布和一次 US 部署维护。现有父子任务映射保持。正式发布目标为 `ghcr.io/silentflower/flower2api-control` 与 `flower2api-account`，标签继续使用既有 `v3-ci-<run>-<attempt>`，发行身份继续 `system-ci-*`。2026-11-13 用户将本版确定为正式维护基线，历史旧版本主动回退退出交付范围。旧包及其签名材料用于安装交接和本次迁移失败恢复，沿既有保护集保留。

控制 Compose 项目及网络使用 `flower2api-<deployment>`；账号角色采用 `flower2api-<deployment_hash>-<environment_id>`，CLI/sender 后缀沿现有规则。省略中间 account 段后，完整环境 ID 加 sender 后缀仍满足 63 字节 DNS 标签限制；网关精确匹配这一新名及原历史名称。保留部署 ID、内部所有权标签与持久目录，避免把外观改名扩展为数据或身份迁移。

## 引用与来源合同

构建及发布默认仅生成新包名。清单读取、账号镜像来源和宿主执行器对新旧两个精确仓库族进行角色及批次匹配；旧来源读兼容承担本次安装交接和失败恢复。未知仓库、混淆角色、错误批次、镜像配置/仓库/内容摘要和原签名检查继续拒绝。公共纯命名规则在实际消费者间复用；新增固定包依赖须同步 SOURCE_FILES 并验证仓库外导入。

数据库兼容演练当前按旧仓库拼接来源 digest，需改为从已验签来源清单获取对应仓库。离线镜像包、清单、Docker 实物及账号 origin 逐项一致。既有数据库迁移协议、签名根和更新目录保持。

## 固定更新器与网络

宿主更新器在 `/opt/vibebench-v3-us/updates/source` 持有独立代码。采用现有固定源码专项运维 SOP：预览精确文件与前后 SHA，核对服务、策略、当前安装、门禁和更新操作，停止服务后更新受信源码及模板，启动并验证原状态。当前 v1→v2 工具对 v2 返回 already-current，本任务沿现有同协议源码维护流程完成本次刷新。

网络寻址根据实际受控容器与已核对部署标签支持迁移前后的两个精确网络名，拒绝歧义。新建和日后重建默认新名。切换时按冻结 ID 处理原 Compose 控制角色和账号角色，保持唯一角色；Compose 项目名称变化后须处理旧项目归属，避免并存角色、宿主端口冲突和遗留网络引用。

更新页的只读来源查询与维护快照共用环境生命周期锁。快照允许最多一秒等待短暂只读占锁，然后继续完整核验；持续占锁仍返回阻塞，防止页面轮询在多个账号更新时误触发恢复。

宿主在控制切换和逐项重建后，最多五秒重复取得新鲜排空证明，期限后仍保留阻塞。环境动作只对服务明确在副作用之前返回的两种排空 409 沿原请求、操作 ID 和代次重试；身份冲突、提交超时及其它错误继续原恢复路径。历史程序的零等待读锁行为同样由宿主收敛等待覆盖。

新控制角色启动后，原账号网络角色以低网关优先级临时接入新网络并保留其精确旧 DNS 别名，账号默认出口继续由原 tun0 持有，以便新调度器继续读取原 sender 的排空状态并逐项重建。只接入当前数据库登记、冻结环境集合内且符合原版/候选镜像及标签的角色。沿原 network-guard 入口原子更新账号命名空间的管理入站规则，管理地址只取本部署新网络网关和实际双控制角色 IP；上游代理与默认拒绝规则沿原入口保留。重建沿原生命周期移除旧角色，临时接入随旧角色收口。控制服务本身只连接一个受信部署网络。

## 一次维护顺序

先完成代码及隔离验收、Check-All、Spec、精确 Git 和正式发行。新包按正式 SOP 配置可见性并验证匿名拉取。随后冻结现场版本、容器、网络、部署配置、固定源码 SHA 与恢复材料，复用更新门禁和锁关闭新认领，等待现有 CLI/API/评审/租约排空。

沿 v2 更新快照及恢复合同保护双库和业务状态。刷新固定执行器，使用同一候选镜像和受信模板重建控制与账号角色，沿原 owner 更新容器关联及环境代次，恢复原资源与内核选择。核对健康、权限、来源、数据身份、原生模板及后续重建命名后开放准入。全程不额外发起付费模型调用；自然业务观测单列。

## 失败恢复

以下已完成的旧包交接机制用于本次迁移恢复与既有材料复用。历史旧版本主动回退保障已退出本次验收范围，后续正式维护以新基线推进。

历史旧控制程序只理解旧包来源。新包回退到旧包时，在双库快照之前，由仍运行的新程序沿同一维护门禁执行 retire 动作，移除原本运行环境的三角色并保留身份及 HOME。宿主持久登记原代次、允许镜像及 CPU 策略，再切换旧控制程序，由旧生命周期重建旧来源角色。中断沿原环境意图恢复。账号内容相同而仓库族改变时也视为需要重建，防止沿用旧名称或把新来源交给旧解析器。

失败恢复旧包时，已登记重建意图的多个新来源角色同样先由候选程序收口，防止旧解析器互相阻断兄弟环境。必要时在原门禁和候选配置下启动候选控制程序；retire 逐项复用允许镜像、登记角色、CLI 孤儿、sender、租约及活动证明，完成后再恢复双库和旧程序。未知角色或候选程序不可读时保持维护关闭。实际 Docker 验收包含两个运行环境和一个停止环境。

本地隔离测试覆盖源码替换中断、网络切换中断和角色部分创建。生产切换前失败恢复原源码、模板、服务和门禁；切换后依据持久操作、原候选/旧版来源及实际容器恢复。快照恢复严格服从 release_started 边界，开放后保留后来业务写入。失败保留已完成 Git/发行事实与准确恢复位置。

当前和最近两套完整历史镜像、全部容器引用及恢复引用纳入保护集。仅沿既有精确清理规则回收已证明无引用项，保持历史 GHCR 包。任务完成以现场迁移验收为准。
