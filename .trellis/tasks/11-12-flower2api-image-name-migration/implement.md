# 执行计划

1. 复用现有 planning 任务并收敛单部署范围，写入研究、设计和 Brief，完成开工评审。
2. 进入 implement 路由并读取平台、调度器及共享指南，核对引用校验、Compose、账号生命周期和所有固定源码消费者的实际定义。
3. 同步新包名发布/拉取/离线包与历史来源读取，修复兼容演练的旧仓库拼接；加入精确新旧角色引用和拒绝路径的定向测试。
4. 同步控制项目、网络和账号容器创建命名；覆盖现存旧名运行、新建/重建新名、真实网络解析及角色归属。保留数据路径、配置键及所有资源策略。
5. 准备受信固定源码刷新及单部署迁移操作单，记录精确根、SHA、服务、容器和网络清单，覆盖前后失败恢复。
6. 验证 `verify_database_definitions.py`；以 `.venv/bin/python` 执行部署工具与受影响调度器测试，运行实际 Docker 的旧命名 → 新命名及本次迁移失败恢复场景，复核双库身份与私有文件、活动拒绝、资源冻结及后续重建。沿 workflow 的来源及数据库兼容验收完整执行。已完成的旧版主动回退资料保留复用，正式维护验收从本版基线起算。
7. 进入统一 Check-All，按结果修复重检，更新权威规范，再展示精确 Git 及发行计划。新增发行元数据按当前正式版本和项目 SOP 递增。
8. 精确推送并手动发布单个新名发行，核对实际源码、原信任根签名、镜像/离线包摘要、两个更新目录和新包匿名拉取。GitHub 首次包可见性按官方界面要求完成，具体人工项在材料就绪后交接。
9. 在线只读重盘点并冻结操作单，按用户本次单部署授权和项目范围检查进入维护；等待养号等在途作业自然结束，刷新宿主固定源码及模板，一次切换并验收。
10. 核对后续新建/重建继续新命名、原生预热和自然请求；按保护集执行既有镜像回收，记录现场结果，再同步本任务进度及 Close。

## 验证与证据

定向合同测试至少覆盖未知仓库、错角色/批次、旧签名字节、离线包引用、控制网络歧义、宿主固定包独立导入、维护占用拒绝和失败恢复。实际隔离 Docker 演练单列证据，测试均使用合成身份及本地上游。

GitHub 正式发行及 US 生产迁移采用本次真实批次；新包可见性和匿名拉取是正式迁移前置条件。首次 Brief 后续接实现，Git 与生产副作用仍执行各自 SOP 的具体范围检查及恢复纪律。
