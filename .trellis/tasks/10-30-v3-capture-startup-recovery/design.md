# 技术设计

## 现有边界

- `images/account/network-context.py` 在网络角色内串行切换监听，严格核对 PID／内核启动时刻，持久 CA 和监听确认由该入口维护。
- `orchestrator/account_runtime.py::_configure_network_context` 执行该入口并核对模式、来源和进程角色；`_finish_capture` 在收口时恢复透传。
- `orchestrator/pi_terminal.py::PiTerminal.start` 为 Projects 和工程养号共用的准备与监督边界。
- `orchestrator/projects.py::ProjectsService._start_work` 保存公开失败，`start` 和 `_manual_retry_event` 共同守住人工启动与自动扫描的差异。

## 私有诊断

1. 为网络切换入口标记固定阶段：读取上下文、停止原监听、准备 CA、启动新监听、确认就绪；失败保存阶段、异常类型、受限栈帧、可用的 errno／返回码和实际执行来源。
2. 使用 root 管理的私有运行目录；目录 `0700`、文件 `0600`，原子发布，拒绝链接，单条诊断限制为 64 KiB。只提取固定字段和栈位置，不复制局部变量、环境、请求正文或任意异常原文。
3. 网络角色保存 `/run/v3/diagnostics/<随机ID>.json` 并返回 `VIBEBENCH_NETWORK_ERROR_V1` 固定协议；管理端在清理前取得本次事实，在 `<数据根>/<projects|warmup>/startup-failures/<随机ID>.json` 留存，记录绑定工作、代次和可用的作业 handle。清理故障独立记录，不能覆盖原故障。既有安全目录和原子发布函数移至标准库模块 `runtime_files.py` 供双方共用，`account_runtime` 保留原导出，不引入日志依赖或公共错误 API。
4. 公开 `failure` 继续遵守原字段白名单及固定提示；私有诊断写入失败不吞掉原异常，也不放行启动。诊断只在失败边界产生，不记录轮询心跳。

## 网络行为修复策略

- 先使用可控的实际进程夹具和同批账号镜像进行重复切换演练，保留阶段及退出事实；验证进程恰好退出、PID 复用、未知 PID、监听启动失败及再次收口。
- 只有可复现或直接证据确认的问题才进入行为补丁，并同步对应回归。若历史故障不再出现，交付诊断与受控恢复能力，结果明确保留“历史具体异常不可还原”，不编造根因。
- 保留进程归属核对、定向 TERM／KILL、有界等待与共享执行的原保护，不能以全局杀进程或重启整个账号代替收口。

## 已确认的实现依据

- 本机真实 `/proc` 文件已打开后收口并回收进程，随后读取 `stat` 和 `cmdline` 均稳定返回 `ProcessLookupError / errno=3`。原代码只捕获路径消失，新增回归在修复前出现两个真实内核错误；修复只把该已退出状态与 `FileNotFoundError` 一样处理，未知 PID 校验保持。
- 原连接重试块覆盖 CA 发布和确认写入，CA 的 `OSError` 会被当作连接失败吞掉。故障注入现要求一次发布即保留 `publish_ca` 与 errno；重试只覆盖 socket 建连。
- 本次两个已验证问题不能证明历史事件 `27231` 的具体触发原因；历史结论仍按证据边界保留。

## 人工恢复

- 复用现有 `/api/projects/agents/{account_id}/start` 和工程养号同构入口；在 `scheduled=False` 的人工路径，为 `startup_unknown` 增加独立准入分支，不将其无条件加入错误白名单。
- 仅处理 `phase=preparing` 且 `started_at`、`segment_started_at`、`runtime_json` 均为空的当前原工作；必须不存在任何输入动作、原生会话或尚未确认的执行，角色归属、环境状态、账号身份及冻结合同均匹配。
- 运行时通过实际账号环境和原生会话位置核对收口，不把公共摘要缺少字段当作空闲证明；任何证据缺失、未知或检查失败均保留阻塞。
- 复用 `start` 已有服务锁、写锁、当前工作／最近错误重读和原子 `manual_retry + generation` 发布过程；不在事务外先把数据库改成 paused，不伪造 `operator_diagnosis` 类型。
- 工作 ID、会话、cwd、冻结设置和抓包开关保持；原 `failure` 留到 `_start_work` 完成终端、基线和门禁确认后才标记恢复。已经开始过的工作不由本分支放行。

## 交付、兼容与回退

- 无数据库迁移、无前端布局或 cc2api 协议变更。两个 Pi 工程空间共享诊断与准入实现，公开失败合同保持兼容。
- 管理端和账号镜像联合构建、发布并核对同批清单；发布前按 Trellis 完成 Check-All、Spec 评估和 Push 计划评审，不能直接覆盖线上 Python 脚本。
- `us` 沿用既有不备份、不重算内存的运维选择。部署前核对 API、租约、CLI、两个 Pi 控制者及未知输入已收口；保留原 HOME、成果、冻结项目版本和最新凭据。
- 健康验收后按项目 SOP 定向回收旧镜像，保留当前、最近两个完整历史批次及全部容器引用。
- 回退仅使用已核对的兼容同批镜像／清单，保留最新持久状态；不得用旧数据库或 RT 覆盖现有资料。
