## 阶段二：逐批交付全部九十仓

下列步骤对三个阶段内全部小批重复，不因达到某个中途项目数或任务数而结束：

1. 恢复本阶段子任务，读取本小批实际源码与现有研究，细化场景、材料、依赖、合法结果和验收；内部小批不再创建任务，已确定的全量目标不反复重问。
2. 由auto-loop prepare完成readiness和Brief后，仅按runner的start_task／run_implement动作启动本批并进入 `trellis-route(target=implement)`，读取before-dev及实际类、字段和函数；母任务只在队列最后执行整体集成。
3. 核完整源码和许可，准备真实离线依赖，在当前目标镜像校准原生集合与资源，冻结逐仓任务表和准入报告。
4. 制作内容及必要最小原生适配，每个修改留原版失败、参考通过、错误候选拒绝和完整适用回归；只读任务验证可执行事实。
5. 跑全部新增默认任务和必要材料分支的真实产品链mock验证，对照页面／API／数据库及角色、预算、用量。
6. 按runner动作进入正式检查、有限修复和规范同步，完成精确本地提交；同名record成功后立即next，真实模型和生产部署状态分列。
7. 将本小批实际证据保存在本阶段任务，继续该阶段剩余项目，三十仓全通过后才结束阶段。母任务台账在最后集成统一更新，其他队列项规划不改；阻塞项保留回访条件，独立阶段按runner继续。

## 验证与回退

规划校验JSON、完整提交、来源摘要、九十仓全集及批次无重漏。初始 `python3 scripts/validate-project-library.py` 的10／45／107只是规划基线；最终重算100／426／726，并与三阶段来源、业务、产品链及完整交付原件逐项对账。保持原研究快照、旧十仓及所有无关工作区字节；SQLGlot私有外部测试继续明确未验证。全量API探针只在临时合成数据库运行，不启动候选或后台线程。

每批按实际修改选择定向验证，已有入口为：

```bash
python3 scripts/validate-project-library.py
python3 -m unittest discover -s orchestrator -p 'test_project_*.py'
```

单任务通过 `scripts/validate-project-scenarios.py` 的实际项目／任务／镜像执行；原版修改目标用 `--expect failed` 留证，参考用 `--with-regression` 联合验证。集成沿 `deploy/v3/run_local_verification.py` 的隔离清单入口，逐批冻结真实可复跑命令，不复制过时测试数。

来源、候选绑定、原生集合或资源不符时留失败现场并修根因，不删节点、降合同或增账号预算。尚未准入的内容留研究区；单仓受阻可调整队列但不缩小全集。真实模型、账号、生产或新外部边界未获授权时不执行该类步骤，本地内容工作继续推进。
