# V2 回执恢复与中央滚动更新设计

## 已核对的入口

- Gateway 的 `tui_native_drain::awaiting_v2_tools` 和 `occupied_v2` 分别提供平台级和账号级布尔值。待回执和已认领的状态使用不同前缀。现有工具账本没有逐条过期时间。
- 宿主更新器在 `HostDeployment.capture`、`drained` 核对平台布尔值。旧 Gateway 在 `system_update_cutover` 再拒绝一次。后台换版已有账号级 `_rollout_lease`，可等待原账号空闲。
- 账号 sender 的 `SessionDriver.idle` 反映还在驻留的会话。现有绑定、账号、节点分配及环境代次证明可以组合复用。缺响应、缺能力或只得到空绑定均列为待核对。

## 回执对账

1. 由 Gateway 分批读取待回执行，绑定当前账号、记录 ID、账号发送器身份、会话和原工具组。后台及人工入口使用同一个对账动作。探测走只读、无唤醒路径。
2. 优先使用同一绑定的原会话状态。实现前核对可复用的 sender 查询，缺少粒度时新增受信的只读查询。旧 sender 只提供整体状态时，原绑定与账号活动复核一致后可采用其完全空闲证明。已核实的编排停止或隔离证据也可证明原进程退出。探测因失联、权限或代次不符失败则为待核对。
3. 写入前重新核对原行、绑定与账号活动。用事务条件更新保留工具组摘要的终态标记。复用旧版本能识别的禁止重放结构。已认领但投递结果不确定的轮在确认原进程和在途工作已结束时可以按无重放原则收口，保留不确定原因。历史记录采用实际结束证据，避免用推算的行年龄决定回收。
4. 正常认领和恢复使用同一记录条件。认领抢先则让原轮完成。恢复抢先则后来的工具结果得到原轮已结束的提示，模型投递为零。优先以现有两库结构实现。

## 更新管理入口

- Gateway 管理路由提供脱敏回执状态和精确单条恢复入口。返回账号、公开状态以及可刷新或恢复的操作，写入携带当前行的版本凭据。按钮行内展示执行中和结果，旧状态冲突需刷新。保持既有管理员鉴权、限幅及隐私边界。
- 人工按钮立即核对所选记录，后台自动核对沿用同一证据链和写入条件。失联返回「该账号延期、平台可继续」，保留记录及账号更新进度。连接恢复后，单条按钮可再次立即核对并续办，后台在现有轮询和账号重试机制中也会续办。重复或并行触发复用现有账号归属和并发保护。收口以原进程已退出且该轮无在途工作为条件。

## 中央与账号滚动边界

- 原版和候选满足既有后台滚动能力，且原账号来源可被完整保留的安装，消费账号级待回执投影。中央继续验证同 epoch 和在途 API、写入、快照等全局条件。受影响账号留在原 sender，与其他账号的换版解耦。
- 编排沿原滚动授权登记可信旧镜像和代次。保留对应节点的原账号身份。更新重试只能收口原账号。需要实际重建该账号时，先证明原工作收口。
- 第一跳先按 `deploy/flower2api/SYSTEM-UPDATES.md` 的 v2 同协议源码维护流程交付固定宿主执行器。核验已签发行、关联源码提交、固定安装根、原服务 ExecStart、策略与受信模板，以及本次变更文件的原新 SHA256。安装器 `SOURCE_FILES` 下已登记的 `deploy/v3/system_updater.py`、`deploy/v3/system_update_host.py` 为宿主逻辑路径。以最终改动生成精确替换清单。在服务空闲、门禁为 idle 时，经私有备份并按现有服务与存储锁合同刷新文件，再验证服务、原安装状态、revision、门禁和签名目录。刷新失败按原备份恢复文件和服务。
- 刷新后使用原系统更新入口安装签名候选。实际旧网关仍拒绝带待回执的强制 cutover 时，仅对已知兼容版本及可完整保留原账号环境的滚动操作采用自然排空。保持维护门禁并核对同一 epoch，确认全局活动和写入排空后执行原冻结、双库快照、数据校验、控制切换和开放准入。每个失联账号保留自身来源与待办，中央及其他账号照常完成。隔离演练以真实旧宿主和旧网关为起点，线上操作由主窗口统筹。
- 需要停止或重建原账号的非滚动路径按实际活动和归属核对。快照恢复和重新开放接单的时序沿原维护操作。
