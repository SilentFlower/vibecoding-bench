# 反重力默认登记运行环境并持续补热

## Goal

用户添加反重力账号后即可在运行环境中看到对应卡片。符合运行条件的账号能在首个业务请求到达前获得一个可用热进程。

## Background

- v1.30.0 线上账号 #16 已启用且 OAuth 就绪，对应环境仍未登记。现有登记由首次唤醒绑定触发。[环境入口](../../../services/orchestrator/agy_placement.py#L68)
- 线上 #14 的发送器在升级后处于第 23 代，容器已运行，AGY 实测为 `unprepared`，进程数 0。现有池规则负责保留已有基础热进程。启动和定时补热由 `native293` 协调器处理。[AGY 状态](../../../services/gateway/src/service/agy_runtime.rs#L596) · [后台巡检](../../../services/gateway/src/service/native_prewarm.rs#L95)

## Requirements

- **R1 默认登记。** AGY 账号正式保存且凭据就绪后，在控制链路正常时默认登记唯一运行环境。卡片沿现有账号名称、编号和执行归属显示。首次准备前显示「等待准备」。控制服务暂不可用时保留已保存的账号，恢复后自动补登记。系统启动或巡检时也补齐已有账号缺少的绑定，包括 #16 这类账号。
- **R2 持续补热。** 新登记账号具备启动条件后由后台首次准备。已运行环境在进程归零、凭据换代或发送器重启后自动补热。账号闲置且有空闲物理容量时准备一个实际可接单的 AGY 热进程。准备期间的业务模型提交数为零。模板准备使用热进程之外的空余名额。
- **R3 生命周期与容量。** 自动准备遵守账号停用、凭据、手动停止、节点、迁移、环境维护、系统更新及既有容量规则。容量不足时保留卡片并等候。同账号的重复准备合并。业务执行和工具等待沿原作业与凭据代次收口。
- **R4 真实状态。** 运行环境可观察等待准备、正在准备、实际热就绪和失败。热进程数来自当前环境的实际观测。用户能看到账户暂停、等待容量或准备故障的实际原因。

## Acceptance Criteria

- [ ] **AC1 / R1** 从正式添加路径保存新 AGY 账号后，首次读取运行环境即可看到唯一卡片。旧库中已就绪但缺绑定的账号在启动或巡检后出现。重复保存通知、补登记与首次真实调用竞争时保持单一环境及原执行归属。
- [ ] **AC2 / R2** 原版 AGY 隔离环境覆盖新增账号、发送器重启、基础热进程退出和凭据换代，均可补出一个有效空闲进程。准备的上游模型提交数为 0。首次业务请求使用该热进程。容量为 1 且开启 CRIU 时仍获得热进程。
- [ ] **AC3 / R3** 已停止、停用、迁移和维护中的环境保持相应状态。节点容量用尽时已有环境持续运行。容量释放后符合条件的账号继续准备。核对同账号准备合并、业务和工具轮的归属，以及实际模型提交次数。
- [ ] **AC4 / R4** 从等待到热就绪的页面状态与发送器一致。准备故障可见，恢复后能清除历史失败。本机及受管远程既有归属、Claude Code 原生预热和 AGY 工具续轮通过回归。

## Scope Boundary

- 本轮交付默认登记、后台零模型补热、相应状态、代码和隔离验收。实际发版及上线沿项目发布流程。
- Messages 工具轮系统补充和缓存前缀归另一窗口的转换工作。两项共用 AGY 业务回归。
