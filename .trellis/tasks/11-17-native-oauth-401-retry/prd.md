# 原生转发 401 时复用已更新的 OAuth 凭据

## Goal

同账号在请求期间更新了 OAuth 凭据时，让网关有机会在内部恢复这笔原生 Messages 请求。

## Background

线上账号 11 在 19:13:15.021 提交原生 2.1.280 请求，于 19:13:16.722 收到上游 `authentication_error` 401；账号同一秒记录了凭据刷新。原生路径当时只发送一次（`services/gateway/src/service/gateway.rs:2488`）。刷新与上游撤销的因果关系仍未验证。

## Requirements

- R1：完整收到真实上游返回的 HTTP 401 且结构化错误类型为 `authentication_error` 时，只读检查一次账号凭据。仅当同一账号当前持久化的 OAuth access token 与首次实际发送的 token 不同、仍有效，且原请求预算有余量，才允许同账号重发一次。
- R2：没有满足条件的新凭据、认证错误不明确、尚无实际提交证据，或重试预算不足时，保留初次 401。第二次 401 直接返回。
- R3：重试仍使用冻结的原生版本和请求策略。请求诊断分别保留实际发送的两次尝试，并标识凭据复用原因。

## Out of scope

- 主动刷新 OAuth、增加轮询或等待 token 更新、因 401 停用账号或换号。
- 数据库结构、配置开关、页面、原生 sender 协议、发布或真实账号模型调用。

## Acceptance Criteria

- A1（R1/R3）：用合成上游复现首次使用旧凭据返回 401、其间持久化新凭据；网关第二次使用新凭据，调用方收到 200，诊断记录两次尝试。
- A2（R2）：裸 401、其他错误类型、同一枚 token、无有效新凭据、状态不明或预算不足时，保持首次状态、错误正文和响应关联 ID，只发送一次。重复 401 最多两次发送。
- A3（R2/R3）：原有签名修复和 429 行为在各自独立场景保持，认证与签名修复不得为同一轮选择叠加额外作业。
