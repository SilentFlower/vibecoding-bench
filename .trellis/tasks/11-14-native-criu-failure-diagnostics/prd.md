# 补齐 CRIU 恢复失败诊断

## 目标

使CRIU模板建立或实例恢复失败后，运维能从脱敏日志及有界私有摘要定位失败阶段、异常类别和底层错误线索，并核对后台补暖与业务本地准备的耗时归属。

## 背景与证据

- 线上v1.5.0账号10-30在2026-11-14T01:47:02Z的一次后台补暖恢复失败，控制器仅输出RESTORE_OPERATION_FAILED，该轮后台补暖总耗时1855ms，包含恢复失败和普通exec回退；01:48:08Z新模板就绪。
- 同源前两次恢复成功耗时848ms、680ms。现场OOM与PID限额触发计数为零。该次底层根因仍未知，原失败目录已被清理。
- 改动前（96d81fb1）的controller.py:299在finally清理实例目录；controller.py:322-330将多种异常合并成通用码。supervisor.py:47-55在CRIU失败时以111退出，控制器可能只得到空报告的解码异常。
- native_runtime.rs:1986的checkout优先使用空闲worker，2022在缺空闲时才等待后台spare；2188的start_spare异步补暖；2340-2365记录checkout/prepared等计时。现场40笔原生样本均命中暖进程，准备中位数73.5ms，前27笔checkout均为0ms。
- 既有账号runtime/native-criu以root私有目录绑定至/var/lib/ccrb-criu，适合在原清理范围之外保存有界脱敏摘要。

## 需求

- R1：模板与恢复失败记录明确阶段、受控异常类型、可用errno、原受控reason和关联的模板/worker/实例规范UUID；字段缺失保持显式未知。
- R2：监督进程的CRIU退出码及脱敏错误分类，在控制器清理前汇总。下游空报告错误保留上游失败摘要，原始错误与派生错误分别标记。
- R3：只保留结构化白名单元数据与受控CRIU源码位置/错误分类；异常原文、原始stderr、环境、凭据、业务正文、快照内存、配置及完整文件路径排除在摘要之外。
- R4：清理实例/模板后，root私有失败摘要仍可读取；最多32条、每条8KiB，目录0700、文件0600，拒绝链接及外来文件归属，轮换只触及受控摘要。
- R5：取证写入、解析或输出失败沿现有退出和清理路径收口，正常取消维持原语义；业务唯一投递、回退截止、并发/内存预算及进程生命周期保持原合同。
- R6：正式源码、打包画像与images/v3/criu分发输入同步；记录本次线上补暖与业务等待的实际计时边界。

## 验收标准

- [x] AC1：注入打开文件/管道、创建namespace、读取报告和映像校验等失败，输出对应阶段与异常类型，有errno时保留精确整数。
- [x] AC2：模拟CRIU非零退出、监督进程异常或空报告，清理后仍有受控上游摘要，可区分CRIU执行失败与控制器报告解析失败。
- [x] AC3：含合成bearer、邮箱、会话内容、私有路径和换行的异常/日志样本在所有持久摘要与输出中均不泄漏。
- [x] AC4：容量、权限、链接/硬链接、外来归属、损坏和超限副摘要边界通过；第33条触发有界轮换；写入失败不妨碍原失败清理及回退。
- [x] AC5：现有dump/恢复失败、模板撤销、取消、FD与pidfd清理回归通过；成功路径原有身份和熵检查继续通过。
- [x] AC6：导出逐文件与source-manifest核对，打包画像包含新增模块；本地故障注入和成功/失败清理链路通过。

## 范围外

- 本次不新增前端、管理API、自动重放或真实模型调用。
- 生产部署与复现线上失败另行安排；历史缺失的根因保持未知。
