# 迁移 flower2api 部署源码并归一 CI 入口

## Goal

将统一平台的部署源码和日常入口统一到 flower2api 命名，清理导入网关的旧工作流，同时保持现有实例的原地升级与回退能力。

## Background

- 用户明确要求将 `deploy/v3/` 改名迁移，并核对、清理 `services/gateway/.github/workflows/` 中的遗留配置。
- 当前正式入口在仓库根 `.github/workflows/`；网关子目录包含原独立仓的 `docker.yml`、`release.yml`，引用旧 `web/`、`docker/Dockerfile` 和 `.version`。根工作流及当前脚本未引用这两份子目录文件。
- 已安装更新器的固定文件清单、Compose 策略和 systemd 启动路径使用 `source/deploy/v3/`。历史签名发行和数据合同继续沿原身份维护。
- 全量规范清理与经验合并归同父任务下的规范子任务，本轮负责新路径和来源合同同步。
- 当前源码分支为 flower2api，基线 eda1a735cee4fd53622f7e5b70966630d973f796。现有349项工作区文件按原归属保留。

## Requirements

- R1：当前仓库的部署源码、夹具和说明迁至 `deploy/flower2api/`，保持文件内容与执行位所需的原合同。当前源码树以新目录作为唯一正式部署源码入口。
- R2：日常脚本、根CI、构建缓存指纹、验证工具、README、单仓说明和有效spec均指向新源码目录；历史资料和固定宿主逻辑路径明确归类。
- R3：原固定宿主包路径、systemd归属、Compose策略、发行身份、签名信任根、镜像与配置标识、双库合同及账号数据归属保持兼容。原版本升级和回退继续可用。
- R4：删除迁入网关的两份失效工作流，构建和手动发布统一由根CI管理。原项目来源和版权记录继续保留。
- R5：保留已有脚本调用的兼容入口，为日常使用提供flower2api命名的脚本入口。
- R6：迁移前后进行来源选择、固定包独立导入、构建发布合同及真实隔离更新/回退验证，保留可审计的实际结果。

## Acceptance Criteria

- [x] 所有受版本控制的部署源文件与夹具位于新目录，当前源码入口、CI及有效文档链接可解析。
- [x] 新旧源码布局及固定宿主包均能正确读取所需源码；新布局缺失文件时拒绝混用残留旧文件。
- [x] 固定文件包能在仓库外独立导入；安装、底座升级与恢复的固定目标、权限和服务归属验证通过。
- [x] 两库定义与迁移登记摘要保持，纯目录迁移保持组件内容身份；完整部署与发布合同回归通过。
- [x] 网关子目录的两份工作流已清理，根CI继续只构建和明确手动发行，来源校验与缓存接线验证通过。
- [x] 新脚本及旧兼容入口转发参数和退出状态正确；实际构建与隔离更新、回退的验证记录覆盖本次路径变化。
- [x] 原349项工作区内容及历史来源正文按原归属保留。

## Non-Goals

- 正式发版、生产安装、生产数据或账号操作。
- 更换已有V3环境项、镜像、签名通道、workflow文件身份及系统服务身份。
- 网关独立发行能力的新建、Rust重写或编排器业务模块重构。
