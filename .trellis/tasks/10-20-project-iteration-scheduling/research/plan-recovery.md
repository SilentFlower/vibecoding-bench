# 推进计划、轮换与超时接续

## 已确认需求

- 用户接受轮换前连续完成步数可配置、默认 5，只有独立验收通过的步骤计数。
- 用户要求另加“一次计划推进 N 步”，默认 2；询问推进约 1.5 步后超时，下次从哪里继续。
- 用户已明确选择同一次 CLI 会话内推进 2 步；正常计划对应一个 Run，不能拆成两个独立单步 Run。
- 同账号不同项目真正并行，同一项目不能并发改写目录；5h／7d 额度阈值、运行窗口与随机补位间隔共同限制新投放。

## 当前代码证据

- `orchestrator/project_iteration.py:620` 的 `_reserve()` 只取 `next_step_index` 指向的一个步骤，提示词明确只做该步。当前没有多步骤计划，不能宣称已有一次执行推进 2 步的能力。
- `_reserve()` 将首轮及修复分别写入 `tasks`、`runs` 和 `project_step_attempts`；`run_id` 在尝试表中唯一。若单 Run 承载多步，不能直接复用现有一对一约束。
- `orchestrator/main.py:6959` 附近将退出码 124 识别为 `timeout`。`_inspect_attempt()` 等待严格释放后，将非 success 的执行送入 `_finish_failure()`，当前不会仅因超时现场看似实现了功能便自动推进步骤。
- `_finish_failure()` 保存候选快照和失败报告，保持实际工作目录；未耗尽修复次数时实例回到 ready，下一尝试继续原步骤。既有修复使用新 Run，不应描述成原超时 Run 直接变回 running。
- `_verify_attempt()` 执行基线及截至当前步骤的回归，通过后在事务中校验父代次、步骤下标和预期检查点，再更新 `checkpoint_digest` 与 `next_step_index`。独立验收不能依赖模型文字中声称“完成了一半”。
- `test_project_iterations.py:test_repair_uses_existing_files_and_regresses_prior_capabilities` 覆盖修复使用不同 Run 但相同工作目录；`test_restart_retains_workspace_and_pending_step` 覆盖重启后保留现场和待处理步骤。本轮仅阅读，没有新增或运行测试。

## 拟定的接续语义

计划目标范围一经创建即固定，例如从路线第 1 步到第 2 步，不能在恢复时改为新的第 2～3 步计划。计划需要保留已接受检查点、下一个未接受步骤、剩余目标和失败证据。

| 事件 | 计划验收进度 | 当前工作目录 | 下一动作 |
| --- | --- | --- | --- |
| 建立第 1～2 步计划 | 0／2 | 原已接受代码 | 从第 1 步开始 |
| 第 1 步验收通过 | 1／2 | 第 1 步成果 | 保存检查点，推进第 2 步 |
| 第 2 步只做了部分后超时 | 1／2 | 保留第 2 步未完成改动 | 保存失败证据，在门禁允许且未耗尽重试时继续第 2 步 |
| 第 2 步随后验收通过 | 2／2 | 第 2 步成果 | 结束原计划，再建立第 3～4 步计划 |
| 第 3～4 步通过 | 本轮累计 4／5 | 第 4 步成果 | 剩余连续额度只有 1，本次只计划第 5 步 |
| 第 5 步通过 | 本轮累计 5／5 | 第 5 步成果 | 轮换项目，未来返回从第 6 步接续 |

“做到一半”的物理文件状态和“验收通过”的逻辑状态分开保存。未通过步骤不能贡献小数进度；恢复只继续该步的剩余工作，并回归此前已接受能力，不能为了重现已通过版本而自动丢弃未完成改动。未确认通过的第一步也不能仅凭模型描述记成 1／2。

当前一次一 Run 的机制能提供每步释放后的独立验收。新需求已确定为单 CLI 内多步，必须增加每步完成后的真实验收交接和检查点，不能等整次执行结束后才用一句总结推断中间进度，也不能拿含后续半成品的最终工作副本冒充先前一步的历史快照。超时旧 Run 保留终态，恢复 Run 关联原计划和可核对的原会话，不把失败记录改写成成功。
