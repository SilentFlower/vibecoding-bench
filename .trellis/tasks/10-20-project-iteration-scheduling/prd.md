# 项目迭代调度策略配置

## Goal

沿用 Tasks 的交互与调度方式，为项目迭代提供同账号真实并行、可配置运行节奏和同一 CLI 会话内的多步计划，并能在超时或重启后保留已验收进度及未完成现场。

## Background

- 现有项目模式仅配置账号、名称和项目键，后台固定活动池 3、按阶段轮换、每次 1800 秒和最多追加修复 2 次；`next_launch_at` 有列但没有实际间隔调度。
- Tasks 的 `BatchIn`、`create_task_batch()` 与 `_execute_batch()` 已提供并发、单次超时、随机间隔、创建时一次洗牌和持久等待，可作为一致的产品参考。
- Git 历史确认：2026-10-12 的 `34f56c02242f43d996fb63e5a42a176f66e65492` 将 `orchestrator/main.py:82` 的账号默认并发 2 改为 v3 强制 1，Tasks 页面仍允许 2。`AccountRuntime.claim()`、单执行清理及网关单 CLI 租约也需配套调整，不能只改表单或信号量常量。
- 当前每 Run 只做一步，尝试表限制单 Run 只关联一次尝试，业务验收依赖整次执行严格释放。新需求需要支持同会话逐步验收，并保持旧批次、历史 Run 和不可变成果可查。
- 调度证据见 `research/tasks-scheduler.md`，接续证据见 `research/plan-recovery.md`，进程隔离可行性和验证限制见 `research/runtime-concurrency.md`。

## Requirements

- R1：项目批次参照 Tasks 展示参数表单、有效容量、策略摘要和等待原因。参数严格校验，不接受 bool、字符串、小数或非法组合，不静默改成另一个值；账号额度只显示继承来源并沿用原账号设置入口，不保存互相冲突的批次阈值。

| 参数 | 新批次默认 | 行为 |
| --- | --- | --- |
| 执行并发 | 2 | 沿用 Tasks 的 1～2 范围，不超过账号和所选活动项目的真实容量 |
| 活动项目池 | 3 | 最多保留该数量的活动项目，实际不超过所选数量 |
| 轮换前连续完成步数 | 5 | 仅验收通过的步骤计数 |
| 一次 CLI 计划推进步数 | 2 | 同一次会话逐步执行，受本轮剩余步数和路线结尾截短 |
| 单次执行超时 | 1800 秒 | 约束整个本次 CLI 计划执行，不按每步重置 |
| 计划补位随机间隔 | 0～0 秒 | 零表示不额外休息，上下限可配置；同一计划内部不额外随机等待 |

- R2：新批次创建时将所选项目随机打乱一次并固定初始队列；首批活动池来自队列头部，完成或阻塞离池后从原队列补入。暂停、重启或刷新不能重新洗牌，未实际开始的项目不提前创建工作目录。
- R3：同账号不同项目的 CLI 真正并行，一并修复 Tasks 在 v3 下配置 2 却实际串行的问题。普通 Tasks 与项目批次共用账号容量，多个批次不能叠加绕过上限；同一项目只允许一个在途写入执行。活动池、CLI 并发和全局活跃账号容量分别表达。
- R4：单项目按路线依赖推进，达到连续完成步数后轮换，返回时接续未完成位置；失败、超时及修复不重复计步。项目完成或局部阻塞后其他可执行项目继续，不因轮换或阶段标签变化重置代码、数据或进度。
- R5：随机间隔作用于两次 CLI 计划的补位。参照 Tasks 先填初始并发窗口，后续补位等待持久截止；等待不暂停兄弟执行、不占 CLI 许可，重启不重抽，到期仍须复查账号、身份、窗口、额度、父批次状态和真实容量。页面显示下一投放时间及未放行原因。
- R6：复用账号现有 5h／7d 已用百分比阈值。任一有效窗口命中启用阈值后不投放后续计划或新的失败恢复；当前已投放的 CLI 计划按冻结范围完成，同会话后续步骤属于本轮范围。窗口重置或真实额度更新后按原被动恢复规则继续，并保留间隔和运行时段限制，不在自然日零点自行清除门禁。未知额度、真实耗尽、认证异常及 API 的原行为保持；不新增主动 usage 或模型探测。并行在途可能越过自设比例，不承诺精确卡住消耗；token 继续如实统计，缺失显示未知。
- R7：暂停禁止新计划，已投放计划允许完成并验收；停止、删除、身份变化、认证错误和实际额度耗尽沿用原门禁强度。并行执行的会话、日志、验收、采集和清理按执行隔离，停止或暂停验收一个作业不影响兄弟作业。登录、重授权及环境维护保持排他保护，不增加 CLI 权限或重抽账号画像。
- R8：正常一个计划对应一个 Run，实例与步骤均能关联该 Run；执行状态和逐步业务验收分别显示。保留已认可的 UI、Tasks→Projects→Runs 导航、英文任务内容、持久目录、原 cookie 鉴权与其他任务模式。共享 Run 的步骤统计不得重复累计整个 Run 用量，历史成果不能用当前工作目录冒充。
- R9：一次计划在同一个 CLI 进程、tmux 和 native session 内逐步推进，每步独立验收并保存检查点后才继续下一步，不能用多个单步 Run 归组冒充。计划固定路线目标范围，恢复先补原计划剩余步骤，不重新追加 N 步；例如默认一轮拆为 2＋2＋1。
- R10：进度只以独立验收和已保存的检查点为准。第 1 步通过、第 2 步做到一半超时时，保留第 1 步成果和第 2 步未完成改动，计划显示完成 1／2、剩余 1 步；下次从第 2 步现场及可核对的原会话接续。超时旧 Run 保留真实终态，恢复另记 Run 并关联原计划；真实 quota_wait 则继续原 Run。不能重建 seed、重做已通过步骤、跳过待完成步骤或虚记小数进度。每步保留首轮加最多两次修复的上限，耗尽后保留现场并阻塞该项目；会话或检查点证明缺失时明确阻塞，不悄悄换会话。

## Acceptance Criteria

- [ ] AC1（R1、R3、R5）：新表单与详情显示一致的保存值、账号上限及额度继承来源；非法值或组合不落库、不启动执行。
- [ ] AC2（R2）：固定随机源能证明只在创建时洗牌一次，恢复不变；创建 100 项目元数据不产生项目目录，首次真正运行才发布对应目录。
- [ ] AC3（R3、R7）：同账号、至少两个就绪项目、并发 2 时，两个实际 CLI 存在重叠执行区间且 session／Run／cwd 不同；Tasks 同账号并发 2 也实际生效。多个批次和混合 Tasks／Projects 总执行数不超过账号上限，同一项目不并行改写。
- [ ] AC4（R4、R9）：默认按 2＋2＋1 推进并在累计 5 步通过后轮换；失败和修复不重复计数，返回后继续下一未完成步骤，重复事件不能重复接受。
- [ ] AC5（R5、R7）：首批填满后，后续计划严格遵守持久随机间隔；双执行同时收口、暂停／恢复和服务重启均不跳过或重抽。额度或时段晚于间隔时继续等待，计划内部不被额外拆成独立补位。
- [ ] AC6（R6）：5h／7d 任一有效阈值命中后，已投放的两步计划允许完成，后续计划及新的恢复执行等待；阈值调整、未知额度、重启、跨自然日和两个执行共同更新仍沿用账号规则，无新增 usage／模型探测请求。
- [ ] AC7（R7、R8）：暂停、停止、capture／续聊、登录／重授权、删除和额度恢复相关回归通过，保持身份、HOME、原资源预算、英文提示及持久项目成果。
- [ ] AC8（R9、R10）：同一正常 Run 和 native session 真正完成两步，步骤之间有独立验收及检查点。第 1 步通过、第 2 步半成品超时后，原 Run 为 timeout、计划为 1／2，轮换或重启返回后原目录和半成品保留，恢复 Run 只完成剩余一步。
- [ ] AC9（R7、R9、R10）：验收期间当前作业写入已暂停而兄弟继续；脱离进程组的后台子进程、PID 复用、重复决定、接受后重启、输入消费不确定及旧代次回包不能误停兄弟、虚增进度或篡改历史；证明缺失时明确阻塞。
- [ ] AC10（R8、R10）：迁移重复执行保留旧尝试 ID、Run、prompt、内容和成果；两步共用 Run 后步骤统计不重复汇总整个 Run，缺失统计仍为未知；明暗／窄屏、SSE 状态与 Runs 链接经过实际 UI／API／DB 验证。

## Non-Goals

- 不用模板生成内容替代真实 GitHub 工程。逐仓检出、基线测试及路线分析继续独立推进，本任务不把现有 100 个种子项目宣称为真实仓库，也不直接替换生产项目库。
- 不新增每日累计时长、次数或 token 预算，不承诺降低封禁或达到特定 token 用量；不改变 OAuth 协议、账号固化画像及原资源预算。
- 本轮不直接提交／推送、发布镜像、部署生产、调用真实模型或启动生产批次；这些操作沿各自工作流与适用授权执行。
