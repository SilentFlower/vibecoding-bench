# 项目迭代调度与同会话多步计划设计

## 1. 边界与默认行为

本任务修改项目批次、账号 CLI 运行时、网关运行租约及其必要的 driver／UI 适配；同时修复 Tasks 在 v3 下配置并发 2 却实际串行的问题。真实 GitHub 仓库替换保持独立，当前内容库、英文任务、账号身份和目录归属不在本任务中重建。

新建批次使用策略 schema 2，默认并发 2、活动池 3、连续完成 5 步后轮换、同一次 CLI 计划推进 2 步、单次执行超时 1800 秒、补位间隔 0～0 秒、每步最多追加修复 2 次。零间隔明确表示不额外休息；用户可以填写非零上下限。

活动池确定可被轮换的项目集合，并发限制实际 CLI 执行数，计划限制一次会话的路线范围，连续步数限制本轮返回同一项目的总推进量。参数不能互相代替。默认一轮拆为第 1～2、3～4、5 步三个计划；完成后轮换，之后返回从第 6 步接续。

## 3. API 与策略契约

保留 `POST /api/project-iteration-batches` 原账号、名称和项目键，增加以下严格整数参数。省略使用默认值，拒绝 bool、字符串、小数及不合法组合；服务端不把非法值静默夹成另一个值。

| 字段 | 默认 | 校验及说明 |
| --- | --- | --- |
| `concurrency` | 2 | 1～2，且不超过账号实际 CLI 上限与有效活动池；UI 随所选项目数调整并明确展示保存值 |
| `active_projects` | 3 | 1～100；有效池大小不超过所选项目数，尚未实际执行不创建目录 |
| `rotation_steps` | 5 | 正整数，不超过本批冻结路线的最大步数；只计验收通过的步骤 |
| `steps_per_plan` | 2 | 正整数，不超过本批冻结路线的最大步数；实际计划被路线尾部和本轮剩余步数截短 |
| `timeout_sec` | 1800 | 60～86400 秒，约束一次 CLI 执行；不因进入第二步重置 |
| `interval_min_sec` | 0 | 0～86400 秒；约束两次 CLI 计划的补位，不在同一计划内额外随机等待 |
| `interval_max_sec` | 0 | 不小于下限，且不超过 86400 秒 |

省略并发参数时按账号上限和有效活动池取不超过 2 的默认值，保持旧客户端只选一个项目也能创建；显式填写超过真实上限的值则拒绝，不能静默夹取。UI 与返回策略显示最终默认值及限制来源。

策略保存在 `policy_json` 并冻结版本。5h／7d 阈值只读取账号已有配置，批次不再保存第二套额度阈值。批次详情增加实际容量、活动实例、下一投放时间和等待原因；原 `active_instance_id` 保留供旧批次解释，不作为新批次的并行所有者。

继续使用既有实例、尝试产物和 SSE 资源路径，实例详情增加计划及其执行列表。新的计划执行通过原 Runs 查询；正常一个计划对应一个 Run，失败恢复产生的新 Run 继续关联同一计划。无需引入新鉴权入口或对外模型调用通道。

## 4. 数据与兼容迁移

### 4.1 新记录

- 增加 `project_execution_plans`：实例归属、批次 generation、固定起止步骤、已接受游标、计划状态、native session ID、冻结执行设置、创建及结束时间。
- 增加 `project_plan_executions`：计划与 Run 的关联、执行序号、会话接续来源、完整执行 source／代次、正在交接的阶段序号及最终释放证据；`run_id` 唯一。
- 增加按实例的在途计划所有权约束；一个步骤被接受后，即使该步骤尝试已结束，计划 Run 未收口时也不能再给同一实例发起另一个写入执行。
- 实例增加冻结的初始随机位置、活动池标记和本轮已接受步数。初始队列与会变动的轮换顺序分开，恢复不能重新洗牌。

### 4.2 尝试与历史

`project_step_attempts` 需要允许一个 Run 关联多步、以及同一步在同 Run 内的有限修复。以事务重建该表解除原 `UNIQUE(run_id)`，保留原 ID、全部历史列、`UNIQUE(instance_id,step_id,attempt_no)` 及单步只接受一次的部分唯一索引，增加 `plan_id` 和逐步暂停证明／会话字节游标。保留原运行最终释放列，不能将“暂停写入”伪装成“整个 Run 已释放”。

无 schema 的旧 `policy_json` 按 schema 1 执行，继续原单步 Run 与历史阶段轮换语义；不重写旧 prompt、内容摘要、Run 状态、目录、尝试 ID 或成果。旧工作区与旧执行证明在完全收口前不得同账号混入新的并行作业。

DDL 通过当前幂等初始化入口执行，保留 SQLite 外键、索引和自增序列；重复启动无额外迁移副作用。迁移测试必须使用包含历史成功、失败、超时和 quota_wait 的真实旧结构样本。

## 5. 调度算法

创建批次只写元数据，在锁外将所选项目洗牌一次，再以事务固定顺序。启动后从队列引入不超过活动池上限的元数据成员，按公平轮换顺序选择可执行项目；只有实际启动某项目时才发布 seed 目录。

每次补位依次核对批次和身份、账号运行窗口、5h／7d 门禁、持久间隔、批次与账号容量及实例在途所有权。进入信号量／环境准备后及实际 exec 前继续复查。等待不占 CLI 租约或长期 DB／账号锁。

先按 Tasks 的方式填满初始并发窗口。后续每次补位使用一个已持久化随机间隔，服务重启不重抽；多个 Run 同时结束时不能重复抽样或同时越过同一个截止。到期投放一个计划后，如仍有空位则为下一次补位另存截止。零间隔可以同一轮填满。

同一项目优先完成本轮剩余连续步数；达到 `rotation_steps` 后放到活动池队尾。完成或阻塞的项目离池，原随机队列补入下一项目；其余项目保留目录和进度。相同账号的多个项目批次与普通 Tasks 共享容量，不能分别获得各自独占的“账号并发 2”。

## 6. 同一次 CLI 的逐步交接

1. 控制端建立固定计划和第一步尝试，预先登记明确 session UUID、执行版本／模型／effort 及原检查点。第一次提示说明本计划范围与当前步骤，要求先完成当前步骤并等待验收；下一步的执行指令仅在通过后投递。
2. CLI 由每作业监督器启动，在同一个 tmux、cwd 和 native session 中工作。driver 使用主会话父链、实际输入和正常 assistant 回复判断候选边界，排除工具中间态、synthetic、sidechain 和重复回复。
3. driver 进入验收等待，不投递后续指令。控制端核对计划／Run／source／generation／阶段序号及主会话边界，暂停该作业完整进程树，获得稳定内核暂停证明后封存候选。只有“回复完成”而没有暂停证明时不能验收。
4. 原 `ProjectVerifier` 在独立无网络、无账号 HOME 的容器验证基线及此前全部已接受能力；通过后以事务保存该步报告、不可变检查点、计划游标和轮换计数。
5. 验收决定带同代阶段序号持久化，再恢复同一 CLI。仍有计划步骤则注入下一步指令；业务失败则在本步追加有界失败证据并有限修复。接受同一步、发送同一条后续指令或处理同一暂停证明均须幂等。不能确认输入是否已被消费时先读取原生输入证据，不盲目重发。
6. 最后一步通过后进入收口状态，等待真实 driver 退出及该执行严格释放，才允许下一计划或批次完成。CLI 正常退出但计划尚有未通过步骤时不得判定计划完成。

超时预算覆盖本次执行内全部路线步骤和同会话修复，不因某步通过而重新计时；管理端暂停和独立验收使用单独有界超时，不消耗 CLI 工作超时。暂停证明丢失、监督器异常或清理不确定时保留现场并阻断该实例的新执行。

## 7. 超时、额度与停止

| 事件 | 接续与状态 |
| --- | --- |
| 第一步已通过、第二步半成品后超时 | 原计划 1／2，原 Run 保持 timeout，第二步工作副本保留；新的恢复 Run 接续原 session 与剩余一步 |
| 第一步代码看似完成但尚无验收 | 不算已完成；继续当前未接受步骤，不能按模型总结推断检查点 |
| 接受检查点后、发送下一步前重启 | 根据持久计划游标、阶段序号和原生输入证据恢复，不重复接受或盲发 |
| 自设额度比例命中或当地时段关闭 | 当前已投放 CLI 计划按冻结范围完成；后续计划及新的失败恢复等待原门禁，间隔保留 |
| 真实额度耗尽 | 原 Run 进入 quota_wait，继续沿用原 Run、计划、session 和工作目录，由原被动恢复协议增加执行代次 |
| 用户暂停批次 | 禁止新计划；已投放计划允许完成并验收，收口后暂停 |
| 用户停止／身份变化／认证错误 | 按原强度收口对应批次执行；旧代次验收决定不得推进进度，其他账号和无关批次不被误停 |
| 修复次数用尽 | 仅阻塞该项目并保留失败现场和最后通过版本，其他可执行项目继续；无可执行项目时才阻塞批次 |

同会话正常计划中的后续步骤属于原投放范围，随机间隔和自设比例作用于下一次 CLI 计划入场，符合原 Tasks 的本轮完成约定；真实耗尽、用户停止和原超时继续独立处理。默认两步计划可能使比例超出阈值，页面须说明该边界。

恢复会话必须来自本计划登记的 session 与同实例目录，禁止从整个账号按 mtime 猜测。会话缺失、截断或证据冲突时保留现场并明确阻塞，不创建新 seed、不悄悄改成另一个会话。每步修复计数跨 Run 保留，上限仍为首轮加两次修复。

## 8. 账号多作业与维护租约

v3 恢复 Tasks 原有 1～2 并发范围；账号实际上限默认 2，尊重合法的既有 `PER_ACCOUNT_CONCURRENCY` 上限配置，禁止页面宣称高于真实容量。非 v3 原路径保持兼容。

`AccountRuntime` 以环境到 source／token 的集合管理作业，执行证明改为带 schema 的逐作业文件与索引。续期线程池按最大实际作业数有界配置；release／恢复／删除／驱逐环境必须检查所有作业，而不是只检查一个 `execution.json`。

网关门禁区分普通共享 CLI、CLI 专用排他（需要切换捕获模式或保持独占的既有操作）与维护排他。普通 CLI 可同时持有两个租约并允许 API；CLI 专用排他阻止其他 CLI、允许独立 API；登录／重授权／维护仍按原规则排空 API。旧 `prepare-cli` 调用保持单 CLI 独占语义，新共享操作只由升级的受信任调度器使用，避免旧维护代码误入并发。

租约快照增加全部 holders／模式／容量，保留旧 `lease` 字段为非空占用提示；所有需要验证特定 owner 的新代码必须读取准确 holder，不能依靠任意首项。旧单租约文件保守读入并进入原对账流程；未知或损坏记录不能当作空闲。owner／generation 的 claim、heartbeat、fence、release 只操作自己对应的租约，排他导入保护不变。

逐作业监督器使用 subreaper 追踪脱离进程组的子进程，PID 和启动时刻由独立握手及内核读取核对。暂停、终止和收口只处理该作业子树；保留 CLI 普通用户身份、容器权限、原 CPU／内存预算、network／sender 角色和账号固化环境。

## 9. 共用设置、网络与统计

每个 CLI 通过会话 settings 覆盖获得自己的 statusLine 采集配置；原用户状态栏继续调用。临时 model／effort／permissions／hooks 同样按本 Run 快照覆盖，driver 不能为不同执行反复改写共享用户设置。账号级设置、信任记录和凭据准备在短锁内原子合并，不持锁等待模型；不在另一执行存活时恢复或覆盖其采集设置。本地与绑定账号的刷新归属必须回归，不能因并行把 RT 分散给第二个刷新所有者。

多个普通 CLI 共享已核验的 passthrough relay，按每执行目录保存本地额度证据；结束一个作业不重启 relay 或清空兄弟配置。capture 模式需要 CLI 专用排他，维护和 sender 仍遵守原边界。原 auth／额度事实仍按账号身份聚合，不增加查询或模型探测。

每个步骤保存本阶段 native 字节起止与去重响应集合，Run 统计则覆盖整个本次计划执行。步骤统计不能对每个关联步骤重复调用整个 Run 总数；失败与修复保留自己的边界。现有排除 sidechain 的口径和缺失未知提示继续如实展示，不宣传完整账号计费总量。

## 10. UI、交付与回滚

创建表单复用 Tasks 布局，明确“并发”“活动池”“连续完成后轮换”“每次 CLI 计划步数”“单次超时”“计划间隔”。账号额度摘要显示继承来源。批次详情展示活动项目、在途数量、下一次投放时间及窗口／额度／间隔／容量等待原因。

实例详情按计划展示“计划第 1～2 步，已通过 1／2，当前第 2 步待继续”；每次执行链接原 Runs，步骤可共享同一 Run 链接但验收结果独立。保留 SSE 选中项、滚动与路线展开状态，明暗主题和窄屏不引入另一套 UI。

新 helper 同步 account 镜像 COPY 与 control 中 driver，冻结源码清单必须覆盖。部署状态／备份检查脚本识别所有执行登记，不能上线时只发现一个作业。任务只做本地隔离构建与验证，不直接提交、发布镜像或部署生产。

回滚前必须暂停并收口全部新计划、导出新增成果并完整备份。新结构出现后不允许旧控制器直接挂载继续写；如需回到旧版，使用成套的升级前 DB／HOME／项目快照并保留新成果旁路副本，具体生产恢复需另按上线 SOP 执行。
