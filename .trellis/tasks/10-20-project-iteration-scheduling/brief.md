# Brief — 项目迭代调度策略配置

## Goal

- 让项目迭代支持同账号真实并行、同一次 CLI 会话内推进多步，并在超时或重启后从未验收步骤继续。

## Scope

- 项目批次的随机队列、活动池、轮换、超时、计划间隔及对应 UI。
- 修复 Tasks 的实际并发，统一 Tasks 与项目迭代的账号 CLI 容量。
- 同会话多步计划、逐步验收、检查点、超时接续与 Runs／步骤用量关联。
- 必要的运行租约、进程清理、采集隔离、历史数据迁移、镜像打包及本地跨层验证。

## Non-Goals

- 真实 GitHub 仓库的逐仓研究继续独立推进，本轮不替换项目库，不把模板项目宣称为真实工程。
- 不增加每日时长／次数／token 预算，不改变账号固化身份、OAuth 协议或原资源预算。
- 本轮不执行提交推送、镜像发布、生产部署或真实模型调用。

## Technical Overview

- 项目在创建批次时随机洗牌一次并持久保存；活动池只登记元数据，实际启动才创建目录。
- 每步完成后暂停该执行的写入，封存候选并独立验收；保存检查点后，继续同一个 CLI 进程、会话和 Run 的下一步。
- 每执行独立登记租约、采集和清理；停止或验收一个项目不影响另一个，登录和维护继续保持排他。

## Context & Decisions

| 参数 | 默认值 |
| --- | --- |
| 同账号并发 | 2，可配置且受真实容量限制 |
| 活动项目池 | 3 |
| 连续完成后轮换 | 5 步 |
| 一次 CLI 计划推进 | 2 步 |
| 单次执行超时 | 30 分钟，覆盖整个本次计划，不按每步重置 |
| 两次计划补位间隔 | 0～0 秒，可配置随机上下限；零表示不额外休息 |

- 正常一个计划对应一个 Run，同一计划内不额外随机休息。默认一轮按 2＋2＋1 推进，达到 5 个验收通过步骤后轮换。
- 第 1 步通过、第 2 步只做了一半后超时：计划保留为 1／2，代码现场保留；下次从第 2 步和原会话接续，原超时 Run 保留，恢复另记 Run 并关联同一计划。
- 每步最多追加两次修复，失败和修复不增加完成步数；用尽后只阻塞该项目并保留成果。缺少可靠会话或检查点证明时明确阻塞，不从 seed 重建。
- 消耗控制继承账号 5h／7d 额度阈值。命中后，当前已投放计划按原范围完成，后续计划和新的失败恢复等待；真实额度耗尽仍按原机制暂停与恢复，因此自设比例可能被在途消耗越过。
- 随机间隔、运行时段、额度与容量共同控制下一计划；重启不重抽间隔。旧批次、英文任务、持久目录及历史成果保留；多个步骤共用 Run 时用量不能重复累计。

## Risks

- 并发涉及共用运行时和历史表结构，须证明定向清理、迁移及重启对账可靠；回滚不能让旧程序直接继续写新结构。
- 无权限进程实验、官方 2.1.293 会话设置及合成 CLI 的同会话两步／真实超时接续已通过；最终冻结源码的页面与任务并行回归均已通过。合成 CLI 不代表真实模型质量或用量。

## Acceptance

- 同账号两个项目和 Tasks 的并发真实生效，混合批次不突破上限；停止一个执行时另一个继续。
- 同一个 Run／会话完成两步，中间有独立检查点；1／2 超时后只接续剩余一步，默认按 2＋2＋1 轮换。
- 额度、时段、间隔、暂停停止及重启竞争不绕过门禁、不重复推进；未开始项目没有目录。
- 历史迁移、步骤用量和 Runs 关联正确，实际 UI／API／DB／执行链路验证及原模式回归通过。
