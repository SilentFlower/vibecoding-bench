# 改造必要性评估

## 评估结论

固定账号环境有长期工程价值，但当前全量任务不宜作为解决账号暂停的首要措施。建议先实施范围更小的身份参数固化、启动校验、运行证据与初始化耗时观测，再依据状态丢失和启动成本的实际数据决定是否引入固定容器。本文件记录评估建议，不代表用户已批准变更现有 PRD 或 Brief。

## 已确认的依据

- 此前服务器只读检查中，账号 10-11 的 9 次运行使用相同有效 Claude `userID` 和 `machineID`；没有证据支持“每次容器重建都换关键设备 ID”的解释。证据摘要见 `/tmp/vibebench-device-audit-20261012.md`，不依赖该临时文件进行实现。
- `orchestrator/main.py:2507` 的系统参数由账号名称稳定派生；当前主要缺口是配置池变化、有效身份缺失时的静默再生成，以及缺少逐次一致性检查，而非全部字段每次随机生成。
- `images/worker/entrypoint.sh:69` 先检查实际 CLI 版本，匹配时直接返回；只有不匹配才安装。是否在服务器每次重复安装尚未逐次验证，不能当成已确认的性能瓶颈。
- 当前完整改造继续使用 MITM，并保留 cc2api 独立身份；容器继续读取宿主系统，代理实际出口稳定性也没有历史证据。因此固定容器本身并没有消除这些关联面。
- 现有任务方案还需要改变登录、续聊、额度恢复、作业退出与清理、sidecar 动态上下文及旧会话索引。这些是实质性成本，可能引入新的生命周期或归属问题。

## 收益与投入

| 目标 | 预期价值 | 当前证据限制 |
| --- | --- | --- |
| 降低账号暂停风险 | 尚未证实 | 平台未披露原因，已观察关键设备 ID 一致，无法估计改善幅度 |
| 保留完整用户状态与缓存 | 明确有价值 | 应先核对哪些状态实际被丢弃，以及这些丢弃是否影响正常使用 |
| 减少初始化等待 | 可能有价值 | 缺少阶段耗时；镜像版本匹配已不重新安装 CLI |
| 简化账号状态归属 | 长期有价值 | 固定进程/网络又增加租约、收口、唤醒与迁移复杂度 |
| 保持各题运行可比较 | 需权衡 | 复用容器可能遗留全局依赖、工具变更和后台进程，需要明确隔离与清理 |

持久数据与固定容器是可分开的选择。Docker 官方说明 volume 内容独立于容器生命周期，删除容器不删除持久内容；现有 bind mount 也直接挂载宿主文件目录。由此可见，保存账号状态不必先完成整个固定容器架构。

来源：

- https://docs.docker.com/engine/storage/volumes/
- https://docs.docker.com/engine/storage/bind-mounts/

## 建议的优先级

1. 固化账号关键身份与可控环境参数；每次执行前校验，缺失或漂移明确阻止并说明原因，保留合法已有身份。
2. 保存脱敏的版本、身份摘要、环境参数、代理配置、执行时间和错误分类；实际出口 IP 能确认则记录，不能确认就标明未知，不将代理服务器地址当作出口 IP。
3. 观测环境准备、CLI 版本准备、首条用户消息和首个上游请求的耗时，优先解决镜像与目标 CLI 版本不匹配造成的重复安装。
4. 若确认必要 HOME 状态正在丢失，再做按账号的持久化增量，同时适配 run 主会话归属、统计及同账号访问协调；继续保留独立工作目录。
5. 当已有数据证明初始化成本显著或需要长期交互运行，再评估固定 worker/sidecar 全量方案。
