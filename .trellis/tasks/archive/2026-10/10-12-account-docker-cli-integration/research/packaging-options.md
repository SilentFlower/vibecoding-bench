# v3 镜像与发送边界决定

## 最新用户决定

2026-10-12 用户明确选择管理镜像与账号镜像分开，每账号一个固定容器；随后选择「账号容器实际发送 HTTPS（推荐）」。这些决定取代此前三组件镜像草案和助手在用户委托权衡后提出的综合镜像建议。

管理镜像启动 gateway、orchestrator 两个服务容器；账号镜像为每账号创建一个容器，包含 CLI/tmux/开发工具、网络/抓包与 Rust 上游发送器。N 个账号共 N+2 个容器，账号间共用镜像层，各有独立持久目录、网络、进程和传输实例。镜像数量为 2，不另外交付 worker、sidecar 或网关发送器镜像。

## 取舍与实现约束

- 两镜像由同一构建入口和 release 清单交付；两个 digest、源码 SHA、CLI、布局及传输桥协议版本一起校验，不等于两套人工安装流程。
- 管理镜像不用携带账号开发/网络工具；账号镜像不用携带 Vue、管理数据库或调度器。共享代码的 Rust 网关与发送器通过构建产物复用，避免复制两套协议算法。
- gateway/orchestrator 仍分别作为容器主进程启动，只有 orchestrator 挂 Docker socket。
- 账号 init 管理网络、DNS、Recorder 与发送器健康；CLI 作业非 root、显式丢弃网络能力并禁止提权。CA 私钥、内部服务资料及控制目录分权，不挂 RT 管理目录。账号合并意味着权限隔离从容器边界改为进程用户/能力边界，须真实验证。
- Node/CLI、Python 和 Rust 发送器使用兼容 runtime；多阶段复制路径和系统库需通过实际镜像验证，不能盲目复制不同基础镜像的所有目录。
- 全部容器仅属于 v3 的独立数据、网络、端口和 labels；不操作旧版资源。

## 为什么要实际发送而不只加代理

当前 `cc2api/src/service/gateway.rs:2520` 的 `forward_request` 在管理端构造请求，`:2561` 的 `req_builder.send()` 真正发起上游连接；`src/tlsfp/tlsfp.rs:362` 仅按 proxy_url 缓存 reqwest client。把账号容器当 SOCKS/CONNECT 中转可以统一出口，但 HTTP/TLS 客户端仍由管理端创建。

最新设计让该 HTTP/TLS 发送层真正运行在账号容器。管理端发送已完成改写的请求，发送器只建立上游连接并流式返回，选号、重试、额度/错误分类和响应处理继续由管理端负责。桥接保留字节、背压、取消与提交状态；不增加自动重放或容器故障直连回退。

这能让 API 的连接池与进程归属于固定账号环境，也让 CLI 和 API 沿用同一账号代理配置；不会让 Rust 请求变为真实 CLI 请求。两条客户端链路的 TLS/完整指纹不能声称相同，字段继承仍需语义证据，固定容器不是防封保证。遥测专项继续暂缓，本轮不声称已统一全部后台 HTTP。
