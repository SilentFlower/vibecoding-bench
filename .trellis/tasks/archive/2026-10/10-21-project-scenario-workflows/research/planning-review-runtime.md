# Research: 三件套的执行状态与恢复窄范围复核

- Query: 复核版本分流、候选封存／释放／评审／恢复、独立场景、尝试与时间预算是否自洽。
- Scope: internal；只读本轮 `prd.md`、`design.md`、`implement.md`，不重新搜索源码，不修改三件套或产品。
- Date: 2026-10-21

## Findings

以下行号对应本次实际读取的规划文件；共 4 条需补足的实质问题。

### RT-01 · P1：评审 session／cwd 隔离尚未覆盖共享 HOME 的会话产物

- 位置：`design.md:102`，关联 `design.md:44`、`design.md:123`、`implement.md:33`。
- 问题：设计明确把隐藏 rubric 放入独立评审输入，但只规定独立 session／cwd。在既有同账号共用 UID／持久 HOME 的底座上，评审原生日志或缓存可能仍位于候选后续能读取的位置；恢复候选后有机会接触隐藏评审包。独立 session 本身不足以满足 PRD AC2 的隐藏材料隔离。
- 建议：在设计中明确评审输入、原生会话／transcript、暂存与反馈的可见性边界，保证候选无法读取隐藏评审产物；保持账号／模型身份复用，但不能仅靠不同目录名或“不主动提供路径”实现隔离。增加评审完成及候选恢复后的实际可读性反例。

### RT-02 · P1：Run 唯一的执行记录未定义 quota 多代次证据的保留方式

- 位置：`design.md:71`，关联 `design.md:74`、`design.md:122`、`design.md:136`、`design.md:142`。
- 问题：执行表被定义为 Run 唯一，却同时承担 source／quota 代次、原生边界和严格释放证明。真实 quota 恢复沿用同 Run、产生新 source；若这些字段直接覆盖，旧代次的释放与用量边界将丢失，也难以拒绝旧回调。工作片段表只明确时间／预留，并未承担原生边界和释放证明的归档职责。
- 建议：明确 Run 绑定与实际 source 代次的一对多关系，例如另设不可变执行代次记录，或将执行唯一性定义为 Run＋quota 代次；原 Run 的当前指针可以变化，但各代证明不可覆盖。测试需覆盖同一候选／评审 Run 多次 quota_wait、迟到旧释放回调与 token 去重。

### RT-03 · P2：评审预算字段的作用域和跨 quota 计量需要冻结

- 位置：`design.md:132`、`design.md:134`，关联 `design.md:138`、`implement.md:24`。
- 问题：文本同时要求每次评审 180 秒、同候选 360 秒、全任务评审 720 秒，但策略只列出一个 `review_budget_sec`，未说明它代表哪个层级、另外两层如何从快照推导。也未明确“每个评审执行”是逻辑一次评审还是单个 quota 恢复片段；若后者每次重新领 180 秒，就不满足单次评审上限。
- 建议：明确 `review_timeout_sec` 约束同一次逻辑评审的全部 source 片段；`review_budget_sec` 明确为任务累计评审预算（默认 720）；同候选上限明确冻结为默认 360 或由明确规则派生。每次领取预算取单次、候选、任务三层剩余的最小值，并定义合法范围／跨字段关系；quota 恢复不重置任何层级。
- 对候选同样写清每次领取 `min(600, 任务剩余)`；1,800 秒包含所有正常轮次、三个尝试及其执行片段，排队和评测不混扣。

### RT-04 · P2：执行计划的“最多两次重试”与设计的“两次总评审”不一致

- 位置：`implement.md:35`，对照 `design.md:115`、`design.md:132`、`design.md:134`。
- 问题：设计规定首次评审加最多一次 error 重评，总计 2 次；执行计划却写“同候选评审最多两次执行错误重试”，可以被实现为首次加两次重试，总计 3 次。若照此执行，会与 360 秒上限和固定评审次数冲突。
- 建议：执行项改为“同候选首次评审加最多一次 error 重评，总计最多两次；有效 uncertain 直接 blocked，不重评”。单独说明执行基础设施最多额外恢复两次的计数归属／持久化范围，不能让它变成第三次业务评审或在新 Run 下重新清零。

### 其余复核范围的结论

- 版本分流基本一致：内容 schema 2＋policy 3，新候选仍为 `project_iteration`，新评审 `project_review` 映射 normal；旧内容 schema 1／旧策略单步与 policy 2 保留，历史 reader 与当前 catalog 解耦。
- 先封存候选及作业、严格释放候选、共享 Scheduler 评审、严格释放评审、再恢复原业务 session 的顺序一致；CAS、父 generation、ACK 丢失和迟到结果也已明确，RT-02 需补足代次存储支撑。
- 任务、轮次、业务尝试、实际执行、验收作业和代码检查点已经区分；正常澄清不加任务／尝试，问答不接受代码，独立场景隔离，同场景保留 session，局部依赖阻塞的原则一致。
- `uncertain` 作为有效未判定直接 blocked，`error` 只因格式／执行问题有限重试，二者语义自洽；问题仅为 RT-04 的执行措辞和 RT-03 的具体预算边界。
- 确认耗时与不确定预留分离、跨 boot 禁止直接相减、重启先收口、仅续验收和不清零重发的原则一致。
