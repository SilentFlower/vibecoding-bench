## 设计决定

### 1. 精简备份作为默认行为

- 保留 `backup` 入口与一致性停机要求；增加显式完整模式，默认精简。现有完整备份仍按原归属识别并参与轮换，不自动解释为精简备份；离线复验入口只接受含恢复清单的新格式。
- 精简模式只排除精确 npm `_cacache` 下载目录、已证明可重建的 CLI 版本，以及当前正式镜像已完整覆盖的固定内容版本目录；不按整个 `cli/` 或 `.cache/` 目录排除。
- 未知 HOME 缓存、`.claude`/`.claude.json`、配置、私钥、工作目录、历史项目内容、任务制品和全部恢复记录保留；Unix socket 保持原排除语义，普通符号链接按原样保存而不跟随。
- CLI 与浏览器排除前生成精确版本、来源和文件散列清单；当前项目内容固定到已核验的官方镜像 registry/config digest。任何来源无法核验的排除项改为包含，不能因追求备份体积丢失恢复资料。
- 增加私有备份清单，记录数据根、发布批次、模式、保留文件字节/权限/归属/链接、排除路径、恢复依赖以及配置文件；清单不向普通业务界面或日志暴露凭据内容。
- 在隔离目录验证 SQLite 完整性、保留数据、链接与权限、最新凭据/身份和内容引用，再发布成功标记并轮换旧恢复点。失败保留现有完整备份，不回写源数据。
- 恢复分为“恢复关键状态”与“按清单准备程序依赖”；只在离线目录演练，不把旧 token 或旧库覆盖回生产。精简备份不承诺在宿主整盘丢失后零下载恢复全部工具。
- 新 CLI 用 root 私有 `.v3-cli-install.json` 记录协议2、精确版本、程序/依赖锁/包定义摘要；旧版本必须通过无网络 npm 重建且程序摘要相同才能排除。浏览器缺少完整恢复来源时保留，因此最初 1.88GiB 是候选下限估计，实际备份可能更大。
- 已完成且通过隔离恢复的同部署、同数据根、同平台备份可提供旧 CLI 来源证明；完成标记须绑定恢复清单摘要，当前精确版本、程序摘要和依赖锁均匹配才能复用。这样清理 npm 缓存后，后续备份仍能保持精简；损坏、未完成或跨部署证明不采信。
- SQLite 连接显式关闭后再生成清单，不能把随 GC 消失的 WAL/SHM 计入恢复文件；备份文件、目录与完成标记同步后才轮换。

### 2. 明确边界的缓存清理

- 维护入口默认输出清单，显式应用时核对部署标记、源目录、清单散列、同部署全部容器状态、占用和原文件元数据；不执行全局 prune。
- npm 只清理 `_cacache` 等已知下载产物，不清理 `.npmrc`、HOME 身份、node_modules 或未知目录。CLI 安装结束清理本次私有下载缓存，安装锁仍生效。
- CLI 在取得安装锁后收口同版本、精确命名的遗留暂存目录；缓存回收失败不阻断已经完成版本验证的就绪程序，安装自身失败仍保留原退出码。
- 浏览器缓存以具体软件包与版本为单位核对实际使用路径、包元数据和保留项目。当前三组 Chromium 版本不因版本号较旧而删除；没有充分引用证明时保留可执行浏览器。先验证保留版本无下载启动，再删除已证明多余的包。
- 停机前额外探针实测：未登记历史目录的 Chromium1248 在切换前、后正式账号镜像中均缺 `libglib-2.0.so.0`，当前无正式账号或活动运行。该历史缓存按 R2 的来源不明分支完整保留，核对原字节/权限；不把既有缺库伪报为浏览器启动成功，不为清理缓存新增浏览器功能或改动旧环境。当前正式项目的离线验收使用独立冻结环境，真实原生观察已在正式两镜像通过。
- 每次应用生成脱敏空间回执；路径父级链接、跨文件系统、活动执行或清单变化时拒绝本项操作，不误报已清理。
- 维护清单绑定数据根、发布、目录身份与逻辑摘要；输出回执在删除前独占创建。备份、维护及 `up` 共用 `.v3-storage-maintenance.lock`，读取清单使用有界、非阻塞、拒绝链接/FIFO 的文件描述符。

### 3. CLI 制品物理复用

- 保留每账号 `/cli/<version>` 逻辑路径及独立 HOME，不增加跨账号可写挂载。
- 仅考虑 root 所有、无组/其他用户写权限、父目录受保护且 `.ready` 已验证的静态程序文件；按内容散列、大小、权限、uid/gid 分组。相同文件在同一文件系统内用原子硬链接替换减少物理副本，符号链接和账号业务文件不参与。
- 先把 CLI 安装调整为锁内写入全新暂存版本目录，实际 `--version` 校验后发布 `.ready` 并替换目录；不能原地覆盖已共享 inode。失败不破坏已有就绪版本，旧客户端仍使用同一逻辑路径。
- 复用操作只在能够确认全部相关角色空闲、路径只读边界有效时执行；旧隔离布局、异常归属或无法证明写入路径的版本保留原副本。不得为了收益重建旧账号或放宽隔离。
- 版本清理检查默认值、账号覆盖、登录/执行/评审记录及历史 run；引用无法判定时保留。CLI 准备与评审既有租约和生命周期锁保持原顺序，磁盘优化不改变并发语义。
- 账号镜像声明 `vibebench.cli-install-version=2`，已核验镜像能力在 `ensure` 缓存；成功安装后只对本版本的大程序文件发布到 root 私有 `bench/cli-artifacts`。没有额外 Docker/网络查询，不增加账号可写挂载；缓存优化失败沿用已验证的私有程序。

### 4. 冻结项目内容去重

- 增加受限存储辅助模块，复用同一套按字节与元数据分组、临时链接及原子替换机制；作用域仅为私有冻结内容，绝不把可写工作区链接到冻结文件或对象库。
- 构建快照恢复固定上游原件并计算源码内容散列后，对快照内项目库进行物理去重，再 COPY 到镜像。逻辑字节、权限和构建来源不变；验证 Docker 层保留链接且文件清单完整。
- `ProjectLibrary.install()` 在新版本私有暂存目录内去重依赖，再做原内容校验并原子发布。现有冻结版本只通过停机维护入口去重，不重算、改写或删除历史摘要。
- 同内容但权限或归属不同的文件不共用 inode；源码对象与普通工作副本仍采用现有独立复制语义，防止候选修改污染基线。

## 生产操作与兼容

1. 保存前置只读状态、保护文件散列、容器 StartedAt、正式/回退镜像引用、数据库历史统计和空间基线。
2. 检查无活动任务/评审/登录/API；先收口管理端，再停止本部署验证辅助容器，保留其网络地址与恢复方式，其他应用不操作。
3. 新脚本沿用服务器管理密码兼容覆盖；核对最小宿主改动，不覆盖无关 Compose/TZ、配置与本地保留脏改动，不伪造宿主代码提交来源。
4. 生成精简备份，在隔离目录验证关键状态与恢复依赖。验证通过后，才轮换同部署旧完整备份。
5. 应用已核验的缓存与静态制品清单；每项重查元数据及保护边界。删除动作仅对明确可重建缓存/无引用版本，文件去重保留全部逻辑路径。
6. 通过同批正式镜像部署后核验健康、100 项目目录、原身份/配置/历史记录及无下载工具启动。旧账号角色不自动唤醒或重建。
7. 报告实际空闲增量、精简备份体积、镜像层独立体积和跳过项。旧完整备份仅在新恢复点证明有效后淘汰；当前和上一版镜像保留。

## 风险与收口

- 精简恢复需要镜像、CLI 与浏览器版本制品；通过固定 digest/版本/散列、恢复清单及隔离验证控制，未知资料保留。
- 硬链接如果遇到原地写入会污染其他副本；先改成暂存安装与原子发布，再仅对账号只读的静态文件去重，并验证重装/失败与候选修改不会影响兄弟文件。
- 浏览器缓存可能是首次任务唯一可用程序；默认保留实际使用版本，未证明可删的缓存不删，空间收益不强行凑数。
- 当前工作区有 262 个无关保留文件，README 与 Compose 含既有 TZ 改动；按任务创建基线逐项保护，提交只包含本轮获准变更。
