# v3 Docker 账号环境隔离对齐

## 目标

在保留账号身份和既有任务能力的前提下，对齐 vm2api 可验证的 Docker 隔离措施，减少业务进程权限、跨账号访问和意外出站。

## 背景与来源

- 用户先要求比较 vm2api 的 Docker 隔离配置，随后认可网络与业务分离、非 root、只读文件系统、出站约束和身份连续性方案，并明确要求“可以我们去对齐吧”。
- 用户补充询问官方 Claude Code 开发容器方案；其定位是隔离开发环境与持久配置的参考，不要求改成编辑器开发容器产品。
- 当前账号容器同时运行网络服务、Rust 发送器及 CLI。容器保留 NET_ADMIN/TUN，CLI 已降为 UID1000 并删除能力；业务容器整体非 root、只读系统及独立网络边界尚未形成。证据：orchestrator/account_runtime.py:374、:1465；images/account/init.py:45。
- 当前持久 HOME、设备身份、凭据所有权和 API/CLI 独立调度已有正式契约，应在隔离改造后保持。

## 需求

- R1：分离网络配置权限与业务执行权限。CLI 与 API 发送业务在非 root、不可提权、无额外 Linux capabilities 的环境中运行。
- R2：收紧系统文件、版本缓存和控制配置的访问；业务仅能修改本账号必要的 HOME、工作区与临时文件，不能访问其他账号的凭据或运行资料。
- R2.1：CLI 不能读取发送器内部鉴权秘密、代理密码、抓包 CA 私钥或管理控制文件；隔离升级不得因同 UID 或扩大目录权限降低已有秘密边界。
- R3：DNS、CLI、API 和服务端 OAuth 网络请求沿用账号出口；网络服务异常、代理故障和重启恢复均不得自动直连。保留普通原生 TLS 与显式完整抓包能力。
- R4：升级、停止唤醒、重建、重新授权及解绑保留原环境 ID、设备身份、持久 HOME、历史会话和凭据所有权，不因隔离升级生成新设备或恢复旧凭据。
- R5：保持普通任务、养号、继续会话、登录草稿、重授权、绑定、解绑、额度采集及 API JSON/SSE 的现有业务语义。CLI 的单次取消不影响健康 API 长流。
- R6：资源上限按实际编译/工具任务验证；账号预算计入网络服务，保持当前已保存 RAM/swap 上限和活跃账号门禁，不通过无限额或静默加预算解决故障。
- R7：管理、发布清单、状态、停机、备份和回滚覆盖新的完整账号环境；仅维护本部署精确归属资源。
- R8：通过实际 Docker 权限与故障测试验收，并如实区分本地隔离夹具、正式非模型网络验证和真实模型调用的证据。

## 验收标准

- A1（R1、R2）：实际业务容器与 CLI/API 进程均为非 root，无额外 capabilities、不可提权；系统目录只读，必要工作区可安装本地依赖和执行构建，跨账号数据访问失败。
- A1.1（R2.1）：从实际 CLI 进程身份尝试读取发送器配置、网络服务环境、私有 CA、管理控制树，均失败；必要状态和暂停信号按原只读契约提供。
- A2（R3）：实际观察 CLI、API、DNS、服务端 OAuth 的出口；直连目标与 IPv6 绕行受阻；代理拒绝、网络进程退出及重启阶段均失败关闭。
- A3（R4、R5）：合成账号完成登录/草稿恢复、关联重授权、绑定/解绑/再次创建、刷新失败收尾；身份与最新合法凭据保持，已修复的 RT 丢失不复现。
- A4（R5）：真实官方 CLI 的本地工具操作、版本准备和安装依赖可运行；API JSON/SSE、CLI 任务和继续会话并行/取消语义通过隔离夹具验证。
- A5（R6）：资源预检覆盖全部账号角色，停机与异常没有漏计容器；峰值及临时目录验证失败时拒绝交付，不静默调整账号预算。
- A6（R7）：旧单容器环境可在无活动执行时受控升级、失败可回退；停机/备份/恢复和镜像批次校验完整，原资料与其他部署保持。
- A7（R8）：检查报告列出 Docker 实测结果和未执行的真实上游验证，不以容器化或测试通过承诺账号免封。

## 范围之外

- KVM/QEMU、复制 vm2api 闭源组件、伪造 DMI 或遥测以隐藏容器、改造为 VS Code 开发容器产品。
- cc2api 的协议改写、Rust HTTP/TLS 发送方式、模型请求内容及账号策略调整。
- 改变地区服务资格、解封保证、用已封账号探测真实模型、自动新增真实账号。
- 合并既有未完成遥测任务、主动扩大服务器资源、修改宿主其他部署的防火墙或启动旧 vm2api。
