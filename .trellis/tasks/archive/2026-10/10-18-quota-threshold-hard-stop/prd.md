# 账号额度阈值触发运行中任务强制中断

## 目标

让已配置的账号 5h／7d 额度阈值约束正在运行的普通批次及养号任务，首次观察到任一有效窗口达到阈值时强制中断任务，减少继续执行产生的消费。

## 背景与证据

- 用户在核对账号 10-17 的封禁时间线后提出：不能只阻止下一任务启动，还在运行的任务达到配置阈值时也应直接中断。
- 线上 3ca729f528a4 于 2026-10-18 19:24（北京时间）启动，首次有效 5h 读数 55%，随后增长到 68%，19:45 成功结束。60% 启动门禁未限制运行中的普通任务。
- QuotaGuard.policy_snapshot／_policy_decision（orchestrator/main.py:2848、:2928）为普通任务与养号读取同一账号阈值。当前契约要求命中阻止下一执行、已启动 CLI 完整收尾，见 .trellis/spec/vibecoding-bench/backend/database-guidelines.md:617。
- v3 普通 run 使用 passthrough，CLI 状态栏被动收集正式响应的窗口读数；orchestrator/account_runtime.py:1202、:1228 没有启用养号 Recorder 收尾协议。观察并非实时上游计费值，单次响应可能直接从阈值下方跳到上方。
- 原任务额度等待／恢复、停止优先级和按执行代次清理已存在；调研见 research/current-quota-stop.md。

## 需求

- R1：沿用账号当前可配置的 5h／7d 已用百分比；两个窗口独立，任一有效读数大于或等于已启用阈值触发强制中断。null 仍代表关闭，不硬编码 60%／80%。
- R2：普通任务（含批次）和养号任务在运行途中也受阈值约束。命中后不再等待完整业务完成，不追加收尾或业务补充提示以继续模型工作。
- R3：中断保留已有项目文件、会话和执行证据，记录命中窗口、实际观测值、配置阈值与时间；不得误记为 success 或 timeout。
- R4：按账号及原执行代次停止任务进程；不得让旧信号终止替代作业、其它账号或同环境独立 API 进程。用户停止、删除及明确认证失败保持优先。
- R5：继续使用被动额度观察；不新增 usage 轮询、模型探测或登录。缺失／无效／过期／异身份记录不得伪造为 0% 或新命中。
- R6：向用户准确说明：保证首次可信观测命中后的强制中断，不承诺上游实际计费百分比绝不越界，也不承诺降低封禁概率。
- R7：用户选择第 2 种处理方式：触发后永久结束本轮，沿用 stopped 终态，原 run／批次 item 不进入 quota_wait 自动续跑。批次保留未执行项，在命中窗口恢复且原投放间隔满足后继续下一题；定时养号沿既有间隔安排新一轮，不恢复被中断会话。
- R8：页面阈值说明与运行详情准确表达“达到阈值强制结束当前轮次，恢复后执行下一题”，并显示实际命中原因，清除本轮相关旧文案中的完整收尾／自动查询表述。

## 验收标准

- A1 / R1、R2：普通任务和养号分别验证低于阈值继续、等于阈值中断、一次响应跨阈值中断；覆盖 5h、7d 任一命中和关闭阈值。
- A2 / R2、R3：真实 driver／tmux 在忙碌模型回合命中时停止，之后不注入收尾／补充，不继续提交该任务的新模型请求；项目和会话文件保留，管理 API 显示准确中断状态与原因。
- A3 / R4：与用户停止、认证失败、进程自然结束、执行代次替换、其它账号并发竞争时，终态与清理归属正确；清理失败不得放行下一作业。
- A4 / R5：被动采集、未知值、窗口重置、配置调整、服务重启及现有持久恢复许可均有回归；离线测试不得触发真实 usage／模型请求。
- A5 / R3、R7：阈值中断后原 run／item 为 stopped，窗口恢复或服务重启不续跑原轮次；仅下一 pending item 在额度与原间隔均允许后投放一次，不重新执行被中断题目、不补发原补充消息。
- A6 / R8：真实浏览器／API／SQLite 核对配置提示、中断状态和命中原因；页面明确被动观察的限制，不再承诺当前 CLI 完整收尾或自动查询 usage。

## 范围边界

- 本轮调整 v3 普通 run／批次及养号的阈值行为。抓包、手动续聊、独立网关 API 的百分比限制、旧 runner 兼容和新额度估算算法不在本轮范围；共同耗尽与认证保护保持。
- 不修改账号身份、代理、凭据、历史任务终态、题库、补充概率或时间策略；不新增服务器备份，不对受限账号发起真实模型验证。
- 生产交付沿用已有 GitHub Actions 和同批次双镜像部署约束；不为本轮规划直接中断或重启线上服务。
