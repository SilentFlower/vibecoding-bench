# 技术设计

## 1. 边界与现状

本轮跨 Python orchestrator、Rust cc2api、Vue 账号卡片和 v3 验证脚本。现有设备身份导入、凭据镜像、owner → profile → environment 锁序、内部服务证明以及生产 TLS 校验保持为基础约束。

当前 canonical_process 是 JSON 列；无需为来源/采样元数据引入新数据库列。不能用容器配额代替 RSS，也不能用同步时 `node -e` 的内存代表官方 CLI。

## 2. 真实指标采集

- 在账号容器 root 管理的运行监督路径增加有界、低频的只读采样；仅识别 root 管理版本缓存中真正的官方 CLI 进程，核对 UID、实际可执行文件、进程启动时间，防止把 npm、测试浏览器或发送器识别成 CLI。不读取命令正文或环境变量全集。
- 从实际 cgroup 读取内存限制，并与 Docker 固化预算交叉核对；兼容 v1/v2、无限制、退出竞态。RSS 从已核对 CLI 的 procfs 读取。
- 实际 Docker 默认无 SYS_PTRACE，root 跨 UID 读取 exe 被拒绝；仅在 readlink 时用账号 fsuid/fsgid，立即恢复后由 root 核对缓存所有权/权限和 PID 启动时间，不新增容器能力。
- 将环境 ID、CLI 版本、采样时间、采样数与最近 RSS/有界观测范围保存到 root 私有 runtime 文件；不保存命令正文、令牌、环境变量全集或对话。样本跨重启可读，但必须显示真实采样时间；版本/归属不匹配不能拿来补当前版本。
- 没有 CLI 样本时仍能同步已测量的容器上限；RSS 保持明确未知。无法从 procfs 直接确认的 Bun/Node 堆指标不伪造。
- 不新增上游请求，不启用 MITM，不为采样额外启动官方 CLI。

## 3. 同步与使用契约

- 扩展受信任 CLI 导入载荷，增加进程来源及可选观察字段；旧调用方仍可兼容。
- 已绑定账号增加受同一服务证明、身份比对和运行门禁保护的进程补齐路径，通过独立“更新进程指标”按钮触发，不绕过设备归属检查。进程更新不改变 OAuth、设备和账号绑定。
- v3 来源必须显式标记；校验内存数值、RSS、时间、版本和来源。坏样本拒绝，文件缺失则表示未采样，不将文件缺失当作同步成功的完整指标。
- `device_profile`/`normalize_process` 对普通旧画像保留兼容；对 v3 观察来源不填造默认范围。进程改写和自动遥测构造只写已确认字段，未知字段不能被内部占位值当作实测发出；不改变账号遥测开关。
- `api.ts` 和 `Accounts.vue` 同步字段，显示“容器内存上限”和“最近 CLI RSS/采样时间”或“未采集”，避免将静态上限、实时 RSS 和历史范围混为一谈。

### 3.1 首次创建配置

从当前 `sync_account_to_cc2api()` 的创建分支提取受控创建逻辑；新的显式创建入口以及保留的旧兼容创建路径，在真正创建的载荷中传入：

| 选项 | API 字段和值 |
| --- | --- |
| Billing 重写 | `billing_mode: "rewrite"` |
| 上游 session 池启用 | `upstream_session_pool_enabled: true` |
| 池容量 4 | `upstream_session_pool_size: 4` |
| 仅属主刷新 | `upstream_session_refresh_policy: "owner_only"` |
| 并发 4 | `concurrency: 4` |
| RPM 上限 50 | `rpm_limit: 50` |

这些字段已有 Rust 请求定义与持久化支持，无需新增字段或改 cc2api 全局默认值。TTL 时长不另行指定，沿用当前 60 分钟。仅在真正创建时应用；查到匹配账号、已绑定重复同步和重授权只按原契约更新相应数据，不将六项配置重新写回。

## 4. 容器转发验证机制

### 4.0 已确认的按钮拆分与后端边界

当前 `webui/app.js:235` 对所有正式账号显示“同步”；`:311` 调用单一 `/cc2api/sync`。服务端会自动匹配/创建并解析权威凭据后镜像本地，因此按钮名称未表达实际副作用。手动选择已有账号目前位于养号表单。

用户已确认采用四个入口：

| 按钮 | 适用状态 | 明确行为 |
| --- | --- | --- |
| 创建 cc2api 账号 | 未关联 | 创建并关联新账号，应用六项新建配置；发现已有匹配时提示改用关联，不静默切换。 |
| 关联已有账号 | 未关联 | 用户选择现有目标，校验设备/身份后关联；保留目标配置，不创建新账号，不连带修改养号设置。 |
| 更新进程指标 | 已关联 | 本地容器 → 原关联账号，仅更新已确认的内存上限、CLI RSS、来源与采样时间；不刷新凭据、改绑定或覆盖六项策略。 |
| 重新授权 | 正式账号 | 沿用官方 CLI 授权；已关联时自动提交到原关联账号并镜像两端，未关联时仅保存本地并明确提示。 |

不新增笼统的“同步凭据”按钮，避免混淆 cc2api → 本地的权威镜像与重新授权 → cc2api 的新凭据提交。后端按动作提供明确入口：

| 计划新增入口 | 行为约束 |
| --- | --- |
| `POST /api/accounts/{aid}/cc2api/create` | 仅未关联时创建并关联；匹配到已有账号返回冲突及关联提示，不自动绑定；重复请求不创建第二个账号。 |
| `POST /api/accounts/{aid}/cc2api/bind`，正文 `cc2api_account_id` | 显式目标的关联，复用现有身份/设备校验、唯一绑定与 owner 转移门禁；不创建、不写六项配置或养号设置。 |
| `POST /api/accounts/{aid}/cc2api/process` | 仅原绑定的进程观察更新；不解析/刷新 OAuth，不修改设备、代理、六项配置或绑定。 |
| 既有登录与重授权入口 | 保持原事务、暂存、回执和恢复规则，仅把按钮文案统一为“重新授权”。 |

原 `/cc2api/sync` 保持兼容，复用公共校验/创建/关联能力但不加入新的指标更新副作用；新 UI 不再调用它。养号表单移除关联账号选择，独立关联窗口只显示可关联目标并明确身份校验；旧 warmup API 的绑定字段保留兼容，不破坏旧客户端。创建和关联成功后按原所有权切换契约镜像 cc2api 权威凭据，不能误称为本地向已有账号上传凭据。按钮可见性只辅助交互，后端仍核对绑定和维护状态。

### 4.1 完整业务链路

使用独立空数据库、随机部署 ID、真实 orchestrator、正式 API 路由和真实 Docker 账号环境。成功 JSON/SSE 上游由隔离夹具提供，代理独立记录客户端来源、CONNECT/SOCKS 目标和连接次数，上游记录关联标记与最终字节哈希。对应 SQLite 账号/绑定和发送器被动证据必须一致。

转发夹具通过正式首次同步创建账号并保留上述六项配置；尤其保留 Billing 重写和启用的 session 池，覆盖该配置下的业务链路，不为通过测试而恢复旧默认值。

生产 TLS 客户端只接受公有根，不能通过修改 CA 文件就认为测试根生效。完整本地 HTTPS 使用仅测试构建的客户端注入/受限启动夹具，保持证书和主机名校验，调用相同生产路由与发送函数；测试构建差异写入报告。生产构建不得包含自定义上游或关闭 TLS 校验的后门。必要时先补测试启动器再跑真实容器链路。

### 4.2 生产公网传输

只使用当前已部署版本的账号发送器与账号代理，发固定 Anthropic origin 下的非模型、无用户对话/真实凭据的 HTTPS 检查；不触发 CLI、usage 查询或 token 刷新。记录 HTTP 返回及发送器的 request_id/归属证据；上游拒绝只表示已完成传输，不能记为业务成功。需要临时唤醒账号时先记录空闲/停止基线，结束后按正式维护路径恢复；不改 allowed_origin、生产代理或账号信息。

### 4.3 真实推理边界

当前唯一正式账号有 account_on_hold，且还没有成功 API 发送证据。真实 Anthropic JSON/SSE 推理需要可用账号，不能从测试替身和公网网络成功推导。在没有可用账号时，报告该项缺前置条件；其余修复和验证继续完成。

## 5. 兼容、恢复与风险

- 普通旧账号仍沿用原画像；v3 已绑定账号通过受控同步补齐，不批量迁移或覆盖历史设备。
- 只清理本次随机部署标签及路径；测试前后核对旧哨兵、工作区 dirty 基线和生产账号资料摘要。
- 生产检查可能短暂唤醒一个空闲账号容器；若资源预算不足，遵守 preflight 并报告阻塞，不停止其他部署。
- 验证若发现转发代码缺陷，先定位部署/构建与场景证据；同一链路的具体修复同步设计后继续，新增产品或生产风险再单独决策。
