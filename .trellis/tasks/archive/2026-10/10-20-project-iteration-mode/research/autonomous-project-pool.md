# 无人介入的多项目迭代：候选方案

## 已确认的产品意图

- 用户要求独立模式，保留原题库模式。
- 启动后的日常运行全自动，不等待人工给需求、选建议或确认验收。
- 项目不止一个，需要可观数量的项目池，每个项目具有持续迭代路线。
- 已确认同一项目在不同账号或批次使用相同的初始代码与数据，不同项目各有独立初始功能和路线。

## 仓库证据

- 实际通过 `parse_topics` 和 `validate_topics` 校验 `topics.md`：600 个主题，21 个分类，每题两条业务补充。README 中的 300 题描述已过时，本规划以实际题库和校验结果为准。
- `orchestrator/topic_library.py` 的 `Topic` 定义包含题号、标题、初始需求、分类和最多两条补充，没有长期路线实体。
- `orchestrator/main.py` 的 `WarmupScheduler._select_topic` 从有效主题中随机选择，并尽量排除最近 20 个；这不是按持久项目路线选下一步。
- `WarmupScheduler._create_task_and_run` 创建新的 task/run 并冻结本次有限补充。
- `orchestrator/account_runtime.py` 的 `_project_view` 按环境 ID 与 run ID 派生项目目录，需为新模式单独设计稳定项目身份，不能假设两个新 run 会自动复用源码。
- 原有 worker 的阶段证据主要证明对应输入已被消费并存在正常回复，不能直接替代每个项目的业务验收。

## 内容组织

- 用户已确认首版交付 100 个不同业务项目，每项目至少 20 个有依赖关系的迭代步骤，总计至少 2,000 个可验收改进单元；600 主题作为可扩充内容来源，不直接复制初始需求形成 600 次从零建项目。
- 每个项目包含能运行的初始版本、合成样例、依赖准备说明和一条具有业务连续性的路线；不能只提供一个题目和大量通用的“优化一下”。
- 同一项目的各账号或批次实例使用同一冻结版本；不同项目具有各自的初始功能与路线，此项已经用户确认。
- 路线步骤涵盖业务能力、数据持久化、导入导出、错误恢复、边界行为及必要的可观测改进；内容必须适配具体项目，不能靠换标题扩充数量。
- 项目池规模不等于同时运行规模；实际活动项目与执行并发继续受账号、运行窗口和资源约束管理。

## 自动推进的必要机制

1. 内容准备：为项目创建初始版本和路线，运行基线验收；没有通过准备检查的项目不进入可调度池。
2. 选择工作：按依赖与未完成进度选一项可执行改进，明确输入版本、范围、预期变化和执行预算。
3. 执行修改：在项目自己的工作副本继续开发，不重置为初始版本，也不共享其他账号的可写目录。
4. 独立验收：由运行器调用冻结的验收定义，核对本轮新行为以及已通过行为的回归；模型总结、退出码为零或模型自己修改后的测试不单独构成完成证据。
5. 成果固化：验收通过才推进路线，保存代码版本、差异、日志和资源用量，使后续步骤有明确起点。
6. 失败恢复：把具体失败证据反馈给执行器，在有限次数和预算内修复；用尽后保存失败现场、保护最后已验收版本，阻塞当前依赖链并选择其他合格项目。
7. 运行恢复：停止、重启、额度等待恢复时核对项目版本和原步骤状态，不重复投递已经确认消费的输入或重复完成同一步。
8. 路线终点：标记项目当前路线完成并切换其他项目；后续扩展通过新版本路线加入，不能默认无限生成新任务以保持消耗。

上述是候选行为机制，不是已有数据库字段、API 或已实现能力。具体契约在产品范围收敛后写入 `design.md`。

## 具体路线示例：书签管理

初始版本具有本地书签列表与合成样例，后继改进可依次为：标签筛选、组合检索、重复合并预览、误操作撤销、批量导入、导出后再导入一致性、集合编排、静态集合页、损坏输入处理、索引更新等。

每步都增加可以自动核对的行为，例如重复合并必须保留来源标签；下一轮读取前一轮保留的代码和数据格式。此示例记录规划阶段的路线粒度；现有首版 100 项目的实际覆盖见 `catalog-scope.md`，实现与验证状态见 `../implement.md`。
