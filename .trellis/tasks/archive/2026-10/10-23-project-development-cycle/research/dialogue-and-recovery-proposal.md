# 动态需求方、失败返工与断点续做方案草案

## 状态与来源

- 本文是简化方案草案，服务于 PRD 的 R2～R5、R7、R9 和 R10。用户已接受动态推进，随后要求简化，并明确指定使用外部 OpenAI 兼容 API 作为需求方。
- 本轮用户新增要求：考虑评审不通过的后续处理；说明模型动态推进的具体做法；超时后下次执行机会应支持类似断点续传的任务续做。
- 未开始产品实现，不把本文中的角色、动作或状态当作已经存在的接口或字段。

## 动态推进的职责

### 开发者

- 在原项目工作区与原生会话中调查源码、回答细节、提出方案、执行修改、测试和修复。
- 同一需求／BUG 的正常交流、超时恢复和验收返工使用同一个逻辑开发者会话。

### 需求方

- 服务端向 `https://ai.flower-cli.com/v1/chat/completions` 发送一次短请求，使用用户指定的 `gemini-3-flash-agent` 生成下一条需求方消息。该地址的可用性以本地最小测试为准。
- 每次根据本地保存的任务、对话和确认过的方案构造请求，无需创建需求方 CLI、容器或长期服务端会话。
- 主模型额度不足、限流或暂时故障时有限降级到 deepseek-flash；主备连通已通过，切换规则与接入以最终 design.md 为准。
- 输入是冻结的真实业务目标、允许披露的材料、公开约束、已确认方案、实际对话及可读的业务验证反馈；需要源码事实时只能依据实际提供或受控读取的公开源码。
- 根据上一轮实际内容生成下一条自然交流：深入追问、回答开发者澄清问题、选择已有材料补充、针对不同方案讨论约束，或明确同意方案并要求实施。
- 对于同一目标，不完整回答与完整回答应产生不同后续动作；不固定每项任务的轮数，不把预设题目换序称为动态推进。
- 不读取私有测试源码、参考补丁或隐藏评分答案；不能编造现场、任意扩展需求，也不能由一条“已经完成”的自述决定交付通过。

### 控制程序与最终验收

- 控制程序复用已有调度，保存原任务、开发者会话和工作区、下一条消息的投递状态、方案确认事实及预算；在现有任务循环内增加一个外部请求步骤。
- 讨论期间允许调查和复现；只有方案确认后进入已授权实施。需求方生成的下一条消息需要先保存意图，再实际投递和核对消费。
- 实际交付后先冻结候选，运行独立程序行为与回归验证。确有语义要求的任务可在交付阶段进行一次正常审查；普通问答不启动评分作业。
- 最终完成必须由控制端验证事实支持，需求方或开发者的文本不能直接写入通过状态。

## 一个有实际分支的交流例子

以现有 Click 错误附注增强材料为候选，不假设已经制作成新内容：

1. 需求方先提出业务目标，要求了解普通错误和参数错误的输出路径。
2. 开发者如果只说明一个入口，需求方追问另一个入口、输出流和退出码；如果两条路径及兼容约束都讲清楚，可以进入方案讨论。
3. 开发者提出方案后，需求方依据已给定的兼容要求讨论边界，明确同意后在原会话要求实施。
4. 开发者形成交付，控制端执行冻结验收。发现未加附注时原输出发生变化，则把这一实际失败事实发回原会话。
5. 开发者修复或对错误证据提出异议，随后针对新交付重新验证；完成数最终只增加一个需求。

需求方每次依据回答生成下一轮交流通常需要额外一次外部 API 调用；计费归外接服务，单独记录其真实用量。开发者继续使用原 Claude 账号额度。平台先保存有效的下一条消息再投递，重启后复用该结果，避免重复生成。实际成本和缓存效果须通过试点测量。

## 验收不通过后的处理

| 情况 | 下一步 | 计量与保留 |
| --- | --- | --- |
| 独立程序证明真实行为不符合已约定要求 | 在原会话反馈要求、预期／实际差异和可公开的复现事实，要求修复并重新提交。 | 属于同一个业务任务的返工；保留每版交付和失败报告。 |
| 最终语义审查指出有证据的问题 | 反馈原要求及交付中的具体证据，允许开发者修正。 | 记业务修正；不只反馈抽象代码或 fail。 |
| 开发者证明评审误读、扩展了原要求或引用错误 | 对同一冻结交付和原验收要求做有限复核。 | 不通过反复重抽碰运气；复核仍冲突则存疑待处理，保留原成果。 |
| 评审超时、JSON 无效、进程失败或验证环境不可用 | 恢复／有限重试对应基础设施阶段。 | 不扣业务修复次数，不让开发者重新实现已经完成的内容。 |
| 剩余预算不足、有限修正／复核耗尽或连续没有进展 | 保留会话、文件与问题清单并显示待处理原因。 | 不自动加预算，不清掉半成品，也不记完成。 |

反馈内容需要从公开需求、可披露材料和实际验证结果生成；保留私有套件与参考补丁隔离。模型异议不能覆盖明确的程序失败，模型审查也不能在交付后新增验收范围。

## 超时后的断点续做

业务任务和底层执行片段分别记录。一次执行超时后，运行历史保持 timeout；完整任务在可恢复且有预算时等待续做。下次可用执行机会先核对旧进程已释放，在同一会话、同一工作区继续。

### 需要恢复的进度

- 真实任务目标、公开约束、已确认方案、当前阶段和待办事项。
- 开发者原生会话、已披露材料、已保存的需求方回复与实际消息消费边界。
- 原工作区和未提交修改，以及最后已接受版本、待验收版本和每次验证报告。
- 尚未投递或尚未确认消费的消息及其原内容，不能重生成另一条消息冒充原投递。
- 已消费工作、角色用量、任务累计剩余预算和对应门禁。

结构化进度与原生日志、文件状态共同作为恢复依据。模型可以整理摘要，但摘要不能覆盖实际文件、消息投递或验证事实。

### 恢复时的处理顺序

| 中断点 | 恢复动作 |
| --- | --- |
| 需求方消息已生成但尚未发送 | 核对原投递意图后发送原消息，不再次生成不同的追问。 |
| 消息已发送但未确认是否消费 | 先核对原生输入；已消费则禁止重发，证据不明确则待对账。 |
| 开发者已消费输入但尚未形成完整回复 | 通过原会话续做当前未完成事项，保留已改文件。 |
| 开发者已交付，尚未完成验收 | 继续原冻结交付的验收，不要求重新实现或重复提交。 |
| 验收结论已产生，尚未写入最终状态或反馈 | 幂等完成原结论的收口或原反馈投递。 |

### 调度与边界

- 同账号内，可恢复且门禁允许的旧任务优先于新需求。任务 A 超时后，新任务 B 到达时 B 保持在自己的队列中，不把 B 的提示注入 A 的原会话。
- 其他账号不受 A 的普通等待影响；账号硬门禁、人工暂停与停止继续生效，等待不持有执行名额。
- 单次片段超时与完整任务累计预算耗尽分别显示；续做不重置累计预算，也不把管理切片算成业务修复。
- 整体预算耗尽、人工停止、身份变更、会话缺失、工作区归属异常、消息消费不明或旧进程释放失败时，不自动强行恢复。
- 任务可在多个执行片段间持续，最终只在独立验收通过后记一次业务完成；缓存是否仍命中继续按真实用量记录，不作保证。

## 后续规划边界

最小循环是“外部 API 生成下一句话 → 投递到开发者原会话 → 保存实际回答 → 生成下一句话或进入交付验收”。验收不通过在原会话返工，执行超时续原任务。先用一个真实需求和一个 BUG 验证，再推进百项目重审；整体范围保持不变。本轮不修改运行时和正式内容库。
