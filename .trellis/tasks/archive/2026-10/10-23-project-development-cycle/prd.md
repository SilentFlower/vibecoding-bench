# 项目迭代按完整需求与缺陷开发周期重设计

## Goal

让自动项目迭代以一项真实需求或一个 BUG 的完整开发周期为任务，在同一会话中完成理解、深入追问、方案确认、实施和验证。

## Background

- 用户在恢复会话 `01a15fce-f690-79f0-a83a-03f3b2077d7f` 后指出：问答很快结束、相关问题被拆散、普通询问还要独立评审，与真实开发使用方式存在明显差别。
- 用户明确举例：“比如说我想给A模块开发一个需求，一般会问这块代码是怎样的，刨根到底到细节，然后在同一个对话里面拿准方案后，才在这个对话去做。”修复 BUG 同样按完整过程组织。
- 用户已确认任务以完整需求／BUG 计数；代码理解、咨询、诊断、方案、追问和返工均属于任务内部过程，不分别计任务。
- 用户接受模型动态推进，并要求简化为外接 API 生成下一条需求方消息；开发者继续在原 Claude Code 会话工作。服务与主备模型的最终选择见 R10。
- 开工前的正式内容为 100 个真实项目、426 个场景、726 个旧粒度任务，其中 understand 234、consult 227、plan 109、diagnose 119、modify 37；这些历史数量不能直接转称为完整开发周期任务数量。
- 开工前每个场景持有独立会话，同场景候选能够恢复原会话，但非修改类回答仍进入独立模型评审，评审未完成会阻止同场景后续对话。证据见后续任务研究记录。

## Requirements

### R1：以真实交付目标定义任务

- 一项任务对应一个能够独立验收的功能需求或缺陷修复，包含明确的初始背景、目标行为、范围、约束与最终交付。
- 理解代码、调查根因、讨论方案、修改代码、补测试和失败修正均在任务内部推进，不拆成独立任务，也不通过固定轮数或时间凑工作量。
- 保留真实上游源码、来源、许可证、固定基线和现有离线依赖；缺陷须可复现，需求须有可验证的行为增量。

### R2：同一会话贯穿开发周期

- 同一需求／BUG 的开发者会话、工作区和已完成成果连续保留，后续对话承接既有解释、调查和方案。
- 暂停、额度等待、工作片段超时或服务重启后恢复同一任务的原会话和进度，禁止将新会话或重建工作区伪装成续接。
- 恢复后应能还原当前阶段、已确认方案、已披露材料、未完成事项和原工作区中的半成品；已经完成的调查、修改与验证不因换一次执行而丢失。
- 已生成但尚未发送的需求方消息、已发送但未确认消费的消息、已消费但尚无完整回复的消息必须能够区分；恢复时先核对实际投递和消费事实，不能重复提问或要求开发者重做已完成工作。
- 开发者已经形成交付、正在等待验证，或验证已经返回但尚未收口时，从相应步骤继续，不重新触发开发者实现或需求方追问。
- 需求方依据本地保存的任务、公开对话和已确认方案重新构造请求；恢复时不忘记既有约束，也不需要长期维持另一套 CLI 会话。
- 任务完成前不因答完某个理解问题就轮换项目；项目轮换、完成数量和预算展示按完整任务定义重新解释。

### R3：对话按实际进展推进

- 需求方根据已收到的回答继续追问细节、回答澄清问题、提供实际存在的材料，并补充任务范围内的约束。
- 需求方采用一次外部模型请求生成下一条用户消息，输入取自当前任务与实际对话。复用已有调度、会话、工作区和投递机制，避免引入第二套常驻执行环境或通用工作流平台。
- 信息不足、根因未明或方案仍有分歧时继续调查和讨论；方案拿准后，在原会话明确进入实施，再依据交付和验证反馈进行修正。
- 不把若干固定问答按顺序拼接后称为动态开发流程；不强制每项任务经历相同轮数。
- 需求方不得编造上游实现、现场数据或测试结果，不得把私有验收答案泄漏给开发者。

### R4：普通对话不逐轮评分

- 理解、追问、咨询、诊断和方案讨论不因每条回复完成而启动独立评分模型，不以每轮 pass 作为继续交流的门槛。
- 对话推进与最终交付验收在职责和产品展示上明确区分；需求方的追问、补料和方案确认不计作独立评审成绩。
- 不以全局移除验收的方式绕过真实交付质量验证。

### R5：按交付结果验收

- 对功能需求验证新增行为和兼容约束；对 BUG 验证原问题可复现、修复后通过和相关回归有效。
- 验收使用控制端独立证据，不能仅凭模型自报完成或退出码为零接受成果；必要的交付审查只在实际交付阶段触发。
- 测试失败后，在原任务和会话内反馈具体事实并继续修正；环境故障与业务失败分别记录，重复验证或重试不增加任务完成数。
- 交付不通过必须对应原任务的具体要求，并提供可核对的问题位置、失败行为、预期与实际差异以及可公开的复现或验证事实；不能只把 fail 或抽象反馈码发回开发者。
- 开发者可修复真实问题，也可针对评审误解给出有依据的异议；复核使用同一份冻结交付和原验收要求，不增加新要求，也不反复重抽判定直到出现 pass。
- 模型评审证据不足、判断相互冲突或复核后仍无法可靠结论时，保留成果并显示存疑／待处理；明确的程序失败不能被模型意见覆盖。
- 评审超时、格式错误或验证环境故障先恢复或重试对应执行，不能直接算作开发者交付失败或消耗业务修复次数。
- 业务修复、评审复核和基础设施恢复分别受有限次数与累计预算约束；无进展或预算耗尽时保留原会话和成果，明确阻塞原因，避免无限循环。

### R6：重组已有百项目内容

- 现有 100 个项目均纳入重审；复用真实源码、既有调查、缺陷复现、独立测试及离线制品，围绕完整交付目标重新归并、筛选和补齐任务。
- 纯理解／咨询材料可以作为背景、对话材料或调查线索，但不能改名后继续冒充完整开发需求。
- 每项新任务保留旧材料与新交付目标的可追溯映射；实际任务数量由有效需求和缺陷决定，不沿用每仓固定数量、726 或历史 2,000 提案作为新任务数。
- 有阻塞或尚未完成准入的项目明确列出，不以样例跑通代替百项目范围完成。

### R7：保留历史与真实计量

- 已冻结内容版本、旧批次、会话、账号身份、运行记录和历史成果继续可读，不批量重算历史任务进度或迁移正在运行的旧作业。
- 页面展示完整需求／BUG、当前阶段、连续对话、最终交付及验证结果；内部对话轮数与业务任务完成数量分别统计。
- 分别统计开发者、需求方及最终验收的实际调用和用量；缓存命中以真实缓存读写证据显示，不由 session ID 推断。
- 开发者执行和原有验收继续遵循现有账号额度、运行时段、资源与严格释放规则；外接需求方的请求、用量及费用归属独立记录，不混算成 Claude 账号额度。

### R8：修复已观察到的结果交接故障

- 保留原会话与超时事实，修复 CLI 对指令局部添加粘贴包装后，平台不能确认输入、无法回收已生成评审结果的问题。
- 合法包装变化可以核对原始投递；输入内容变化、未知额外文本或归属冲突仍须拒绝，不通过宽松匹配或直接采信 pass 放行。
- 新流程复用的对话交接同样覆盖该边界；修复与真实账号重新验收分别留证。

### R9：区分执行片段超时与完整任务结束

- 单次执行达到时限只结束当前工作片段，原运行保留 timeout 事实；完整任务在预算和恢复条件允许时进入待续做，不直接判业务失败或当作新任务重新创建。
- 下次可用执行机会先核对原作业已严格释放，再从持久进度续做；同一账号内可恢复的原任务优先于新的需求／BUG，不把新任务消息混进旧任务的会话。
- 因额度、运行时段、人工暂停或恢复证据异常而不可执行的任务不得无限占用执行名额；其他账号独立推进，调度时继续遵守各账号的有效门禁。
- 所有工作片段共用完整任务的累计工作预算；恢复、进程重启和新建底层运行记录都不能重置预算。累计预算耗尽时保留待处理状态和原因，不自动无限加时。
- 超时续做与交付失败后的业务修复分别计量，不因基础设施切片而损失业务修复机会。
- 人工停止或取消优先于自动恢复；原会话或工作区缺失、输入消费不确定、身份变化或旧进程尚未释放时，保留现场并阻塞恢复，不新建会话冒充成功续接。

### R10：以简单配置接入外部需求方模型

- 接口为 `https://ai.flower-cli.com/v1`，采用 OpenAI 兼容格式，主模型为 `gemini-3-flash-agent`。服务端通过 HTTP 请求生成需求方消息，不为需求方创建 Claude Code 会话或容器。
- 需求方备用模型为同一服务的 `deepseek-flash`。主模型额度不足、限流或暂时服务故障时有限切换；实际使用模型和切换原因可查。认证或参数配置错误应明确报错，不能靠反复切模型掩盖。
- 主备均不可用时保留原任务和待生成消息，等待恢复；有效消息已经生成则复用它，不重复调用或同时发送主备两条消息。
- 页面支持动态调整一个 Base URL、API Key 和多个可用模型；按列表优先级确定主用与降级顺序，保存后无需重启。密钥保存在服务端受保护配置，前端只显示已配置状态，留空保存沿用既有密钥；密钥不进入任务、源码、前端响应、原生日志或导出报告。
- 配置修改不更换开发者会话，不重新生成已保存消息；在途请求使用开始时的配置，后续请求读取新配置。旧任务已使用的模型被移除时从新列表重新选择，不因旧模型名阻塞新请求。
- 请求只携带生成下一轮业务交流必需的任务背景、已披露材料和实际对话，不上传私有验收源码或参考补丁。
- 请求受超时与输出上限约束；服务故障、限流或无效回复保留原任务，禁止投递不完整问题、重新创建开发者会话或将其判为业务失败。
- 用户提供的凭据授权本地最小连通测试；完整真实任务调用、生产配置应用和部署另按最终计划执行。

## Acceptance Criteria

本轮勾选依据是已授权的隔离机制验证、36 项独立原生内容准入及实际上线验证。开发者回复和最终语义评审使用隔离替身，未运行真实 Claude 业务任务；真实模型质量、费用和缓存收益不在这些勾选的证明范围内。真实供应商仅进行最小动作及模型目录连通验证。

- [x] AC1（R1、R6）：新任务均有独立交付目标、范围和验证依据；对话阶段不被单独计作任务；100 个项目都有明确重审结果与可核验的就绪／阻塞记录。
- [x] AC2（R2、R3）：至少以一项功能需求和一个 BUG 实际演示完整周期，包含源码细节追问、澄清或补料、方案确认、实施、验证及必要返工；开发者原生会话和工作区贯穿过程。
- [x] AC3（R3、R4）：相同目标面对不同回答时能产生不同的合理后续交流；普通讨论轮次没有独立评分作业，后续对话不等待每轮 pass。
- [x] AC4（R5）：未交付、原问题仍存在、兼容回归失败或验收证据不足时不能记任务完成；修正后只记一次业务完成。
- [x] AC5（R2、R7、R9）：暂停、额度中断、超时恢复、服务重启及停止竞争保持正确任务阶段、原会话、确认过的方案和半成品；历史 timeout 保留，恢复片段不重置任务累计预算，也不消耗业务修复次数。
- [x] AC6（R7）：页面、API、数据库和原生日志对同一完整任务的阶段、对话、成果与用量一致；历史版本和旧批次继续读取原语义。
- [x] AC7（R8）：原始输入、完整包装和实际观察到的局部包装均能正确完成交接；内容差异、伪造归属和额外指令被拒绝；已形成最终结果不因输入包装误判而超时重发。
- [x] AC8（R5、R7）：隔离模拟与真实模型行为验收分别记录；未经重新实测，不把模拟成功称为真实模型质量、成本或缓存命中验证成功。
- [x] AC9（R5）：验收不通过能在原会话获得具体证据、修复并复验；评审误解可针对同一冻结交付提出异议；复核仍存疑时保留成果，不靠重复抽评通过；评审或环境故障不惩罚开发者。
- [x] AC10（R2、R9）：分别覆盖消息未发送、已发送未确认、已消费未回复、开发者交付待验证、验证完成待收口这五处中断；恢复后只执行尚未完成的步骤，不重复发送或提交交付。
- [x] AC11（R9）：队列同时有原任务续做和新任务时，在同账号恢复条件满足且有剩余预算的情况下优先续做原任务；停止、预算耗尽、证据异常与旧进程未释放均不能被下一次调度绕过。
- [x] AC12（R3、R7、R10）：指定外部接口可返回合法需求方消息并送入开发者原会话；外部请求失败或重复收口不产生重复提问，密钥不出现在公开数据，需求方用量与 Claude 执行用量分开。
- [x] AC14（R7、R10）：从真实页面修改 Base URL、密钥和多个模型并保存，服务重启后保留；在途调用、待生成消息和已生成消息分别按上述边界处理，鉴权与密钥脱敏有效。
- [x] AC13（R10）：模拟主模型额度不足、429 和暂时服务故障时使用 `deepseek-flash`；认证／参数错误明确失败，主备均失败时保留任务等待；只投递最终有效的一条消息并按实际模型记录用量。

## Out of Scope

- 新增账号、提高账号资源预算、改造网关协议或重新设计养号与额度系统。
- 删除或重建生产账号、旧会话、历史内容版本、运行记录和业务数据。
- 为拉长耗时添加无业务价值的等待、固定轮数、重复问题或重复评审。
- 不启动 auto-loop、不触发真实 Claude 开发任务；外部服务仅执行已授权的最小连通测试。用户在实现和检查完成后另行确认了精确 Git 计划，并明确追加“并部署”，因此允许提交推送及更新现有美国 v3 环境。
