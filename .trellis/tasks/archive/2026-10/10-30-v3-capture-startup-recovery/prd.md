处理账号 10 的 Arrow 抓包启动故障，使原目标能够在保留已有成果和执行身份的条件下恢复，并使后续启动失败可被准确诊断。

- 用户先要求检查线上启动失败，随后明确要求“处理吧”；处理对象为 `us` 部署的账号 10。
- 2026-10-30 14:28:43（北京时间），工作 `9772ee0ad1c14f998f6787eae8fa87b4`、目标 `AR-WEEKDAY-DEV`、控制代次 29 记录 `startup_unknown / preparing / ValueError`，当前状态为 `blocked`。
- 当次工作区和 Python 依赖已准备完成；仅留下作业设置文件和已关闭的抓包状态，未生成 CLI 进程证明、原生会话或输入动作。账号环境已回到 `ready` 和透传模式；网络容器 OOM 与 PID 超限计数均为零。完整检查事实见 `research/incident.md`。
- `orchestrator/projects.py:2002` 将未知启动错误转换为固定提示，只保存异常类型，历史原始异常已无法还原；目前只能定位到抓包网络切换边界，不能将进程竞争等假设当作已确认根因。
- `orchestrator/projects.py:1287` 的人工恢复检查没有接纳 `startup_unknown`，因此当前普通启动入口不能直接恢复此工作。

## 需求

- **R1 故障诊断**：真实启动失败须保留可定位到失败步骤的私有诊断；原始故障与后续清理故障分别留存。诊断绑定账号、工作、空间和本次尝试；任何公开 API、SSE、页面和普通日志均不得泄露凭据、请求正文或私有诊断内容。
- **R2 有证据的修复**：使用隔离夹具验证抓包网络切换和监听进程收口，只修复通过复现或直接证据确认的问题；历史原因无法恢复时明确记录这一限制。
- **R3 受控人工恢复**：现有人工启动入口可以在服务器确认原工作尚未开始执行、没有输入动作、账号身份与冻结合同一致、环境和执行已严格收口时恢复该原目标。自动调度不因此获得重试未知执行的权限；已有执行、输入未决、身份变化或清理未确认时继续拒绝。
- **R4 保留现场**：恢复沿用原工作 ID、Claude 会话 ID、工作区、冻结工程版本、CLI／模型／思考预算及抓包开关；原故障事实在真实启动成功前保留。
- **R5 线上交付**：完成本地验证和项目要求的检查后，按现有 v3 联合镜像流程交付到 `us`，并通过现有人工控制入口恢复一次原目标，观察实际启动和响应。沿用该环境“不做备份、不重新计算内存、保留现有资源参数”的既有运维选择；完成部署后的定向旧镜像回收。

## 验收标准

- [x] **A1 → R1**：注入网络切换及清理异常，能在私有诊断中定位原失败步骤、异常类型和栈位置；两类故障可区分，敏感测试值不进入诊断及公开输出，诊断写入失败不覆盖原故障。
- [x] **A2 → R2**：真实隔离进程／容器内重复执行透传→抓包→透传成功；已确认修复有对应回归，未知 PID 不被误杀，兄弟执行和原证据不受影响。
- [x] **A3 → R3**：人工恢复仅接受已核对的未启动原工作；自动扫描、已发输入、未知输入、存在运行时、未完成收口、身份／合同变化及旧代次均被拒绝，拒绝不清除原故障。
- [x] **A4 → R4**：恢复保持上述执行身份和已有成果；只有终端及启动后门禁成功才记录 `resolved_at` 与 `runtime_recovered`。
- [x] **A5 → R5** `[上线后验证已完成]`：同批镜像和线上归属核对通过，原工作实际启动并出现可信原生响应，健康、资源参数、身份、抓包开关和部署后镜像保留集复核通过。实际发布、恢复入口及验收证据见 `validation.md` 与 `release.md`。
