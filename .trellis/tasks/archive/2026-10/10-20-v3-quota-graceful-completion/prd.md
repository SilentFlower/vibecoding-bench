# v3 额度阈值恢复为本轮完成后等待

## Goal

让 v3 普通任务和养号在达到自设额度百分比阈值时完成当前整轮，再等待下一轮允许启动。

## Background

以下旧实现和代码位置取自实施前 `7d705e3`；完成情况见实施记录和父任务组合验证。

- 用户明确要求：“之前硬性的超过阈值也改回来……直接 stop 任务……没必要”。来源及统一语义见父任务 R6、D2。
- 旧实现由 `orchestrator/main.py:6515` 的 `_enforce_running_quota` 写 stopping 并清理；`:6793` 的等待回调触发检查。
- v3 普通任务和养号都使用 passthrough，且 driver 的 QUOTA_WARMUP 为 0：`orchestrator/account_runtime.py:1244`、`:1270`。Recorder 中旧养号逐请求阈值逻辑不是本次 v3 主路径，不能以猜测扩大到旧 runner。
- 已有下一轮启动门禁、等待和持久单次恢复：`orchestrator/main.py:2850`、`:3092`、`:3588`、`:6212`、`:7047`。
- 既有强停测试/离线验证及页面说明必须随行为同步：`orchestrator/test_quota_hard_stop.py:1`、`deploy/v3/verify_quota_hard_stop.py:1`、`webui/index.html:426`、`webui/app.js:513`。

## Requirements

- P3-R1：普通任务（含批次）和养号在运行中等于或超过自设 5h/7d 阈值时不被 STOP，不写阈值导致的 stopping/stopped；运行中降低阈值同样只影响下一轮。
- P3-R2：“本轮完成”涵盖已启动 run 的原定业务、补充消息、收尾及原超时；不因阈值提前收尾、不替换历史冻结计划，终态由实际进程结果决定。
- P3-R3：保留两个阈值的配置数值、严格校验、启动前检查与下一轮等待；批次保留未执行项和原 next_launch_at，养号保留正常随机间隔。
- P3-R4：继续被动采集及在发布本轮终态前消费最后观察，使后续投放看到最新用量；不增加 usage 轮询或模型探测。
- P3-R5：真实限流/额度耗尽、认证失败、用户停止、删除、超时、清理失败和既有单次恢复许可保持各自处理；不把自设阈值误称为实际额度耗尽。
- P3-R6：页面、部署说明、单测和真实本地验证统一表达“本轮完成后等待”；历史 stopped/stopping 意图按原记录收口，不改成成功，不自动续跑历史停止任务。

## Acceptance Criteria

- [x] 普通和养号分别覆盖低于、等于、一次响应跨过 5h/7d 阈值及运行中降低阈值，本轮均能按实际结果完成。
- [x] 真实 driver/tmux 在跨阈值后继续执行原定补充和收尾，项目及会话保留，API/SQLite 显示实际终态。
- [x] 本轮结束后，下一普通任务、批次 item 和养号轮次在命中有效阈值时不启动；窗口 reset/被动更新/关闭阈值后只按现有许可与原间隔恢复一次。
- [x] 用户停止、真实耗尽、认证失败、超时、停止意图重启收口及独立 API 并发回归通过。
- [x] 页面不再声称达到自设阈值会强制结束本轮，明确本轮可能越过所设百分比。

## Out Of Scope

- 旧 runner/Recorder 的百分比策略、抓包/交互续聊/网关 API 的百分比策略、阈值默认值与真实耗尽算法。
- 历史强停任务返工、历史终态迁移或复活、账号凭据/画像变更及真实账号模型验证。
