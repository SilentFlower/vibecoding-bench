# cc2api：SSE事件与压缩长流统计修复

## 目标

修复 R4-01／02，使合法 SSE 排版及等价压缩长流得到一致的本地用量与诊断摘要，客户端响应继续原样转发。

## 背景与证据

- 用户明确选择修复 R4-01 和 R4-02。两项共同服务于同一响应观察结果，作为一个交付，不另拆独立产品任务。
- 依据既有研究 [第四轮评审](../10-29-cc2api-vm2api-wire-differential-study/research/alignment-review/round-04.md)；66 组冻结实验中，12 组多 data／CR-only 和 4 组压缩长流出现统计缺失。它们不是生产故障率或新原生版本抓包。
- 当前产品基线为 cc2api `7a5495127f379f66e16b79a48da168088d08002f`。R4-01 的现有原因位于 `cc2api/src/service/usage.rs:112`、`:168`：按 LF 和单 data 行读取。R4-02 的现有原因位于 `usage.rs:388`、`diagnostics.rs:321`、`gateway.rs:7108`：压缩响应结束后整包解码、受到整个响应 1 MiB 的采样限制。
- UsageCapture 同时服务正式用量和独立诊断。本地费用是标准 API 折算，不能据此推断官方订阅额度扣减；默认数值零不能解释成完整免费响应。

## 要求

- R1（R4-01）：按完整 SSE 事件读取多 data 字段、LF／CRLF／CR、跨 chunk 边界、流首 BOM、注释与空行；同一事件的 data 用换行连接，只在空行派发。未派发 data 不贡献用量，已派发事件继续保留既有累计最大值、真实零值、缓存分项、未知模型和 partial／未定价语义。
- R2（R4-02）：已有支持的 gzip／x-gzip、zlib／raw-deflate、标准 br、zstd 及预算内编码链采用有界增量观察，使常规长度事件组成的长 SSE 不再因整条响应超过 1 MiB 而丢失头尾 usage。完整 JSON、异常大行／事件、解码层数、工作区与输出块仍有资源边界；无法可靠识别或完整解码的格式保守标记 partial，不据部分解码宣称完整。
- R3：用量记录、尝试诊断以及已有缓冲入口使用一致的观察逻辑；EOF、末帧、body error 和 Drop／下游取消仍只完成一次，不重复落库或把损坏／中断冒充完整零消耗。
- R4：网络响应的原字节、编码头、状态、时序及既有重试／调度维持原合同；观察失败只影响统计完整性，不阻断转发、不读取第二份网络响应、不等待完整正文或数据库后才返回。
- R5：所有统计继续遵守安全摘要和异步持久化合同；不持久化响应正文、工具参数、完整头或身份明文，采集故障沿用现有受控原因及 observation_failures，不让迟到快照覆盖终态。

## 范围外

- 不修改 R3-01 响应保活、R4-03 补结束帧策略、R4-04 计时定义；不增加设置、前端、数据库迁移或定价变化。
- 不改变请求编解码、身份／CCH、stateful 缓存锚点算法、自动遥测载荷规则和账号窗口限额来源。
- 不覆盖冻结研究，不使用真实账号推理或生产环境，不部署；Git 提交／推送遵循项目独立计划评审。

## 验收标准

- AC1 → R1／R3：合成 SSE 的紧凑／多 data／CR-only／CRLF／BOM、注释及跨字节分块，明文与各编码得到相同 token／缓存／模型／结束摘要；累计 max 与真实零值正确，未派发尾事件不贡献用量。
- AC2 → R2：实际 Gateway 通过大于 1 MiB 的长 SSE 对照，同时覆盖解压后超过 1 MiB 和原始压缩字节超过 1 MiB 的情况；统计及诊断保持可用，不把所有上限直接取消。大 JSON／大事件、未知／损坏／截断编码仍受控标记 partial。
- AC3 → R3／R4：实际 Gateway＋本地上游＋临时 SQLite／DiagnosticsStore 验证 API／CC、JSON／SSE、正常结束／取消／错误，客户端正文与上游字节一致、有效编码头一致、用量每次只写一条；不新增上游请求、补结束帧或变更 TTFT。
- AC4 → R1–R5：Rust 格式、全量及既有 CCH／请求压缩／保活／诊断／费用回归通过，记录精确命令、结果及未覆盖边界；安全摘要不包含合成正文秘密标记，既有观测故障计数和根／尝试终态保持一致。
