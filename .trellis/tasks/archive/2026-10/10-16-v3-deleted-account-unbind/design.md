# 技术设计

## 边界

主要修改 Python cc2api 客户端与 AccountRuntime 所有权切换；不改变 Rust 门禁接口的不存在语义，不新增数据库结构或用户按钮。原 owner → environment 保护、运行状态检查与凭据处理保持。

## 明确不存在的判断

复用 Cc2ApiClient._request 已通过异常链保存的 urllib.error.HTTPError HTTP 状态，不根据“not found”等提示文本猜测。仅针对解绑/删除时的原绑定账号 lease GET 或 prepare 返回 404，再成功分页读取账号列表确认该 ID 不存在，才跳过无法为已删除账号建立的远端门禁。列表包含原 ID 或列表查询失败时继续拒绝。实现优先在该调用边界处理，不为全部管理请求提供宽泛容错。

新绑定目标和正常远端账号仍沿用严格查询、prepare、占用核对和 finally release。已有远端门禁不得被错误分类为缺失。

完整列表确认复用 `Cc2ApiClient.list_accounts(require_complete=True)`；仅该可选模式校验页号、页容量、总数/页数、当页行数、正整数 ID 和全量去重计数。原普通列表调用保持兼容。无法证明完整时拒绝，不把过滤掉的坏行当作账号不存在。

## 本地安全收口

缺失远端门禁不代表本地空闲。原 jobs 检查及 main 的活跃运行/续聊/登录保护保留；调用实际发送器状态，活动或读取失败时拒绝。仅确认无活动后停止旧容器、更新 stopped，在上下文内清空原绑定和养号状态。继续沿用既有本地凭据发布，不访问已删除账号、不产生新设备或凭据。

## 验证与上线

单测使用真实 HTTPError 异常链验证状态分类，合成 SQLite 检查绑定事务及拒绝后的不变性。隔离堆栈以空数据库创建合成绑定，正式 cc2api DELETE 后调用 bench DELETE，再核对实际页面与两库；不使用生产账号作为失败演练资料。生产只在完成验证和发布后，通过正式解绑路径解决已确认的悬空记录，保留 HOME/身份基线并核对停止状态。

## 风险与恢复

404 可能来自错误路由，因此必须附加成功列表读取；远端缺失也可能残留发送器，所以不能跳过本地占用检查。发布前保留当前部署清单与停机快照，按 v3 SOP 成组切换；不复制或手工恢复已删除的远端账号。
