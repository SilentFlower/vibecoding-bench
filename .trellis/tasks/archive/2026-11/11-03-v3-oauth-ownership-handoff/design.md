# 凭据所有权与受控交接设计

## 1. 范围与不变量

对应 PRD O1–O8。本设计新增的是 v3 管理账号的所有权协议，不改变普通非 v3 OAuth 账号的刷新语义。

- 任一可执行时刻只有一个刷新所有者；交接中可以两边都暂停。
- 账号业务状态和凭据归属分离。人工停用、封禁、额度冷却与 RPM/并发配置不能被交接覆盖。
- 长期所有权必须持久化；RuntimeGate 的 30 秒租约只承担短期占用，不能被无限续期当作解绑状态。
- 管理 profile 仍为 root 管理的完整镜像，关联运行 HOME/access 仍为 AT-only；不增加业务可读的 RT 存储。

## 2. 持久状态

以下为待新增的协议模型，不能当作现有字段调用：

| 记录 | 内容与用途 |
| --- | --- |
| cc2api 账号所有权记录 | 按账号记录 owner=gateway/local、phase=ready/handoff/reauth/reconcile、协议版本、代次、受信任部署/环境/本地账号归属、当前操作 ID |
| cc2api 交接回执 | 操作 ID、方向、请求摘要、原/目标代次、阶段及提交结果；与所有权和需要更新的凭据同事务写入，不额外保存令牌 |
| bench 本地归属及待办记录 | 即使关联字段为 NULL，仍保留原远端 ID、环境/部署、已确认代次与阶段；在本地事务中写入，不包含令牌 |

cc2api 记录为远端准入权威，本地只有在受信任回执确认 owner=local 后才可运行刷新。新迁移支持 SQLite/PostgreSQL，使用显式条件更新；缺失、损坏、代次不符或提交结果不明均进入待核对。

普通手工账号无本协议记录时沿用原模式；新 v3 CLI 创建从交接阶段发布，确认本地 AT-only 后再允许网关使用，避免创建成功而本地关联失败时出现两个所有者。

| 持久状态 | cc2api 普通上游活动/刷新 | v3 本地刷新 | 允许的受控操作 |
| --- | --- | --- | --- |
| gateway / ready | 允许，仍受原业务状态约束 | 不允许 | 开始解绑或关联重授权 |
| local / ready | 不允许 | 允许，仍受本地原约束 | 开始回交或本地重新登录 |
| 任一 owner / handoff | 不允许新活动，等待已接纳活动结束 | 不允许新刷新 | 同操作、同代的交接与回执查询 |
| gateway / reauth | 不允许普通活动/刷新 | 不允许普通刷新 | 原受控临时目录登录和提交 |
| 任一 owner / reconcile | 不允许新活动/刷新 | 不允许新刷新 | 核对回执并恢复原操作 |

任何状态检查与接纳新活动都要在同一账号协调边界中完成，检查后不能无许可发送；不得持有同步互斥锁跨网络等待。远端排空等待不能阻塞当前在途刷新取得其结束所需的锁，完整锁序在实施时按现有 await 边界核对并用并发测试验证。

## 3. 统一上游准入

在 AccountService/RuntimeGate 附近复用现有账号锁与占用机制，引入账号级上游活动许可：

1. 调度筛选时读取脱敏归属摘要，暂停账号不进入新候选；不修改评分权重。
2. 获取 RT、刷新、401 恢复或发起任何账号上游活动前核对持久 owner/phase。
3. 实际发送前再次检查，许可覆盖到发送结束；prepare 先关闭新许可，再等待已有模型、刷新及后台活动排空。
4. 旧 AT 的遥测会话要停止后续派生发送，已经派生的请求也计入排空。bootstrap、无认证辅助路径、count_tokens、测试账号、额度和预热不能绕过。
5. 本地刷新调度、任务、两个迭代、登录与恢复入口同样读取本地归属；结果不明不能因关联字段为空就降级本地刷新。

对暂停或交接使用明确的暂不可用错误，不写成凭据永久失效，不触发跨账号重试来绕过既有粘性会话。后台预热/遥测按暂停跳过，不能因此停用账号。管理配置读写继续走原权限和字段白名单，所有权字段仅受控交接可写。

## 4. 解绑：gateway → local

1. 按 owner → profile → environment 顺序取得现有本地锁，确认没有任务、Pi、续聊或登录占用。
2. 生成一次操作 ID，持久化无令牌意图；远端核对当前归属与代次，进入 handoff，关闭该号所有新上游活动并排空已有活动。
3. 在同一 OAuth 刷新锁内读取最终完整凭据；解绑允许结构完整但 AT 已过期的凭据，不为交接无条件强刷。
4. 本地保存同身份的完整 HOME/profile 与待确认归属，提交清空绑定及原养号字段收口；pending 期间本地不启动刷新。
5. 远端确认交接为 owner=local 并写回执；本地确认该回执后才完成归属记录并放开本地使用。远端账号维持 dormant 准入，记录及配置保留。

任一边只完成部分写入，重试都使用同一操作 ID 查询已提交事实后继续；不能把网络超时当作远端未提交。

## 5. 关联：local → gateway

1. 保留现有明确目标、账号 UUID/邮箱、设备身份、环境及唯一绑定校验；有本地所有权记录时核对原远端 ID 与代次。
2. 来源必须是当前所有者的完整 HOME/profile。按本地原所有者机制在临期时刷新，再停止本地活动；不分别尝试两份 RT，不根据 expiresAt 选较大值。
3. 远端进入 handoff，使用独立的受信任交接操作类型导入当前凭据；复用回执、刷新锁及身份条件更新，不能伪造 login: 租约。
4. 导入确认后，先完成本地绑定与 AT-only 发布，确认本地已停止持有运行刷新权，再提交远端 owner=gateway 并恢复准入。
5. 确认最终回执后收口本地 pending。若远端已提交，恢复只镜像当前权威快照，不能恢复历史令牌。

首次创建、显式 bind、兼容 sync 和旧 warmup 关联入口共用交接协调逻辑。以上回交流程只适用于已证明 owner=local 的记录；已证明由 gateway 持有当前刷新权的首次关联继续从远端取当前快照，不上传本地旧凭据。新建目标从本地当前来源交接；同身份/设备校验本身不构成“哪边凭据更新”的证明，来源不明或相互冲突时转待核对。已由本协议管理的其他环境占用目标保持拒绝。

## 6. 关联重授权

沿用 begin_login、commit_bound、finish_bound_login 的暂存和同账号提交机制：

- 开始时进入持久 reauth，排空已有上游活动；受控登录会话可以完成授权，其余后台刷新与普通请求保持暂停。
- 暂存保留原设备信息，新身份从本次 CLI 登录产物验证；登录成功不等于提交成功。
- 新凭据、有限认证状态恢复及回执仍在同一远端事务内提交；主 HOME 只发布 AT。
- 本地镜像和暂存清理都完成后回到 gateway/ready；取消、超时、崩溃和已提交回执沿用原对账原则。
- 已完成远端提交不能被取消回滚；人工/其他停用与限流不能被解除。
- 未绑定本地账号重新登录沿用本地所有权，不因此恢复远端准入。

## 7. 并发、失败与重启

所有交接带原代次和操作 ID；远端状态、凭据写入及回执使用条件事务，迟到旧刷新/401 继续按实际 AT/RT 与代次条件丢弃。

| 故障点 | 恢复要求 |
| --- | --- |
| prepare 前失败 | 原所有者保持，未产生交接事实 |
| 排空/快照/本地写入失败 | 保留原凭据与待办，停在可核对阶段 |
| 远端提交响应丢失 | 查询同操作回执；仍未知则两端保持维护 |
| 远端已导入，本地未完成 | 使用回执及当前权威快照补齐，不重新导入旧 RT |
| 进程重启或租约到期 | 根据持久归属与阶段恢复；租约失效不能放开长期暂停 |
| 刷新请求本身结果未知 | 保持待核对；无法恢复有效授权时明确提示重新授权，不承诺无损重试 RT |
| 原远端账号明确已删除 | 沿用既有完整缺失证明后本地收口；新目标缺失仍拒绝 |

## 8. 旧数据与展示

- 现有已绑定账号在受控初始化核对身份后归入 gateway，保留当前配置和 token。
- 独立本地账号与远端手工账号沿用原用法，不因缺新表而全局停用。
- 历史已解绑记录没有充分前次归属证明时，不仅凭 NULL、邮箱或到期时间推断所有者。进入待核对，只有证明同一来源或显式重授权后才建立新交接记录。
- 升级先只读盘点旧对应关系，不因同名或邮箱相同就暂停无关账号或改写归属。只有已证明属于同一 v3 关系且存在所有权冲突时，才关闭该关系双方的新刷新入口并核对；来源未证明的关联请求返回待核对，不在后台尝试两份 RT。
- 账号/环境响应提供可读的脱敏状态与恢复动作，列表读取不做 OAuth 探测，不引入逐账号历史扫描。cc2api 与 v3 界面都能解释“本地管理，网关暂停”。

## 9. 交付与回退

### 实施补充：显式重授权与本地删除

- 来源不明的历史解绑账号在成功完成本地强制重授权后，记录绑定原环境、设备、身份和 RT 摘要的无令牌证明；显式关联可用该证明向原远端 ID 交接新授权，不能退回按到期时间猜测来源。
- 新授权证明使用本次登录冻结的 CLI 版本，后续关联仍按该版本重新核验当前 HOME。独立账号未具备 cc2api 设备来源时允许保存本地登录，但清除旧证明且不授予关联资格；已退休或刷新待确认的受管恢复仍需严格身份核验。
- 删除本地账号仍不要求完整 RT。先用独立 retire 操作排空并暂停原远端账号，清除绑定后记录 retired，普通本地执行也保持关闭；只有明确重授权后才能恢复使用。原 HOME、历史和不可变 ID 继续保留。
- 这两项复用同一持久归属与回执协议；普通配置热更新和账号业务停用状态不改变。
- 受管账号实际刷新 RT 前先持久化待确认事实；收到并保存确定结果后恢复 ready。网络断线、解析失败或进程中断不自动重试旧 RT；本地待确认允许明确重授权，远端待确认允许原账号的受控重授权。既有无归属记录的账号继续原刷新行为。

父仓库和 cc2api 子模块必须同批发布。新增协议能力校验，服务端拒绝旧管理端对受管账号执行不理解新状态的绑定变更；部署/回退预检必须核对能力，不能单侧降级。

已有 local 或 pending 记录时，旧版本不能直接恢复运行。回退应先完成交接/对账，再使用理解同一所有权状态的兼容版本；不恢复旧 token 或历史数据库覆盖线上状态。

沿用 US 不做业务备份、不重新计算 RAM、保留参数的约束；发布前预拉取并核对镜像，按原空闲/停机 SOP 执行，不强杀用户任务。生产只做健康、状态和必要的非模型验收，合成验证与真实 OAuth 可用性分别报告。
