# V3：凭据所有权交接与关联重授权统一门禁

## Goal

让同一账号在 cc2api 与 v3 本地之间可靠交接刷新权，长期解绑后可恢复关联，并让已关联重授权遵守相同的维护边界。

## Background

- 父任务：11-03-v3-credential-handoff-iteration-console。本子任务独立验收，建议先实施。
- 当前重新关联从 cc2api 解析凭据后覆盖管理 profile，再改变绑定；不判断解绑期间本地独立轮换的所有权，见 orchestrator/main.py:9334。
- 当前解绑清空关联并交接 RT 给 HOME，但没有持久暂停远端账号，见 orchestrator/main.py:9639、orchestrator/account_runtime.py:897。
- v3 本地后台刷新与 cc2api 的按需刷新都已存在；具体路径、现有导入限制与来源依据见 research/code-map.md。

## Requirements

- O1 单一所有者：持久记录当前由 cc2api、本地或未完成交接管理刷新权；维护或结果不明期间不允许两边同时刷新。普通手工 OAuth 账号及非 v3 行为沿用原有机制。
- O2 解绑：要求本地工作空闲并收口在途请求后交接。原 cc2api 账号保留 ID、配置和管理能力，暂停该号所有上游活动，包括模型、count_tokens、预热、额度、遥测及 OAuth 刷新；v3 本地获得完整凭据并独立运行。
- O3 重绑：核对原账号、设备和目标占用，按明确所有权交接当前凭据，临期时由当前所有者按需刷新。交接确认后原 cc2api 账号接管刷新，v3 运行 HOME 恢复 AT-only。正常情况无需重新登录，不新建替代账号。
- O4 关联重授权：维持原绑定，在临时目录登录并核对身份；维护期间统一阻止新上游请求和自动刷新，新凭据确认导入原 cc2api 记录并同步后恢复原所有者。失败或取消不主动以旧副本覆盖已提交凭据。
- O5 故障恢复：对响应丢失、部分落盘、服务重启和迟到回包提供可继续的结果；无法确认远端是否提交时保留凭据与维护状态，先查回执再决定下一步。
- O6 保留与兼容：账号/环境/设备 ID、HOME、缓存、历史会话、项目事实、RPM、并发、优先级、代理及既有额度状态保持；只有明确的认证失效停用可按原规则恢复，人工/封禁/限流状态不擅自解除。
- O7 旧记录：新建、当前已关联、首次关联既有目标、历史已解绑、远端已删除及真正独立账号分别处理；来源无法证明时展示待核对或要求明确重授权，不用 AT 到期时间推断 RT 新旧，不因同名或邮箱相同就改写无关账号。
- O8 可观察：管理端可区分凭据由谁管理、已解绑暂停、交接中、重授权中和待对账，错误提供可执行的恢复入口，不展示令牌或内部服务秘密。

## Acceptance Criteria

- [x] OA1：同账号并发的本地刷新、API、预热、手工额度查询和导入只服从当前所有者；解绑后 cc2api 对该号的上游连接数为零，其他账号正常，对应 O1/O2。
- [x] OA2：解绑期间模拟多次本地凭据轮换，重绑后原远端 ID 持有最后一次已确认交接的凭据，运行 HOME 不含 RT，原配置/缓存/会话均保留，对应 O3/O6。
- [x] OA3：已关联账号重授权成功仍为原 ID；错误账号、缺失身份或环境代次变化均不覆盖原凭据；人工停用和限流保持，对应 O4/O6。
- [x] OA4：在每个持久化边界注入超时、断线、写入失败和重启，结果不明时不放开门禁；同操作重试不重复轮换或回滚凭据，对应 O1/O5。
- [x] OA5：当前绑定账号无感兼容；历史解绑来源不明时准确提示并保留数据；远端已删除允许显式本地收口但不把新目标缺失当作成功，对应 O7。
- [x] OA6：SQLite/PostgreSQL 的新增持久状态及回执语义一致；状态展示不泄露 AT、RT、授权码、内部令牌或真实身份映射，对应 O1/O5/O8。
- [x] OA7：隔离验证使用真实调度、HTTP、两个数据库、容器和本地合成上游，分别覆盖解绑→独立刷新→重绑、关联重授权与中断恢复；不以单测替身冒充真实 OAuth 验收，对应 O1–O8。

## Non-Goals

- 不采用两端独立刷新或按过期时间择新；不批量重新授权、不替换设备或强行中断用户工作。
- 不更改套餐、请求评分、平滑发送和普通配置热更新的现有产品语义。
- 不实现迭代导航合并；该交付归子任务 B。
