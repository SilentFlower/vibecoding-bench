# V3：凭据交接与工程迭代入口整合

## Goal

让账号在解绑、长期独立运行、重新关联及重授权后保持明确的凭据归属，并把两种工程迭代收拢到一个导航入口。

## Background

- 来源：本轮对话中，用户要求将已讨论的几项工作一起创建 Trellis task；此前磁盘清理已明确搁置。
- 凭据方案按本轮讨论的“解绑后暂停该 cc2api 账号的上游活动，由 v3 本地接管；重新关联时交回”规划。暂停只针对该账号，保留管理操作及受控交接。
- 导航方案已得到“可以”的明确回应：顶层为“工程迭代”，内部切换“项目迭代 / 养号迭代”。
- 当前代码事实及文件定位分别记录在两个子任务的 research/code-map.md，两个子任务已实现、验证并提交，父任务继续联合交付。

## Child Tasks

| 子任务 | 所有权边界 | 对应需求 |
| --- | --- | --- |
| 11-03-v3-oauth-ownership-handoff | cc2api、orchestrator 的凭据归属、解绑重绑、关联重授权及必要状态展示 | P1、P3 |
| 11-03-v3-iteration-console-tabs | WebUI 统一入口、页内模式、账号选择、旧链接和实时订阅生命周期 | P2 |

两个子任务可独立验证。实施顺序为凭据交接、迭代导航，最后按同批正式镜像联合验收；树结构本身不表达技术依赖。

## Requirements

- P1：一个账号始终只有一个被允许刷新凭据的所有者；解绑、重绑和关联重授权有明确的交接结果与中断恢复。
- P2：在“工程迭代”页面内切换两个空间，保留所选账号；切换页面只影响查看，两个空间的后台工作、计划和历史保持独立。
- P3：正常交接保留账号 ID、设备、固定环境、HOME、缓存、历史会话和既有账号策略；老记录不凭猜测覆盖凭据。
- P4：两个子任务分别通过适当验证后交付同批新版，沿用当前 US 部署参数和现有发布 SOP。

## Acceptance Criteria

- [x] PA1：子任务 A 的凭据所有权、全入口暂停、长期解绑后重绑、关联重授权及故障恢复场景全部通过，对应 P1/P3。
- [x] PA2：子任务 B 的统一导航、账号保留、独立空间、旧链接与订阅清理场景全部通过，对应 P2。
- [x] PA3：联合使用时，从两个迭代空间操作同一账号，维护状态一致可见；查看或切换页面不会启动、停止任务或绕过凭据门禁，对应 P1/P2。
- [x] PA4：交付记录能关联父仓库、cc2api 子模块、同批镜像与 US 部署验收；保留当前环境和账号数据，对应 P3/P4。

## Non-Goals

- 不继续磁盘清理、不重做评分/RPM 平滑发送、不改套餐分级或重新迁移账号。
- 不把“解绑后两边继续使用、cc2api 保留凭据托管”作为本轮模式。
- 不合并两个迭代空间的数据、计划、项目池、完成事实或工作目录。
- 不删除历史记录、不自动更换设备身份、不批量重新登录、不处理无关应用。
