# Brief — 原生转发 401 时复用已更新的 OAuth 凭据

## Goal

- 同账号在请求期间更新了 OAuth 凭据时，让网关有机会在内部恢复这笔原生 Messages 请求。

## Scope

- 原生 Messages 的上游认证 401、同账号单次重试及两次实际发送的诊断。

## Non-Goals

- 主动换票、轮询等票、因 401 停用账号或换号。
- 数据库结构、配置、界面、sender 协议、发布及真实账号模型调用。

## Technical Overview

- 完整收到真实上游 HTTP 401，且错误类型为 `authentication_error`，才触发一次只读检查。
- **重发硬门槛：同一账号当前持久化的 token 必须与首次实际发送的 token 不同，且仍有效。原请求必须还有时间预算。** 全部满足时才在同账号重发一次，沿用原生版本、会话和请求策略。

## Context & Decisions

- 线上样本在请求提交后记录了凭据刷新，原生转发只发送了一次。上游撤销原因未验证。
- 本轮只复用已更新的凭据。未命中恢复条件时保留首次 401，第二次 401 直接返回。认证恢复与签名修复不叠加，原有 429 决策继续生效。

## Risks

- 必须以实际提交的 token 和上游尝试为准，核对凭据归属与准入，避免在发送状态不明时重放。

## Acceptance

- 合成上游先拒绝旧 token、再接受新 token：调用方收到 200，诊断记录两次发送及重试原因。
- 裸 401、其他错误类型、token 没变、无有效新凭据、状态不明或预算不足时，只发送一次，并保留首次响应。再次 401 时最多发送两次。
- 原有签名修复与 429 独立场景通过定向回归。

## Next Step

- 启动任务，在网关原生重试入口实现凭据复用及定向验证。
