# 技术设计

## 设计目标

将 Claude Code 2.1.257 升级拆成协议、运行时、首次发布和 `cli-bg` 状态分类兼容四个
可独立检查的子任务，避免在同一次改动中混合抓包推断、代码实现和生产操作。父任务只
维护跨任务契约与最终验收。

## 任务依赖

```text
cc2api 2.1.257 协议适配 ─┐
                         ├─> 镜像发布、线上迁移与验证 ─> 父任务集成验收
vibecoding-bench 运行同步 ─┘
首次发布后的 cli-bg 429 证据 ─> 状态分类兼容与再次发布 ─┘
```

- 协议子任务和运行时子任务可以独立实现与检查。
- 发布子任务必须等待两个实现子任务均通过 Check-All，且目标提交已经推送。
- `cli-bg` 状态分类兼容子任务基于首次发布后的 429 证据独立实施，完成代码检查后再次
  发布 cc2api，并通过账号代理链路验收。
- 发布失败不回滚已经验证通过的源代码；按各服务旧镜像和数据库备份分别恢复。

## 跨任务契约

- 版本身份统一为 `2.1.257`，build time 为 `2026-09-01T05:28:54Z`，Stainless package
  为 `0.112.1`，Node runtime 为 `v26.3.0`，Bun UA 为 `1.4.1`。
- Fable 5 与 Fable 5.1 是两个模型 ID，分别建模；family 配额共享，但请求 beta、
  fallback、thinking 和 CCH 输入不能混用。
- `[1m]` 本轮只记录官方 2.1.257 的可观察行为：Fable 5.1 实际 message 请求不带
  `context-1m-2025-08-07`。不迁移账号 `allow_1m_models`，不在网关主动注入该 token。
- 原始抓包和生产凭据不进入 Git；任务文档只保存脱敏统计、模型结构、hash 结论和
  upstream request ID。
- 生产发布必须保留管理员自定义 settings，特别是 system-role 模型列表和账号 1M
  allowlist，不得通过覆盖默认值丢失线上配置。

## 集成验收

父任务在四个子任务完成后核对：

1. cc2api 内置默认画像、allowed range、账号 canonical env 与设置页均为 2.1.257。
2. vibecoding-bench 所有新建 worker 类型在无页面覆盖时实际运行 2.1.257。
3. 线上 cc2api 和 vibecoding-bench 使用本次构建镜像，健康检查和版本分布正确。
4. Fable 5.1 system role、共享配额与 CCH 命中正常，首字节卡死日志能与 request ID
   关联，但不会伪造 SSE 数据。
5. 账号 `allow_1m_models` 保持部署前值，Fable `[1m]` 后续抓包另行立项。
6. `cli-bg` 状态分类默认放行，命中后只绕过正文形状改写，并经 `proxy_url` 非空账号
   的 cc2api 代理链路验证不再集中返回 429。

## 风险与回滚

- 抓包类型多且存在同版本不同模型子画像，最大风险是用版本级常量覆盖模型级差异。
- 默认设置迁移可能覆盖线上自定义值，必须使用条件迁移或追加式迁移并在部署前后比对。
- 生产发布涉及两个独立镜像体系，必须分别记录旧 image ID / tag 与 DB 备份位置。
- Anthropic 上游零首字节卡死无法由本项目消除；回滚只恢复本地行为，不保证上游恢复。
