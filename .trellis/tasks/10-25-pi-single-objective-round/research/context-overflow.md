# 故障复盘：Pi 上下文超限与长期输入膨胀

## 1. 根因分类

- 隐式假设：把“启用 SDK 自动压缩”当成每次请求前都有保护。实际锁定的 0.75.1 在连续工具循环之间不检查；恢复时最后 aborted 消息的零用量又绕过阈值。
- 跨层契约：控制端每次提供整池目标及整项目材料，SDK 保存全部工具结果，模型恢复和降级继续沿用历史，输入增长没有独立边界。
- 测试缺口：原故障测试使用小型历史，不能证明真实请求体在持续工具流和旧会话恢复时有界。
- 生产证据：上游明确返回最大 1,048,576 token 的上下文错误；此前成功消息 usage.totalTokens 为 995,718，包含大量缓存输入。该事实来自本次只读排查，不是根据页面通用错误猜测。

## 2. 先前机制的局限

- 内容过滤的同模型重试和备用模型降级解决不同故障，不能缩小原有请求体。
- 单目标收尾可以阻止继续开启下一目标，但同一目标的工具流及已经膨胀的旧会话仍需独立治理。
- 直接调用模型为百万级历史生成摘要，仍会先发送同一个超长输入，不能作为恢复前提。

## 4. 同类问题扩展

- 项目迭代和工程养号共用 ProjectsService／Pi host，统一适用；两个命名空间、各自计划和整个工程池轮次不混用。
- 单次结果或固定指南也可能过大。分页允许调小 limit；预览明确声明不完整；固定用户输入不静默截断，触发阈值后归纳旧交互，无法降低用量时保留原文报错。
- 混合工具批次必须保留调用／回执配对；只按最近若干条消息切片会留下孤立回执。
- 旧通用错误不能直接解锁。绑定原错误事件的已核实诊断仅开放既有显式启动路径，身份、未知输入、合同和账号门禁继续优先。
