# 技术设计

## 所有权交接

绑定期间 cc2api 负责刷新，管理 profile 保存其镜像，固定 HOME 与 runtime/access 保持 AT-only。解除绑定是所有权转换：空闲证明、停止原发送器之后，在既有 owner → profile → environment 的保护范围内，明确交接管理侧完整凭据，不能以“HOME 文件已经存在”决定来源。

未绑定账号运行后 HOME 才是本地轮换权威。不能在每次 ensure 时无条件用 profile 覆盖 HOME。补齐逻辑必须限定明确的 AT-only 缺失状态与可核对来源，保留已轮换的 HOME、新增未知字段及现有原子写入权限。

## 收尾保护

梳理 AccountRuntime.sync_credentials、owner_transition、release、ensure、后台 OAuth 刷新 finally、维护和启动 reconcile。集中使用现有原子 JSON 工具，在同一所有权锁序内处理完整凭据；不增加第二条 OAuth 刷新链。

在允许本地 HOME 回写 profile 之前校验凭据结构与完整性，AT-only 或损坏副本不能降级覆盖完整管理凭据。无法交接的异常要保持可恢复状态，不能仅写 DB 后报成功；覆盖文件故障、重复调用、服务重启的收口行为。正常远端与缺失远端的占用门禁、改绑严格校验保持。

解绑的数据库与文件之间用 root 私有 `runtime/credential-handoff.json` 记录交接意图，仅保存 schema、两端账号/环境 ID 与管理文件 SHA256，不保存 AT/RT。停止旧实例并校验资料后、DB 改绑前落盘；全部发布完成才删除。部分失败、重启或维护对账不能绕过该记录；重复显式解绑重新验证原账号及文件摘要后续办，来源变化则拒绝。未完成交接禁止普通唤醒和再次改绑。

完整凭据交接仅属于保留账号的解绑，显式删除本地账号继续只做原占用/停止/删除收口；不能新增“必须先修复失效 RT 才能删除账号”的前置条件。

## 验证机制

修改现有“解绑保留 HOME 原值”的测试预期：HOME 目录和身份保持，但凭据内容按新的本地所有权补齐 RT。构造与生产一致的初始状态，不再让 profile/HOME 都有 RT 的夹具掩盖缺陷。

单测实际驱动 claim/sync/release，模拟刷新失败但不调用真实上游；覆盖本地 RT 轮换、缺失/坏 JSON、写文件故障、绑定镜像及重启恢复。扩展现有真实删除后解绑夹具，走页面、正式接口、两库和文件，加入作业收尾后再次创建，保持本地代理、随机部署和旧哨兵保护。

## 线上恢复与部署

沿用 v3 同批控制/账号镜像与固定发布清单，保留既有管理密码覆盖、RAM/swap 和其他部署。停止自有服务后先备份最新现场，再处理明确受损的账号。恢复只从 `/opt/vibebench-v3-us/backups/pre-deleted-unbind-ci-38831776288-1/data` 中同账号的凭据补回丢失 RT；反向核对四份顶层配置、当前/备份 AT 与 expiry、绑定为空、无活动执行或未确认授权。守卫不成立则停止，不猜测刷新令牌。

补回 RT 不等于该 RT 未被上游撤销。生产不自动重建账号、不发送 OAuth 或模型探测；本地完整性和身份验证完成后明确报告实际限制，真实创建或重授权由用户显式选择。

## 风险与回退

跨文件交接可能中断，必须验证不报假成功、重试不回滚新凭据。备份令牌可能已失效，不能以文件存在证明可用。回退只按兼容批次切换镜像，不回滚数据库或覆盖新凭据。
