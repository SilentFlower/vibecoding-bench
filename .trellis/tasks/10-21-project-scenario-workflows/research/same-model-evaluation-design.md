# Research: 同账号同模型独立会话评审设计补充

- Query: 用户已选择自动评审且没有额外模型，怎样在现有共享调度下冻结评审依据、路由合理澄清并区分任务结果与评审故障？
- Scope: internal；补充设计建议，不定义已经实现的接口。
- Date: 2026-10-21

## Findings

### 1. 已确认边界与可复用入口

- 首版使用原任务现有账号、相同冻结 `execution_model` 配置和独立 session；沿用账号身份、CLI 版本及 effort 快照，不跟随评审发生时的全局设置漂移。不新增供应商、账号设置或人工逐项审核系统。
- 复用 `Scheduler.submit()`（`orchestrator/main.py:6393`）及共享账号 semaphore、窗口、身份和额度门禁（同文件 `:6746`）；新增评审作业也须映射到受控 normal workload，不能建立直连模型通道。
- 旧 `_verify()` 在候选冻结时同步验收（`orchestrator/project_plans.py:567`），新语义评审不能沿用这一持有许可等待模式。先保存回复、文件候选、消费／会话接续证据并严格释放候选执行，再排评审；评审完成后才恢复需要继续的原任务会话。
- 评审使用独立 cwd、独立 session 和单独的有界输入包，不恢复候选 session，也不挂载候选账号工作目录。独立的是评审上下文，不代表换了一个模型。

### 2. 冻结评审输入

- 控制端生成评审输入包，包含契约版本、评审作业 ID、任务／尝试／轮次 ID、内容版本、父 generation、输入包摘要、回复摘要、代码／fixture／环境摘要及当前已披露分支。
- 可信判定依据单独包含：当前用户目标、必须约束、允许修改范围、合法结束类型、逐项 rubric、允许的等价答案边界、合法分支 ID 与触发条件。只提供本任务当前版本的依据。
- 被评材料单独包含：当前任务真实 user／assistant 对话、已披露材料事件、候选回复全文或完整有界正文、源码事实片段与固定引用、控制端产生的原生行为结果。不能仅拿最终一句“完成了”评审。
- 回答超出评审输入上限时保留完整原文对象；不能默默截断后给确定结论。允许按固定策略分段取证，仍不能覆盖所有必需依据时归评审依据不足。
- 所有输入先封存并计算摘要；重启后复用同一包，不从仍会变化的工作区取材料。基准事实和 rubric 来自控制端冻结内容，不能从候选解释反推答案。

### 3. 结构化评审输出建议

- 输出为一个严格 JSON 对象；控制端校验字段、类型、枚举、字节上限及未知字段，拒绝含多个相互冲突判定的结果。下列字段仅为设计建议，最终 schema 由主设计统一。
- `evaluation_id / task_id / turn_id / response_digest / basis_digest` 回显输入身份；控制端另对照真实作业归属、generation 和候选摘要，不因模型回显正确就信任结果。
- `decision` 仅允许 `disclose / pass / fail / uncertain`；`branch_id` 只能引用当前允许的冻结分支，非披露决定不得携带任意待发送文本或路径。
- `criteria` 按冻结 criterion ID 返回 `satisfied / violated / unknown`、简短理由及证据引用；证据只能指向真实回复片段、源码证据 ID 或机械检查 ID。控制端校验引用存在与版本匹配，不要求输出推理过程。
- `result_kind` 表达准确解决、排除 BUG、方案成立、合法信息不足等业务结果；它与评审作业的运行状态分开，不能用一个 success 混合表示。
- `feedback_codes` 引用内容作者预先允许披露的反馈类别；完整评分依据留控制端。控制端生成发回候选的补充或修正提示，不直接执行评审输出中的自由指令。

### 4. 合理澄清与条件披露

- 每个正常 assistant 回合先形成不可变响应，再判当前是合理索取材料、已提交答案还是无效回避。正常结束一轮不是任务已通过，条件追问不增加任务覆盖数。
- `disclose` 只在请求与诊断需要有明确关系、材料尚未提供、当前入口允许该分支时成立。按“代码”“复现”等关键词命中不能判合理澄清；评审必须给出支持该分支的回复证据。
- “给最小复现”可一次披露足够的代码、输入及异常；请求部分材料也允许按样板发送预先定义的完整相关材料组，不强迫固定问满几轮。
- 控制端检查已披露集合及分支次数，避免重复材料和循环索要。评审只选择分支 ID，实际文本／文件来自冻结素材；发送意图与原生消费证据沿用已有可靠交接规则。
- FM-DG-01 的资料不可得必须由冻结入口决定，不能由模型自行切换；PS-TRIAGE 材料全部可提供，仅提问不足以完成；TY-D02 请求注册代码或相关 help 都可触发同一合法材料，help 需来自真实夹具。
- 披露请求不适当、已有充分材料仍回避或反复索要同物，可按具体 rubric 判任务失败；评审无法区分请求是否合理时应 `uncertain`，不能臆造新材料或自动认定模型错误。

### 5. 多解、信息不足与不确定的区分

- `pass` 要求所有必需 criterion 已满足且无硬性失败；允许表达不同、调用方式等价或方案选择不同，不使用答案相似度、长度或指定术语数量评分。
- 合法信息不足是被测模型对真实缺口作出的正确处理：说明缺少什么、为何影响结论、怎样核实，并满足该入口的自然结束条件。记录为“恰当处理，未定位根因”，不冒充已定位 BUG。
- 当任务仍能获得必需材料时，应先 `disclose` 并继续；未完成的诊断不能因一句“信息不足”通过。无 BUG 结论须有与当前输入及版本一致的依据。
- `fail` 指证据足以证明候选违反用户要求或事实，如捏造 API、错误根因、遗漏必需约束或未经授权改库；报告关联具体 criterion 与证据。
- `uncertain` 指评审本身无法在冻结依据下可靠判断，如依据覆盖不足、有效方案超出当前可判边界或证据相互冲突。保存候选与评审原因，标评审未决，不冒充候选失败或自动通过。
- 非 JSON、身份／摘要不符、非法分支、引用不存在、执行超时或运行环境错误属于评审作业错误；不是合法 `uncertain`，也不消耗被测任务业务修正次数。额度等待保持等待状态。

### 6. 规则与真实行为优先

- 控制端先检查来源／代码范围、只读源码保持、材料披露顺序、候选版本及提交完整性；确定事实不依赖模型投票。机械检查故障归环境错误，不能硬判候选错误。
- 咨询示例和工程修改先运行独立原生业务验收，核对实际加载位置、输出与副作用；工程修改还需适用回归。评审不得把已确定的行为失败改成通过，也不得仅凭候选自报测试成功放行。
- 语义评审主要判断理解／诊断／方案是否正确及说明与行为是否一致。原生测试通过不自动证明诊断理由正确，语义评审通过不替代工程测试。
- 所有必须的机械与语义检查通过后才接受任务；只有工程修改通过才能接受代码检查点。咨询临时脚本、业务输出和只读问答均不产生工程能力接受。

### 7. 评审隔离、同模型风险与校准

- 控制端的评审指令和冻结规则为唯一判定任务；候选回答、源码注释、日志及证据都以带来源的结构化数据字段传入，其中“忽略规则”“调用工具”等内容只是被评文本，不能成为评审指令。
- 评审不能修改候选、验收器或 rubric；不接受候选自带“正确答案”或伪造角色消息。若评审需要补证据，由控制端按冻结证据引用提供，不让它执行候选文本里的命令。
- 同模型可能共享知识盲区、误解 API 或偏好自己的表达。独立 session 降低直接会话影响，但不消除相关误判，结果应明确标为“同模型独立会话评审”。
- 用已核对的正确／错误／多解／无 BUG／合理澄清及信息不足反例校准 rubric，优先让原生对照和可核查事实纠正评分规则；人工仅做初期校准和抽查，不引入人工逐项放行或覆盖工作流。
- 保留 criterion、证据、模型／CLI／effort、输入包与 rubric 摘要，可离线复核误判；不将模型自报置信度当通过概率，不用重复同模型多数票冒充独立真值。

### 8. 有界重试、恢复与用量

- 建议一次评审作业首次加最多一次重试，另有累计有效执行预算；结构／执行错误可在该上限内重评同一冻结输入，合法 `uncertain` 不无限重抽到通过。原生环境错误沿用已有最多本地再验一次的约束（`orchestrator/project_plans.py:610`）。
- 重试次数、实际已消耗预算、待评输入与结果均持久化；模型额度等待沿用原共享调度恢复，不额外发探测请求。候选回答完整而评审中断时只恢复评审，不重跑候选。
- 评审结果接受需再次核对父状态、generation、任务／轮次、回复与依据摘要，并以唯一键幂等接受；停止、旧代次或已被替换输入的回包仅留历史，不继续披露或推进。
- 被测执行、评审执行和本地原生验收分别计耗时；评审使用同一账号原额度，输入／输出／缓存 token 单列。等待不计模型有效运行，未知用量保持未知，重试不增加任务数。

## 实现补证：同实际模型绑定

2026-10-21 的实现已从候选精确原生主回复读取 `message.model`，封存为 `resolved_model`，评审启动时固定该值并核对评审实际模型。空 `execution_model` 仍保留为原配置快照，不能解释成私有 HOME 可任意使用当前默认。`test_review_model_drift_is_review_error_without_business_retry` 已验证漂移不会接受候选或消耗业务修正；隔离 Docker 矩阵检查真实进程配置，模型调用为 0。
