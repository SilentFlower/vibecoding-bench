# Research: 同账号同模型自动评审的最小 API 与页面契约

- Query: 内容 schema 2／执行 policy 3 的首批三项目，如何最小改造 API／UI，支持同模型独立评审、恢复、累计预算与历史读取。
- Scope: internal
- Date: 2026-10-21

## Findings

### 1. 已确认边界与现有入口

- 用户已选自动独立评审，复用当前账号和冻结的同一模型配置；独立的是评审会话与依据，不宣称跨模型独立。人工仅离线校准／抽查，不建设逐项审核或覆盖自动结论 UI。（本任务 `prd.md` 的 R3、R9、AC9）
- 内容 schema 2 与执行 policy 3 是本次设计目标，当前正式接口尚不支持；旧内容 schema 1、policy 1／2 按旧语义保留。首批仅三项目，可变任务数，不等待 100 项或每仓 20 项。
- 当前创建 DTO 只有账号／项目与工程计划参数，严格 `extra="forbid"`；新增策略必须同步 DTO、管理器归一、持久化及表单，不能靠前端任意加字段。（`orchestrator/main.py:10136`）
- 现有项目公开资源已覆盖 catalog、batch、instance、attempt artifact／file、usage 和 SSE，可优先扩展其版本化投影，不必先增加一整套顶层资源。（`orchestrator/main.py:10174`）

### 2. 最小读取与创建契约建议

以下描述所需语义，字段名和路径是设计输入，不冒充现存 DTO 或最终 schema。

| 入口 | 最小契约 |
| --- | --- |
| 目录摘要／详情 | 返回内容版本、可执行项目、场景数、任务数、任务类型和就绪状态；公开当前应披露的用户目标，隐藏参考与评审材料。研究数与可执行数分开。 |
| 创建批次 | 少量就绪项目即可创建；所选项目可有不同任务数；policy 3 明确任务累计预算及评审预算来源。继续严格拒绝空／重复／未知选择及非法类型。 |
| 批次／实例 | 同时返回运行生命周期、场景／任务结果分布、当前执行与评审排队、受阻原因；不能继续以单一 `next_step_index` 推断全部任务结果。 |
| 任务／尝试详情 | 稳定任务 ID、场景 ID、类型、适用源码／输入版本、回答或候选摘要、执行 Run、独立评审 Run／记录及结果；重试不新增任务覆盖数。 |
| 成果详情 | 固定回答、验证／评审结论及理由、依据版本；工程任务另列候选与已接受 checkpoint。问答通过没有新代码版本，也可有完整成果。 |
| 用量 | 按任务、类型及执行／评审角色累计，附可信记录覆盖与未知标记；提供累计有效运行时间、次数和剩余预算。 |

- `timeout_sec` 当前是单次 CLI 计划超时，新任务总预算不能静默复用其含义；旧 API 默认与历史 policy 保持原定义。（`orchestrator/main.py:10145`）
- 当前策略上限取 `len(manifest['steps'])`，页面也以 `step_count` 设置计划／轮换上限；新版本需要按真实可执行任务及依赖验证，不再以 20 为准入门槛。（`orchestrator/project_iteration.py:153`；`webui/app.js:96`）

### 3. 状态与恢复在页面中的最小表达

| 情况 | 展示与推进语义 |
| --- | --- |
| 候选已冻结、评审排队 | 显示“待评审”和共享容量等待原因；候选已释放，不能为等评审继续占住 CLI。 |
| 评审执行中 | 展示独立评审记录及用量角色；不把它算作受评任务的又一次作答。 |
| 任务通过 | 按类型展示结果；只读任务可通过且 checkpoint 不变；工程任务另确认代码接受。 |
| 评审不确定／评审异常 | 明示未判定与原因，不能写成受评模型回答错误或自动投放业务修正；按冻结的评审重试预算处理。 |
| 受评执行超时待续 | 旧 Run 保留 timeout，同任务／同场景 session 跨新 Run 接续；显示已用／剩余累计预算及恢复资格。 |
| 回答完整、验收未结束 | 只继续程序验证或独立评审，禁止重发用户首问、重新生成同一回答或重计已封存用量。 |
| 信息待补 | 显示当前缺少什么、可提供什么；若任务目标仅为合理澄清并已满足，可直接验收，不一律挂起。 |
| 任务预算耗尽／依赖受阻 | 分别显示未完成原因及依赖任务；停止该任务自动继续，独立任务仍可推进。 |
| 当前运行收口 | 展示通过、失败、未判定、耗尽及受阻分布；“执行结束”不等同“任务全通过”。 |

- 页面应按批次／场景／任务／执行／评审各自状态域翻译；当前 `completed` 统一为“路线完成”、`timeout` 仅显示“超时”，不足以表达上述状态。（`webui/app.js:61`）
- 页面使用服务端恢复资格与下一动作，不由浏览器猜是否续作答或仅续验收。首版可以自动推进，必要时只展示原因，不需要人工逐项通过／覆盖按钮。
- 普通 Run 的项目续聊禁令保留；同场景跨 Run 接续经项目控制链，不能打开通用续聊绕过任务、分支及预算。（`webui/app.js:2676`；`orchestrator/main.py:11381`）

### 4. 容量、用量与预算

- 批次调度摘要至少区分候选执行中、评审执行中及评审排队，总在途容量仍与普通 Tasks 共用账号上限；先释放候选后调度评审，单账号容量为 1 也可完成闭环。评审等待不应被页面提示为“模型作答中”。
- 受评作答与评审的 token／请求／有效耗时分别累计，同时可展示总消耗；同模型并不意味着可以把评审成本并入最终一轮输出。评审预算耗尽也不应伪造受评任务错误。
- 当前输入合计包含普通输入、缓存写、缓存读，公开统计尚无三项分拆；必须从真实 usage 保留分项，不能由合计倒推。（`orchestrator/main.py:323`；`orchestrator/project_iteration.py:507`）
- 当前 `/usage` 的 `complete` 只表示各尝试有用量证据；新 UI 应命名为记录完整性，不能当成任务完成率。部分已知显示已知小计及缺失数，全未知显示未知，不显示零。（`orchestrator/main.py:10248`；`webui/app.js:355`）
- 剩余预算由服务端跨 Run 持久累计；重启、额度等待与评审排队不能重置任务预算。有效运行时间不直接等同 Run 墙钟时间，具体计时边界归运行时设计。

### 5. 历史、Cookie、SSE 与最小交付验证

- 当前库初始化失败会让管理器为空，历史 API 和项目 Run 文件树也返回 503；必须让历史 reader 独立于当前 catalog 准入。页面将目录与批次同置 `Promise.all` 的加载方式也需拆开，目录错误不能遮住已保存历史。（`orchestrator/main.py:7843`、`:10164`、`:11071`；`webui/app.js:108`）
- 旧 frozen manifest、release、Run、固定回答／报告和对象按所属版本读取；对象缺失显示缺失，不用当前目录替代，不恢复退役生成库。
- 复用项目资源前缀的新读取／动作可沿现有管理桥；新增顶层前缀才需加白名单。Cookie／Origin 校验及内部路径拒绝不变；不新增鉴权豁免。（`cc2api/src/service/runtime_bridge.rs:152`、`:177`、`:205`）
- SSE 继续推送与普通读取一致的公开投影，离开页签关闭流，保留展开／滚动；不要在 SSE 回调再查用量或评审。长报告按需读取，避免每两秒重复整份答案。（`webui/app.js:388`、`:443`）
- 最小验收应覆盖：三项目可变数量建批次、只读通过但代码不变、容量 1 的评审闭环、仅续验收、同场景跨 Run 续作答、未知用量、剩余预算跨重启、评审不确定不算业务失败、空库历史可读；明暗主题／390px／XSS 和旧 policy 1／2 继续回归。
