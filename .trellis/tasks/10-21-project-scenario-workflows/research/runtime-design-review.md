# Research: 自动评审执行与恢复的窄范围设计复核

- Query: 复核同账号／同模型自动评审、版本兼容、场景会话、任务预算及候选释放交接的竞态。
- Scope: internal；仅依据既有研究与最新 PRD，不重复扫描源码，不定义最终数据库 schema 或新增 UX。
- Date: 2026-10-21

## Findings

### 1. 已确认选择与版本边界

- 依据最新 `prd.md` 的 R3、R7、R10、AC9，采用现有同账号／同模型的独立评审会话；人工只作校准与抽查，不新增人工覆盖流程。
- 新内容使用 schema 2，新执行策略使用 `policy.schema=3`；内容 schema 与执行策略 schema 各自校验，不能把两个数字当作同一版本。
- 旧内容 schema 1、无策略 schema 的旧单步批次、旧 `policy.schema=2` 同会话计划继续原 reader／调度语义，不追溯补造任务或成本。
- 新候选沿用 `run_kind='project_iteration'`，通过冻结策略版本分流；独立评审新增 `project_review`，在 `_execution_workload` 映射到 `normal`。
- 同名 run_kind 不足以识别新执行：所有项目上下文、恢复、成果及输入发布入口都必须解析内容／执行版本后路由。
- 历史读取应独立于当前正式 catalog 是否就绪；不能因新内容校验失败导致旧发布、旧会话与成果一并 503。

### 2. 分离的持久职责

- 业务任务保存稳定 ID、类型、冻结输入版本和最终结果；对话轮次保存材料披露、真实输入消费与响应证据。
- 业务尝试保存首次执行及最多两次继续／修正；额度恢复和执行基础设施恢复属于同尝试的新执行片段。
- 执行片段保存 Run、source／quota 代次、进程／启动身份及时间区间；不能用尝试行数量代替实际模型次数。
- 验收作业绑定一个不可变候选、rubric／环境版本和评审执行；代码检查点只由获授权修改且行为验证通过的任务接受。
- 独立场景使用独立工作区和 session，同场景内的任务保留原 session；输入声明依赖前次代码时只绑定已接受版本。
- 同场景同时至多一个候选写入执行；待评审期间同场景后继不能提前修改持续工作区，其他独立场景可继续。

### 3. 回答封存、释放与评审交接

1. 原生最终回复到达后，核对输入消费、响应父链、阶段／source／generation，定向冻结完整作业树。
2. 先持久化回答字节／摘要、源码候选、材料披露历史、输入版本及验收作业归属，再发出停止／释放请求。
3. 只有同代严格释放证明、执行锁和 CLI holder 均收口后，验收作业才能提交共享 `Scheduler`；单有 Run 终态不足以开始评审。
4. 评审使用独立 session／工作区和冻结输入；同一账号／模型指运行配置复用，不允许继承候选 session、候选 prompt hooks 或可写项目设置。
5. 评审结构化输出经控制端解析并核对证据；明确业务不合格才允许生成有限修正，解析错误／依据不足属于评审受阻。
6. 接受决定与待发送动作在同一事务落盘；评审自身严格释放后，按原输入消费证据 resume 候选 session，投放当前分支材料、下一任务或可公开修正反馈。
- 评审不把完整 rubric、隐藏样例或原始评审正文回灌候选；需要显式生成反馈投影，并记录它实际披露的摘要。
- 机械行为验收和语义评审是不同作业类型；机械验收失败不应被模型赞成覆盖，代码检查点接受需汇合规定的必要结果。

### 4. 默认预算与持久时间片段

| 技术建议默认值 | 机制 |
| --- | --- |
| 候选单次有效执行 600 秒 | 每次启动领取 `min(600, 任务剩余预算)`；不是整场景／整 Run 的统一重置时钟。 |
| 每任务累计有效工作 1,800 秒 | 跨轮次、三个业务尝试、Run 和 quota 代次累计；先碰次数或时间上限即停止业务继续。 |
| 单次评审累计有效执行 180 秒 | quota／基础设施恢复沿用该次评审剩余预算，不重新给满 180 秒。 |
| 同一冻结候选最多两次评审 | 首次加一次因超时、结构错误或不确定的重评；有效明确判定不能反复重评直至变通过。 |

- 默认值写入创建时策略快照，可由合法内容档案在服务端上限内明确覆盖；后续全局设置变化不修改已执行任务余额。
- 评审成本单列，单候选评审有效时间至多 360 秒；候选 1,800 秒预算不包含评审、机械验收或排队时间。
- 计时覆盖实际解题思考与工具执行；材料等待、评审等待、quota／时段等待、共享容量和启动准备另记，不用墙钟总差扣业务预算。
- 片段绑定业务归属、Run/source、boot 身份及单调时钟基准；在输入消费、暂停／候选封存、quota 退出和释放时落高水位，并周期性持久化。
- 每次片段关闭与预算累计使用唯一片段身份／序号及 CAS，重复退出回调、恢复扫描或重复消息不能重复扣费。
- 为崩溃尾段预留本次允许预算；可核对停止时间时结算退回未用部分，不能确认时保留不确定预留而非清零再发满预算。
- 确认工作时间与不确定预留分别记录，后者不是伪造的实际耗时；无法证明安全余额时受阻，不跨 boot 直接相减 monotonic。
- token 继续按原生响应去重、片段／任务归属记录输入／输出／缓存；未知与部分已知保留，评审 token 不计入被测任务 token。

### 5. 主方案还需明确的竞态与接口

- **封存后、释放前崩溃**：恢复先定位同 source 原执行并严格收口；验收作业保持待释放，不能重新生成回答或启动第二个评审。
- **释放后、评审提交前崩溃**：持久验收作业充当投放依据；事务认领＋唯一候选／评审序号，避免两个 tick 同时提交。
- **评审提交后 ACK 丢失**：回查绑定 Run，不盲建新 Run；实际 quota 恢复沿原评审 Run／session／配置和预算。
- **评审结果晚到**：接受前复核父 generation、任务／尝试、候选摘要、rubric／输入版本和当前状态；旧结果只保留历史，不覆盖已接受／停止结果。
- **停止或暂停竞态**：`project_review` 需要父任务门禁，覆盖排队、信号量之后、准备之后、实际 exec 与 quota 恢复；不能仅映射 normal 后依赖普通 task 状态。
- **评审未释放便续候选**：必须有评审 Run 严格释放门禁；否则同账号容量 1 时仍可能死锁，容量 2 时可能长期挤占。
- **共享容量饥饿**：已就绪评审与候选补位需要明确公平调度规则；持续补候选不能让旧待评审任务永远排不到，不另开绕门禁通道。
- **同场景会话变化**：评审读取封存回答而非动态主 JSONL；候选 resume 前复核原 session 长度／消费记录和代码状态，不接纳未知人工续聊。
- **基础设施重试耗尽**：未实际投递不扣业务尝试，但需独立有界退避／停止条件；否则绕过三次业务上限仍会无限启动。
- **条件材料循环**：有限材料／轮次身份与允许转移应冻结；重复索要已披露材料不无限生成新候选／新评审次数。
- **工程验收与评审并发**：两者绑定同一快照，必要结果汇合后 CAS 接受一次；其中一项报基础设施错误不能触发业务修正或接受部分结果。
- **接口缺口**：需要统一的候选封存／严格释放、验收作业认领／结果落盘、任务决定与待发送动作、时间片段结算接口；这些是新接口需求，不是现有方法。

### 6. 依据与针对性验证

- 依据 `runtime-and-recovery.md` 第 4、5、8～12 节、`content-and-evaluation.md` 第 5、6、8 节、`shared-recovery-contracts.md` 及最新 PRD；源码定位沿用这些既有研究。
- 重点验证容量 1／2、两个候选同时待评审、交接每个落盘点崩溃、重复提交／迟到回包／父停止、仅续验收以及 quota 新代次预算不重置。
- 兼容验证涵盖旧内容 schema 1＋旧执行策略 1／2 的历史读取与开放任务，以及空新 catalog 不遮住旧成果；不以恢复退役内容通过测试。

## Caveats / Not Found

- 本文为 600／1,800／180 秒与两次评审的技术建议，未经过真实模型成本／成功率校准，不能当作产品效果保证。
- 同模型独立会话提供上下文隔离，不保证评分无偏；冻结正确／错误／多解样例及人工抽查仍需校准。
- 未改产品代码、未运行测试／模型／Git；旧研究中「评审方式待决」保留为当时事实，当前选择以最新 PRD 为准。
