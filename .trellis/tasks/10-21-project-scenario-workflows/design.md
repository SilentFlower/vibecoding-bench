# 真实项目多场景任务与恢复改造：技术设计

## 1. 目标与版本边界

实现 PRD R1–R10、AC1–AC9 的一项完整能力：数量可变的真实项目场景、自动分类验收、可恢复执行及可解释成本。首批接入已有三项目的 13 个场景／20 个任务；100 项目约 2,000 任务是后续内容池目标。

本文描述目标契约，当前落地及验证证据见 implement.md 与 research；有实现不等于已通过验收。

| 边界 | 既有版本 | 本轮新增 |
| --- | --- | --- |
| catalog／项目内容 | schema 1，线性 steps，app.py JSONL | schema 2，scenarios／tasks、原生环境和分类验收 |
| 执行策略 | 无 schema 的旧单步、policy.schema=2 同 CLI 计划 | policy.schema=3，多类型任务／评审与累计预算 |
| 候选 Run | `project_iteration` | 保留 run_kind，由冻结内容及 policy 版本分流 |
| 独立评审 Run | 无 | `project_review`，接入 normal 额度及原 Scheduler |

旧 reader、旧策略与旧发布按原语义保留，不回填问答任务、历史时间或未知 token。一个新批次的内容必须有一致的执行适配版本；混选不兼容内容明确拒绝，历史批次不重绑定当前库。

## 2. 模块职责与复用

- `project_library.py` 保留快照、对象摘要、受限路径和旧内容加载；按内容版本委托新增场景内容校验与公开投影。新 catalog 不设 100 项目／20 任务下限，就绪内容非空即可。
- 新增 `project_scenario_content.py`：schema 2 的项目／场景／任务、真实依赖、材料与验收引用校验；公开字段白名单和原生环境档案引用。
- 新增 `project_scenarios.py`：新版本表、任务选择、轮次、业务尝试、Run 绑定、材料事件、预算、候选封存、任务接受与恢复；使用原 SQLite、锁、Scheduler 和对象库，不增加消息队列。
- 新增 `project_evaluation.py`：原生验证作业、独立评审输入／结果、严格解析、受控评审调度与反馈投影；不直接连接模型供应商。
- `project_review_runtime.py` 管理私有评审容器、原所有者刷新及严格释放；`project_scenario_usage.py` 按原生来源累计用量；`project_native_regression.py` 为三仓固定全套回归控制脚本的权威来源。
- `ProjectIterationManager` 作为现有 API 门面，按冻结版本委托旧 `ProjectPlans` 或新场景执行器；历史读取与当前内容准入解耦。旧 `ProjectPlans` 的政策和结果保持。
- `main.py` 衔接请求 DTO、初始化、共享调度、父状态门禁、恢复与公开接口；`account_runtime.py`、账号 driver 及 worker 增加新版本交接、隔离评审子容器生命周期与有效时间片段。
- `webui/` 仍为原生 JS／HTML／CSS，沿现有 API、Cookie 和 SSE，不引入前端框架。

## 3. 新内容与环境契约

新 catalog 记录 schema、版本和就绪项目引用；项目保留可核对的上游 URL、完整 commit、许可／归属文件、源码摘要及环境档案。项目数量与内容池目标分开。

| 内容单元 | 必需语义 |
| --- | --- |
| 项目 | `project_key`、标题、描述、来源、许可、固定 seed、环境引用、场景清单 |
| 场景 | 稳定 `id`、业务目标、独立起始源码／应用／数据、任务展示顺序、会话策略 |
| 任务 | 稳定 `id`、`kind`、首问、已开放素材、真实依赖、允许改动范围、合法结果、轮次上限、验收引用 |
| 依赖 | 目标任务 ID、所需回答产物或已接受代码状态；回答依赖不隐含代码依赖 |
| 材料分支 | 分支 ID、语义触发条件、固定可披露素材、合法下一轮与结束类型；不接受评审临时编写材料 |
| 评测依据 | 必需事实／约束、明确失败项、等价答案边界、真实源码引用、原生用例和公开反馈码 |
| 环境 | 固定 Python／平台、运行及测试依赖制品摘要、离线准备、原生执行适配器、各类验收资源上限 |

`kind` 固定为 `understand/consult/diagnose/plan/modify`。ID 在项目内唯一，引用存在、依赖无环、分支可达；不依赖数组前缀推断完成。首版只接受已冻结材料分支，不做自由人工追加材料产品。

实际格式：场景使用 `default_entry/entries/tasks`，入口 `id/task_ids` 可带 `materials/setup`。任务依赖为 `requires=[{task_id,artifact}]`，artifact 是 answer 或 code；首版明确拒绝跨场景依赖。setup 仅含固定 source 与 app/ 内 target，入口、任务、分支分别幂等投放。环境为 `environments/<id>/profile/profile.json` 和独立 artifacts；requirements 精确锁定版本。原生 spec 为 script/args/python_paths/expected/resource_profile，工程目标另引用 regression.runner/contract。

公开任务、seed 和已披露素材与控制端隐藏评测分别存放。模型只能得到当前首问、应有业务输入与已披露内容；不能直接把含全部答案的研究 Markdown 放入候选工作区。修正反馈使用白名单投影，不回传完整 rubric、隐藏样例或原始评审包。

新内容按项目计算受限源码快照，catalog 摘要汇总项目摘要，避免把整个 100 项目库都套用单源码树上限。每份候选继续受 128 MiB／10,000 文件等既有边界约束。依赖环境、wheel 档案、安装日志与源码快照分开，不打包 venv 链接树。

首版仅提供满足三仓的显式 Python 原生适配器和固定 CLI 应用适配器：受控脚本及参数由内容端冻结，隔离容器执行，不在控制宿主运行候选命令。验收时离线，实际导入候选库或用户应用，核对加载路径。

完整原生回归与任务业务验证使用不同预算。现有 30 秒／256 MiB 不能覆盖 Typer 约 181 秒全套及 Pydantic 约 348,636 KiB 宿主峰值；新环境资源按目标镜像实测固化，不能削集合换取通过。第一阶段就绪条件包含这项实测。

## 4. 工作区、会话与代码状态

项目仍是账号／批次隔离单位；场景拥有独立工作区及候选 session。独立场景从固定基线启动，文件和会话都不继承别的场景答案或失败半成品。同场景任务接续原 session，不因正常独立评审创建全新业务上下文。

同项目同时至多一个候选写入执行，保留原项目并发约束；其他项目按共享并发真实并行。待评审场景不占 CLI，其他独立场景可以被后续选择，但不能改写待评审场景目录。

状态标识由上游 commit、库源码摘要、用户应用摘要、业务 fixture 摘要及环境档案组成。接受后的本地检查点另绑定父状态与产生它的任务，不能称为上游新 commit。

只读任务允许声明范围内的临时复现／输出，受保护源码与应用保持。咨询示例输出与文件往返不发布工程检查点；`modify` 必须验证授权范围与行为后才能接受代码。

任务首次准备输入时固定代码父状态。显式 code 依赖绑定前置任务已接受的候选摘要与作业身份，不能使用场景目录里另一失败任务的未接受修改。多个 code 依赖须能由同一已接受作业继承链覆盖，否则受阻，不自行合并；相同字节的回退不能按摘要折叠成继承关系。切换前先封存当前目录和交接意图，替换中断保留现场并拒绝猜测；同任务后续额度／超时接续只复用已准备状态，不再重置半成品。

未声明 code 依赖的新任务也从场景已接受版本准备输入；尚无代码接受时从初始基线及固定入口材料开始。其他任务的未接受临时文件／代码先封存到独立旧工作目录，不能通过新任务的输入基线绕过授权范围检查。当前任务自己的 setup 和分支材料随后幂等投放。

## 5. 持久化职责

沿用原项目发布、批次、通用 tasks／runs 和对象库；新业务状态独立建表，避免给旧 `next_step_index` 附加新语义。下列为新增表及核心归属，具体 SQL 必须逐列实现并经迁移回归。

| 新表 | 关键归属与不变量 |
| --- | --- |
| `project_scenario_instances` | 项目实例＋场景唯一；固定起点、工作区、session、当前已接受代码摘要 |
| `project_scenario_tasks` | 场景＋稳定任务 ID 唯一；类型、输入状态、结果、预算、实际尝试计数及当前阶段 |
| `project_task_attempts` | 任务＋尝试序号唯一；首次／超时继续／业务修正原因，最多三次 |
| `project_task_executions` | Run 唯一；固定任务／尝试／轮次与角色，记录该 Run 的整体执行归属 |
| `project_execution_sources` | 执行＋quota 代次＋source 唯一；逐代保留原生起止、候选及严格释放证明，不覆盖前代事实 |
| `project_task_deliveries` | 任务＋稳定阶段／材料动作唯一；pending 投递意图、consumed 原生消费位置及摘要；driver 另保留发送交接证明 |
| `project_evaluation_jobs` | 候选＋评测版本＋评审序号唯一；输入／依据摘要、机械／语义结果、评审 Run 及父代次 |
| `project_work_segments` | 执行来源＋片段序号唯一；角色、boot／单调时钟基准、已确认耗时、不确定预留及结算高水位 |
| `project_scenario_plans` | 场景内明确任务 ID 集合与通过集合；评审跨 Run 时保留逻辑计划，单场景至多一个开放计划 |

候选完整性绑定任务、尝试、阶段、最终消息、原生区间、源码／输入摘要和评测版本。候选记录先持久化，再释放执行。代码对象继续用内容寻址存储；任务接受与下一动作同事务落盘，使用父 generation、输入版本及唯一接受约束防重。

同一 Run 的 quota 恢复在 `project_execution_sources` 新增来源记录，工作片段和释放证明关联明确来源；Run 行的当前代次只用于定位，不能覆盖旧代次边界或把前代释放当成新代释放。

新增表幂等初始化，旧表 ID、索引、自增序列、发布与工作区保留。任务／评审绑定事实不能只放内存队列，所有认领都能在重启后对账。

## 6. 状态与完成语义

| 对象 | 新状态／结果语义 |
| --- | --- |
| 任务 | pending、ready、running、waiting_material、evaluating、passed、failed、exhausted、blocked、cancelled |
| 业务尝试 | 实际输入消费后开始；修正或超时继续才计下一尝试；普通澄清不增尝试 |
| 候选 | captured、waiting_release、ready_for_evaluation、evaluating、accepted／rejected／evaluation_blocked |
| 评测作业 | queued、running、quota_wait、passed／failed／uncertain／error／cancelled；与任务结果分开 |
| 业务结果 | 已解决、正确排除 BUG、可行方案、合理信息不足等；信息不足不冒充已定位根因 |

一次正常 assistant 回复只形成候选，可能需要披露材料，也可能提交最终结果。必要机械检查与适用语义条件全部满足才通过；纯问答通过只记录回答与结果。

场景按冻结入口和已选择分支的必要任务判断，未选择分支不进成功／失败分母。批次运行结束时展示通过、失败、耗尽、未判定及依赖受阻分布；不能把全部收口写成全部通过。

业务失败仍可修正时，尝试结束、任务回 ready；尝试／时间耗尽才最终 failed 或 exhausted。依赖传播只影响真实后继，同项目独立任务继续。父停止、认证／清理或输入证明故障保留原有更强阻断。

新策略保留默认并发 2、活动项目池 3、每逻辑计划 2 个任务及通过 5 个任务轮换；任务失败／耗尽或场景收口也可结束本次访问并轮换，避免失败项目长期占池。逻辑计划保存明确任务 ID，评审等待可以跨 Run，旧 schema 2 同 CLI 契约不变。

## 7. 同模型独立评审

复用候选创建时冻结的 `claude_code_version`、`claude_effort_level`、`execution_model` 和账号身份；空字符串所代表的 CLI 默认也按原快照处理。评审不探测模型清单，不新增账号或供应商，不随全局设置漂移。

空 execution_model 仍保留为空，不用后续全局设置补写。候选封存时从已核对父链的原生最终消息读取实际 model ID 并绑定回答版本，评审以该已使用的 ID 启动；评审原生实际 model 也须一致。无法确认或发生漂移时保留候选并按评审错误有限处理，不能把新私有 HOME 的默认值当作原账号默认值。此解析只读已有日志，不调用模型列表。

评审使用新 session、独立 cwd 和控制端固定输入包，不恢复候选 session，不将候选可写项目作为评审工作目录。评审包包含当前真实问题／已披露对话、回答、必要源码事实、行为验证结果、rubric 及身份摘要；候选回答和源码是被评数据，不是执行指令。输入完整性或控制包上限无法满足时明确评审受阻，不能静默截断后作确定判定。

同账号候选共用原 HOME，因此仅换 cwd／session 不满足隐藏材料隔离。采用已研究可行的**无特权评审子容器**：

- 仍由原 Scheduler、账号 semaphore 与 `AccountRuntime.claim(..., shared_cli=True)` 登记作业／租约；复用原账号 network 角色的网络命名空间及精确 account 镜像／CLI 版本，不走旧 worker／sidecar 旁路，不增加账号、网络代理或容器特权。
- 独立 PID／挂载视图、只读根及原资源限制，只挂私有 HOME、输入、driver 和日志。私有宿主根在原 CLI 的 home/projects/flows/runtime 等所有已挂载目录之外；评审 transcript、流量内容与隐藏输入不能同步回候选 HOME 或共享 flows。
- 由原凭据唯一所有者提供 AT-only 受控副本，复用原身份和配置，不让评审自行刷新 RT 或生成新身份。绑定账号沿原 watcher 定向更新；未绑定账号需要刷新时先释放评审租约，再走原刷新所有者，防止 shared／exclusive 自锁。
- 现有作业登记新增执行容器角色／精确 ID／私有证据根与创建意图，`wait/control/cleanup/reconcile` 按已核对的作业角色分派；固定账号 CLI 的 container_id 不变。创建中断、停止、quota、账号维护／删除和重启都能发现子容器；实际全部进程退出后才能释放租约，不影响健康兄弟及公共 network／sender。

该隔离复用既有网络挂接与共享租约，新增的是受控执行边界。私有评审会话与证据可持久恢复，但候选无法通过共享 HOME、PID 或日志读取；不能依赖提示词保密或会话结束删日志代替隔离。可行性与原方法定位见 `research/review-isolation-feasibility.md`。

新场景环境从原账号 RAM 静态预留 512 MiB 给单评审池，固定 CLI 至少保留 512 MiB；network／sender 份额不变，额外 swap 仍只给固定 CLI。原 CLI 的 CPU／PID／tmpfs 份额也按 4/8＋2/8、384＋128、64＋64 MiB 分配，不增加账号总预算。已创建的旧布局必须空闲显式重建，不在运行中静默降限。

刷新待办绑定原 Run、request_id、身份、环境代次及被拒 AT 的摘要。身份／环境换代或原所有者发布不同有效期内 AT 后，旧请求不阻止新上下文；新请求替换时将旧请求归档为 superseded，而非伪造刷新成功。原批次仍核对原身份，旧线程在持 owner 锁时核对 expected request_id，不能刷新或覆盖新请求。相同上下文、相同被拒 AT 的有限失败继续保持受阻。

评审输出为严格、单一、有界 JSON：

- 身份：评审作业、任务、轮次、回答摘要、依据摘要；控制端另核真实归属，不能仅信任回显。
- `decision`：`disclose/pass/fail/uncertain`；披露只能选择当前允许的固定分支 ID。
- 逐 criterion 的 satisfied／violated／unknown、简短原因与存在的证据引用。
- 合法结果类型和允许反馈码；不要求输出推理过程，不执行评审返回的任意命令、路径或自由材料。

程序行为以测试结果为准，语义评审不能覆盖确定的行为失败。机械引用存在不能替代语义正确；方案允许多解，短答案不扣分，包含正确符号但结论相反应失败。工程任务以行为与回归为必要条件，不为无关说明无条件追加模型评审。

TY-M01 的用户测试与用法交付包含非确定性质量要求，故其工程验收在业务观察、实际用户测试和冻结原生全套通过后，另经同模型评审核对真实业务相关性。其余两个纯库修复仍以独立程序事实接受。评审能读取冻结候选实际变更文本；criterion 显式 allow_candidate_evidence 时才允许引用 candidate:<path>，引用必须存在于该版本 candidate_files。

合理澄清可触发固定材料组；材料只能披露一次，投放意图与真实消费可恢复。首版每任务默认最多 4 个正常答复轮次，内容只能在服务端上限 8 内明确覆盖；不把轮次当任务数。

`uncertain` 是有效但未判定，直接保留候选并将该任务标记 evaluation_blocked／任务 blocked，不自动重抽直到通过，也不发业务修正。格式、引用、身份错误或评审超时属于评审 error，最多重试同一冻结输入一次；耗尽后受阻。首版不提供人工直接覆盖结果的运行工作流，人工用于离线校准和抽查。

## 8. 提交、释放、评测与接续

1. 候选正常回复后，核对原生父链、输入消费、source、阶段及 generation，定向冻结并封存完整回答和候选。
   同时冻结该任务已消费的业务输入及先前回答，包含首问和实际披露材料；评审只读该冻结对话并核对输入摘要，不以最后一条补充材料替代原问题。
2. 持久化 candidate 和 waiting_release 评测作业，再让 driver 结束当前执行；使用真实收口与严格清理证明，不伪造退出码或把提交等同任务通过。
3. 等候选 CLI holder 完全释放后，运行隔离机械验收，并按需要通过原 `Scheduler.submit()` 排独立 `project_review`。机械验收沿本地验证并发限制在后台执行，不持数据库锁，也不阻塞项目调度 tick；不持有候选名额同步等待评审，容量为 1 也能闭环。
4. 所有评审入口、实际 exec、quota 恢复及接受点均复核父 generation／状态、内容和候选摘要。待评审队列按就绪时间优先于新候选补位，不额外增加账号容量。
5. 评审严格释放后，把材料披露、有限修正或下一任务动作落盘；需要继续时恢复原候选 session／工作区，按真实消费证明投放。
6. 服务重启按持久状态重新认领：先收口原执行，再补评测或恢复未完成业务；提交 ACK 丢失先查绑定 Run，禁止盲建第二个执行。

接受点是 CAS 事务。旧代次、停止后或已替换回答的迟到结果只留历史，不推进状态；候选或评审任一方未严格释放都不能启动相冲突的下一执行。

## 9. 预算、尝试与超时

新 policy 3 默认候选单次有效执行上限 600 秒、单任务累计 1,800 秒；首次加最多两次继续／修正。保留独立的整 Run 保护截止，新预算不得静默改变旧 policy 2 的 timeout_sec 含义。

每次逻辑评审尝试最多 180 秒，同一冻结回答首次加最多一次因执行／格式错误的重评。`review_timeout_sec` 约束该逻辑尝试的全部 Run／source 片段；同回答累计上限在创建时固定为 `2 × review_timeout_sec`（默认 360 秒），`review_budget_sec` 专指任务全部轮次累计评审上限（默认 720 秒）。每段领取上述三层剩余量的最小值，quota 或基础设施恢复不重置任何一层。先达到任何上限即评审受阻；这些是可配置初始上限，不是实测最优值或目标耗时。

新创建 DTO 用 StrictInt／显式范围校验预算；冻结策略包含 `timeout_sec`、`task_budget_sec`、`review_timeout_sec`、`review_budget_sec`，并拒绝 bool、字符串、小数和未知字段。尝试上限 3、同候选评审上限 2 为首版固定规则；配置不得在恢复时增发余额。

公开范围为候选单次及任务累计各 60～86,400 秒，评审单次 60～600 秒，任务累计评审 60～86,400 秒；实际单次领取任务／评审剩余量，不能因公开配置最小值而向上补发内部剩余预算。

实际输入消费后扣业务尝试；正常澄清、额度恢复、未投递的启动错误及只续验收不扣业务修正次数。执行基础设施故障对一个业务任务、对一个冻结回答的评审分别最多额外恢复两次，跨 Run 持久计数并按既有调度 tick 退避，随后受阻；不以此无限重启。

逻辑评审次数按实际消费评审输入认领；未消费的启动恢复不算一次已完成评审，已消费但未完成的基础设施接续沿原私有评审 session／尝试，不重新给予时限。完整评审输出无效后重评才是第二次逻辑尝试。评测作业关联一至多个真实执行 Run，旧终态 Run 不改回运行，不因当前 Run 指针改变而丢失历史。

工作片段覆盖模型解题与工具执行；排队、环境准备、额度／时段等待、材料等待、评审及本地验证另记。片段内单调计时，绑定 boot 身份，输入消费、候选提交、暂停、退出及周期高水位落盘；使用唯一片段序号幂等结算。

启动前预留本段允许预算，确认退出时退回未使用部分。崩溃尾段不能确认时保留不确定预留，显示为预留而非实际耗时；安全余额无法确认则受阻，不清零重发。跨 boot 不直接相减单调时钟。

超时旧 Run 维持 timeout。完整候选已封存时只续机械验证／评审，不重问；回答／修改未完成时新 Run 恢复原 session 和半成品。输入消费、会话或候选证明不可靠则保留现场阻塞。已通过任务、已消费材料及已结算用量都不重做。

## 10. API、页面与成本

沿用项目资源前缀，并对新内容增加 `content_schema`、场景／任务数及就绪状态。现有创建批次根据所选内容选择 policy 版本；旧请求语义保留，新内容按显式预算或新默认值建立策略快照。

API 必须通过 `model_fields_set`／`exclude_unset` 保留请求省略信息，再由所选内容的策略归一补默认值；不能让 DTO 的旧 `timeout_sec=1800` 抹掉新默认 600。显式合法值按原样冻结，显式 null 预算拒绝；旧可省略 concurrency 的语义保持。旧内容提交新版本专用预算字段明确拒绝。页面根据内容版本初始化默认值，只提交当前合法策略，记录用户已修改字段；API 省略、新旧显式值、切换内容和重绘均加入对照。

创建请求的 `scenario_entries` 可按 project_key → scenario_id → entry_id 选择固定入口，独立于 policy。nested URL 中 task_id 是数据库任务行 ID，稳定业务标识在 task_key 字段。

`GET /api/project-instances/{id}` 新投影包含场景、稳定任务、类型、依赖、任务结果、执行／评审状态、恢复资格和代码接受记录。旧实例继续返回原 steps／plans 语义。

新详情路径置于 `/api/project-instances/{id}/scenario-tasks/{task_id}` 下，按需提供 attempts、artifacts、file。所有任务／尝试必须归属该实例，文件按冻结清单有界读取；不新增顶层白名单或鉴权豁免。首版不增加人工审核或任意自由续聊入口。

用量按任务／类型／候选与评审角色聚合，保留输入、输出、缓存读写、请求、有效耗时及来源覆盖。全部未知返回 null，部分已知返回小计与不完整标记；不能把一个共享 Run 的总量重复分配，不能由现有输入合计倒推缓存。原 `complete` 的统计完整性与任务通过分开。

页面展示“同模型独立会话评审”，区分任务通过、代码接受、执行结束、超时待续、只续验收、待材料、评审受阻、预算耗尽和依赖受阻。目录失败不遮住历史批次；回答／详细证据按需加载，不随 SSE 反复推整份报告。SSE 使用同一公开投影，保留展开／滚动，切页关闭连接。

## 12. 兼容、回滚与具体风险

历史 reader 不依赖当前 catalog 就绪，缺失对象准确报错，不用当前目录伪装历史。普通题库、额度、认证与严格清理沿原入口；新增运行类型要纳入停止、恢复、配额及普通续聊拒绝。

内容、离线环境与控制脚本同步 Dockerfile、dockerignore 和 `deploy/v3/manage.py` 的快照清单。`.env` 业务文件由冻结素材在临时目录生成。Typer 上游源码自带的非秘密测试 `.env` 保留原固定提交身份：仅为该精确路径增加打包例外，快照入口核对固定 SHA-256；其他环境文件仍排除。本轮不发布镜像或部署。

Git 交付也按原始字节保存正式内容与本任务研究证据，禁止自动行尾转换改变冻结摘要。python-frontmatter 固定提交的 `AGENTS.md` 属于上游源码数据；仅对正式种子和本任务对应研究副本开放精确忽略例外，不放开本地工具指令文件。交付前从 Git 索引导出内容，核对完整目录与固定 catalog 摘要。

回滚先停止并收口新版本在途候选／评审，备份 SQLite、发布及对象；旧执行版本继续可读。旧代码不能解释的新 policy 3 保持禁止调度，不能删除记录或把它降级为旧线性步骤。

具体风险：同模型相关误判、评审私有证据与凭据刷新交接、异步释放竞争、崩溃尾段计时不确定、原生全套成本高于旧默认。分别用规则／正反校准、隔离挂载与唯一所有者、持久 CAS／严格释放、不确定预留及目标镜像实测处理。评审子容器占原 CLI 名额且计入原账号／宿主资源预算；不承诺评审无误或 token 必然下降。
