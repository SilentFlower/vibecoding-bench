# 真实项目多场景任务与恢复改造

## Goal

将项目迭代模块扩展为围绕真实项目的多场景任务执行：既能理解、咨询、诊断和讨论方案，也能按明确请求修改工程；分别判断任务结果、代码接受与整轮运行结束，并在超时后可靠接续未完成工作。

## Background

- 用户已确认取消每项目固定 20 步；任务数量由真实场景决定，不能用追问、重试或拆分实现／测试来凑数。
- 规模方向为 100 个真实项目、约 600～800 个业务场景、约 2,000 个独立可验收任务；这是内容池目标，不是每仓配额，也不代表这些新任务已制作或跑通。
- 现有 100 仓来源、固定提交、原生基线与 2,000 项工程候选保留为事实资料。原研究完成度不能替代新场景验收与模型完成度。
- 三项目场景样板位于 `research/project-scenarios/`：python-frontmatter 为 4 场景／6 任务，pydantic-settings 为 5／7，Typer 为 4／7。共 17 个理解、咨询、诊断、方案任务与 3 个工程任务。现已物化冻结源码、业务素材和离线环境；原生内容、调度机制和模型完成分别记录，真实模型完成数仍为 0。
- 现有实现已支持同会话多步、持久工作区、独立程序验收、超时新 Run 接续和每步三次尝试；仍以线性工程路线和 `app.py` JSON 行协议为中心，问答评分与跨执行累计预算尚未实现。
- 用户已选择 A：自动独立评审，并说明没有额外模型。首版复用执行任务的现有账号与同一模型配置，在独立会话中评审；不要求新增供应商、账号或凭据，评审消耗的原额度与用量单独记录。

## Requirements

- R1 内容覆盖：项目包含若干业务场景及稳定任务标识，覆盖理解、咨询、诊断、方案、工程修改；允许独立任务与真实依赖，不设置每项目统一数量或必须改代码的要求。
- R2 用户问题：首问、按需补充材料、条件分支与自然结束条件明确；首版使用冻结分支素材，正确排除 BUG、合理澄清都可以成为任务结果，补充材料与重试不算新任务。
- R3 分类验收：关键事实与源码证据、可运行用法、诊断链和方案约束分别验收；可确定行为由独立测试判断，其余采用同一现有模型的独立评审会话。评审依据与回答版本冻结，不能依赖执行会话自报成功；人工用于初期校准及抽查。工程修改仍使用独立业务验证及适用回归。
- R4 状态边界：任务通过、代码检查点接受、场景完成、运行结束分别记录；只读任务通过不增加代码能力，运行结束可以包含明确失败或未完成结果。
- R5 版本与隔离：独立场景固定基线与输入；声明使用前次修改时绑定已接受代码状态。用户应用增强与上游库修复的修改对象分别约束；评审输入、HOME 和原生日志必须与候选可读目录隔离。
- R6 恢复：超时保留执行记录、会话、工作目录和半成品，已通过任务不重做；在会话、输入消费及检查点证明可靠时接续当前未完成任务；材料不可靠时保留现场并阻塞。
- R7 预算：每任务首次执行加最多两次继续／修正，累计有效运行时间跨恢复保留；分类记录 token 与耗时，未知用量不能伪造。额度等待与基础设施故障不能冒充模型业务失败。
- R8 调度与展示：支持不同类型任务推进和必要依赖阻塞；页面能区分通过、失败、超时待续、待材料、预算耗尽及受阻原因，展示按任务类型与完整尝试累计的成本。
- R9 内容接入：首批为已有三个真实项目样板提供可执行的接入与验收路径，允许就绪的部分真实内容先运行，不以补齐 100 项作为试点启动条件；新增模型供应商与独立人工审核工作流不作为首版前提。
- R10 兼容与数据：既有历史发布、批次、会话、成果及原题库功能保留可解释的版本语义；不能以恢复旧生成内容或批量重置历史数据解决接入问题。

## Acceptance Criteria

- [ ] AC1：少于 20 个任务、不同场景长度与真实依赖均可被验证和执行；无缺陷诊断、咨询、方案可独立通过而不改源码。（R1–R4）
- [ ] AC2：用户只能获得首问和当前分支应披露材料，隐藏参考与验收不进入候选工作区；冻结的错误结论、捏造 API、缺约束反例不能通过，可行的等价答案能够通过。（R2、R3、R5）
- [ ] AC3：三项目样板分别包含真实咨询、信息不足与无 BUG 场景，以及两项库修复和一项用户应用增强的独立行为验收。（R3、R5、R9）
- [ ] AC4：前两任务已通过、第三任务半途超时，后续执行只续第三任务，保留半成品；已接受状态和成本不重复累计。（R4、R6、R7）
- [ ] AC5：候选完整而验收未结束时可接续验收；输入消费、会话或检查点不能确认时拒绝盲重发。（R3、R6）
- [ ] AC6：同一任务多次超时／修正后达到次数或累计运行预算上限，明确记录未完成并终止自动继续；独立任务仍可执行，真正依赖任务受阻。（R4、R7、R8）
- [ ] AC7：页面和 API 的任务数、场景数、结果、恢复状态及分类累计成本一致；重启后状态可恢复；基础设施错误与业务失败区分。（R4、R7、R8）
- [ ] AC8：现有普通题库、历史项目读取及适用调度／恢复回归保持；内容研究、接入就绪与真实模型完成分别报告。（R9、R10）
- [ ] AC9：只配置一个现有账号和一个执行模型即可完成被测执行与独立评审；评审上下文隔离、先释放候选再调度评审，不因两个候选占满共享容量而死锁。评审错误／不确定不冒充被测模型失败，额外用量与预算单列。（R3、R6–R9）

## Out of Scope

- 本轮交付以本地模拟模型机制、真实项目原生验收及 UI/API/DB 验证为界，不自动启动真实模型批量试跑、发布镜像、生产部署或历史数据库清理；真实评审质量与成本校准单独开展并报告。
- 不把内容池数量目标当作首批代码交付已自动包含的 100 仓新场景生成；扩展内容的批次边界在实现规划中单列。
- 不训练模型、不引入攻击或账号操作类场景，不扩展账号身份和网络能力。
- 不恢复已退役的生成项目或将真实项目改写成同构 `app.py`。
- 不新增模型供应商／账号设置，不把跨模型互评或人工逐项审核做成运行前提；不提供人工直接覆盖自动结论的首版工作流。
- 不建设任意人工自由补充材料的会话产品；首版按冻结分支披露，保证相同入口的可比较性。
