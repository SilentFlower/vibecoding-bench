# 修复登录草稿转正式账号后的额度挂载遗漏

## 目标

新账号通过登录草稿保存为正式账号后，首次运行完整抓包任务能正常读取该账号的额度状态，无需用户手工重建环境。

## 背景与证据

- 用户在本会话先要求恢复 11-5，再明确要求永久修复已定位的源码缺陷。
- 11-5 原网络容器没有 `/quota-accounts/14`，宿主额度文件存在且未阻断。四次启动由 Recorder 写出“养号额度策略或许可不可读取，已停止执行”，随后监督器以 43 退出。
- 11-5 已经通过既有维护接口重建恢复；同一工作和会话产生正常模型响应。本任务不重复操作其线上环境。
- 网络角色只为已有正式 ID 的账号加入额度目录，见 `orchestrator/account_isolation.py:184`；登录草稿不具有该 ID，见 `orchestrator/login_drafts.py:225`。
- 登录提交通过 `_row()` 绑定正式 ID，见 `orchestrator/account_runtime.py:2234`；绑定仅更新数据库，见 `orchestrator/account_runtime.py:294`。`ensure()` 继续复用旧角色，见 `orchestrator/account_runtime.py:644`。
- 线上两份根因模块与当前仓库源码摘要一致；本次恢复和调查记录位于 `.deploy/11-5-quota-repair-20261106/`。

## 需求

### R1：正式账号的额度挂载完整

正式账号需要 CLI 额度文件时，其布局 2 网络容器必须具备指向本账号额度目录的只读挂载；新登录草稿转正式账号、以及历史已保存但遗漏挂载的账号均能在后续实际准备入口获得正确环境。独立 API 不读取该额度文件，保持健康传输，不为补齐而等待排空自身已持有的并发许可；后续需要额度文件的准备仍须满足挂载和空闲门禁。

### R2：空闲修复与运行隔离

仅在原有维护门禁确认空闲后修复遗漏；有活动 CLI、API、等待请求、评审或未确认执行时保留现场并明确等待或拒绝。未知归属、错误账号挂载或损坏证据不能按普通缺失处理。状态读取不触发容器重建。

### R3：资料与兼容性

修复保留环境 ID、画像、HOME、设备身份、最新凭据、项目工作区、原任务和原会话。有效挂载的环境直接复用；未提交草稿、取消／重登、旧隔离布局和人工停用继续遵守现有约束。

### R4：回归与可核验交付

覆盖“无 ID 草稿创建 → 正式绑定 → 首次实际执行”的原故障链，并验证挂载归属、只读访问、并发保护、幂等性和失败收口。验证不使用真实 OAuth 或付费模型请求。

## 验收标准

- AC1（R1、R4）：隔离场景重现旧版遗漏，修复后正式账号首次抓包可在网络容器中读取自己的额度状态，不再因目录缺失生成失败暂停信号。
- AC2（R1、R3）：已存在且正确的额度挂载不重建容器；首次修复后重复启动不重复重建。
- AC3（R2、R3）：有在途／等待 API、CLI 或评审时不停止或移除原容器；没有越过现有维护门禁。独立 API 自持并发许可且仅缺少 CLI 额度挂载时继续使用健康发送器。
- AC4（R2）：挂载指向其他账号、可写、来源错误或 Docker 观察不可核实时拒绝使用，且不暴露其他账号的额度或凭据。
- AC5（R3）：恢复前后环境 ID、画像、HOME 身份和凭据保持；原项目、任务和会话保持；草稿与登录提交失败仍可按现有机制恢复。
- AC6（R4）：聚焦单元／集成回归与本地 Docker 隔离验收通过；记录实际验证范围及结果。

## 范围之外

- 不修改额度阈值、Recorder 的真实耗尽／认证保护、Claude 协议或账户策略。
- 不增加 UI、配置项、数据库字段或产品依赖。
- 不自动发布镜像、部署生产、修改已恢复的 11-5 或其他线上账号；发布沿独立的既有流程处理。
