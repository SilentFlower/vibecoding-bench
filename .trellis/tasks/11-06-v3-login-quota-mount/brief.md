# 任务摘要 — 修复登录草稿转正式账号后的额度挂载遗漏

## 目标

- 让新账号保存后首次抓包正常读取本账号额度，无需手工重建环境。

## 范围

- 修复正式账号准备时的额度挂载核验与空闲补齐，兼容历史遗漏环境。
- 补充运行时、登录草稿和本地 Docker 回归，并更新对应规范。

## 非目标

- 不修改额度策略、登录 UI、数据库结构或账号隔离规则。
- 本任务不自动发布或部署，不重复操作已经恢复的线上 11-5。

## 技术概览

- 在 `AccountRuntime.ensure()` 复用网络容器前，核对本账号额度目录的实际来源、目标和只读属性。
- 明确缺失时，经过现有排他维护门禁，一次性重建该账号的空闲运行实例；保留原资料，再继续准备。挂载正确时直接复用；错账号、可写或无法核验的挂载拒绝使用。
- 独立 API 不读取 CLI 额度文件，准备时只跳过明确缺失的补建，避免等待排空自身并发许可；需要额度文件的其他准备仍执行挂载检查与空闲补齐。

## 背景与决定

- 根因已验证：登录草稿没有账号 ID，创建网络容器时跳过额度挂载；正式保存只更新数据库，旧容器继续被复用。
- 11-5 已通过原维护接口恢复并产生正常模型响应，本轮处理永久代码修复。
- 选择首次实际使用时补齐，覆盖新账号和历史遗漏，保持原额度发布路径与登录提交协议。
- 全程保留环境身份、HOME、最新凭据、工作区、原任务和会话；活动或等待中的 API、CLI、评审及未确认执行均受原门禁保护。状态查询不触发修复。

## 风险

- 缺失挂载的环境首次补齐会增加一次启动耗时；占用或重建结果不确定时保留现场并等待／对账。
- 本地源码覆盖验证不能代替正式镜像发布后的验证。

## 验收

- 完整覆盖“草稿创建 → 正式保存 → 首次抓包”，容器能读取本账号额度且不产生缺文件暂停。
- 正确挂载和重复启动不重建；并发准备最多成功补齐一次。
- 在途／等待请求、CLI、评审及遗留执行存在时不停止原容器。
- 独立 API 自持并发许可且仅缺少 CLI 额度挂载时，健康发送器继续可用。
- 错误挂载拒绝使用，其他账号额度不可读，本账号额度挂载不可写。
- 原身份、凭据、工作区和会话保留，登录提交失败与重试回归通过。
- 单元／集成回归与合成账号的真实 Docker 隔离验证通过，不调用真实 OAuth 或付费模型。
