# 账号执行与评审串行复用资源设计

## 目标与边界

落实 PRD 的 R1–R6。评审与同账号其他 CLI 互斥，评审自身仍使用原私有 HOME、PID 命名空间、冻结输入和 AT-only 凭据。无评审时保留普通任务的既有并发；独立 API 发送及其他账号不加入该互斥范围。

不调整评分内容或账号指纹，不增加服务器 RAM，不做数据库结构迁移，不新增网关租约协议。当前实际入口、已有类和方法见 `research/runtime-evidence.md`。

## 资源交接

### 预算与新环境

- 新建登录环境与新建项目环境统一采用 `isolated_account_limits` 的普通三角色预算，不再写入旧静态预留布局。
- 私有评审借用原账号扣除网络、发送器后的 CLI RAM；仅在固定 CLI 已确认为 stopped 后启动。评审 RAM＋swap 等于 RAM，额外 swap 仍只属于原固定 CLI。
- CPU 使用原账号扣除网络和发送器后的有限份额；保留私有评审既有 UID1000、只读根、PID128、tmpfs64MiB 和独立挂载边界。
- 保留旧 `scenario_account_limits` 及布局 reader，用于核对已创建旧容器及指标；不把静态份额之和用于解释新的串行模式。
- 1536 MiB RAM、2048 MiB 额外 swap 时，新固定 CLI 为 RAM1152 MiB、RAM＋swap3200 MiB；私有评审为 RAM1152 MiB、RAM＋swap1152 MiB。网络256 MiB、发送器128 MiB全程保持。

### 切换顺序

1. 只读准入核验实际三角色、账号预算、原身份和环境代次。有效普通布局无需旧评审文件；存在旧文件时必须核对其内容与真实 HostConfig。
2. 待评审出现后停止向同账号投放新的非评审 CLI，已有执行自然收尾；排队不持有资源租约、不扣业务尝试。
3. `ProjectReviewRuntime.start_run` 在环境锁内通过 `AccountRuntime.claim(shared_cli=False, exclusive=False)` 认领现有非共享 CLI 租约。原 Tasks、续聊、养号和维护均须在共同认领边界尊重这一占用；不调用排空 API 的 `prepare`。
4. 在固定 CLI 仍运行时完成缓存版本、原身份同步、网络 passthrough 核验及私有输入准备。持久化切换意图，然后停止固定 CLI，reload 核验退出；不得用 pause 代替停止。
5. 只在主容器已退出且没有未知评审实例时启动私有评审。继续使用原 Scheduler、normal 额度、实际模型冻结与进程证明。
6. 正常结束或异常清理都先停止并核验私有容器；确认其不再持有进程和 RAM 后，再启动同一个固定 CLI 容器并核验健康。最后释放租约和切换记录。

## 持久状态与恢复

新增 root 私有的 `runtime/project-review-serial.json`，使用原子发布、0600、fsync。以下字段是本任务新增的内部协议，不作为当前已有字段使用：

| 字段 | 定义 |
| --- | --- |
| `schema` | 固定1 |
| `environment_id/environment_generation/container_id` | 精确绑定原账号三角色中的固定 CLI 和环境代次 |
| `source/run_id/review_intent` | 绑定原评审执行，不可跨 Run 或代次重用 |
| `phase` | `prepared/cli_stopping/cli_stopped/review_running/review_stopping/cli_restoring` |
| `cli_was_running` | 是否由本次切换负责恢复固定 CLI |
| `cli_limits/review_limits` | 经过实际容器交叉核验的原固定配额及本次有限评审预算 |
| `review_container_id` | 创建 ACK 可用时登记的私有容器 ID；ACK 丢失沿已有精确标签和 intent 找回 |

执行记录补充串行模式标识，并同时支持当前单作业记录与历史共享评审记录。`_save_execution`、`cleanup`、`wait_worker`、`release` 和 `reconcile` 必须根据实际评审角色处理，不能再依赖 `shared_cli=True` 才能清理私有容器。

- 每个外部 Docker 动作之前记录意图，动作之后重新观察；ACK 或控制端重启后根据实际容器状态恢复，不能仅信任 phase。
- `ensure`、准入和状态读取认识合法切换：其他 CLI 返回可重试等待，不自动唤醒固定 CLI，不把合法暂时停止直接误判为坏环境。
- 恢复顺序始终为先收口本次私有评审，再恢复原固定 CLI；未知运行容器、容器身份冲突、停止结果未知或租约不一致保留占用并受阻。
- 固定 CLI 恢复失败时保留记录和门禁，允许原维护/对账路径重试；不能先释放占用再声称环境 ready。
- 既有批次的 generation、候选冻结、限次重试及额度恢复语义不变。等待期间不改业务结果；完整回答已封存时只恢复验收。

## 调度与兼容

- 跨所有有效活动批次判断待评审，排除已停止、旧代及无效作业，避免永久饥饿或旧结果拦截新任务。通用认领边界仍须复核，防止已经排入线程池的普通任务插队。
- 项目调度只在确认其他 CLI 已释放后投放评审，CLI 租约是最终互斥保证；忙碌作为等待处理，不标成业务失败。
- 普通 CLI 的串行状态检查、画像核验和认领共用同一环境锁，避免评审在检查与认领之间停止容器；版本安装仍在此锁外，认领保持有效。
- 新环境不创建静态评审预留；已有普通布局可直接走串行流程。旧 schema1 评审布局只读核对，保持固定 CLI 原限额；不隐式扩容、重建、换设备或换 HOME。
- 旧 Docker 隔离版本、坏画像及未知角色继续按原显式维护规则处理，本任务不绕过既有门禁。
- 评审采样从私有容器读取；固定 CLI 停止期间不发采样 exec，不把其旧限制冒充评审实测值。独立指标导入仍须原排他配置门禁。

## 验证与回退

以“首次登录创建 → 保存 → 同环境项目执行 → 程序验收 → 私有评审 → 恢复与落盘”为关键回归，并覆盖同账号跨批次/普通任务竞争和独立发送连接。现有 Docker 场景验证中的候选/评审重叠断言改为互斥与三个阶段实际预算证明；候选之间原有并发仍单独验证。

切换会增加同账号的等待和容器启动开销，换取同一预算内顺序运行。原生程序验证有其独立的有界资源池；本任务不将所有项目原生测试预算包装为账号 CLI 预算，也不宣称整个平台不存在其他资源约束。

本任务保留新记录以供审计。回退只能在串行评审已停净、固定 CLI 已恢复且没有未决切换时进行；旧版本无法读取新记录时先完成对账，禁止直接清文件掩盖状态。新建普通布局回到旧版本后仍会受旧评审预留限制，应在上线/回退单明确说明，不能回退后继续承诺新号可直接评审。
