# Brief — 合并 flower2api 主线并把新功能移植到第二版控制台

## Goal

- 把 `flower2api` 主线（`9c80a39a`，独有 34 个提交）合并进 `feat/console-ui-revamp`。主线的新功能全部保留，并以第二版控制台的结构和 token 呈现。

## Scope

- 解决 11 个冲突文件：
  - 系统更新后端与文档（已按并集合好）；
  - 系统更新弹窗：承接旧页面的新功能，旧页面保持删除；
  - 账号页、调度详情；
  - 请求记录、请求证据；
  - 运行环境页及其样式；
  - 1 个验证脚本。
- 核对自动合并进来的前端文件，使其符合第二版静态规则（不写死颜色、不用旧工具类和 lucide）。
- 主线修改过的验证脚本改用第二版选择器，`ui-guidelines.md` 补充移植后的合同。
- 验证通过后，由 Push 计划确认完成合并提交，并推送 `feat/console-ui-revamp`。

## Non-Goals

- 合入 `flower2api`、发版和部署。
- 修改主线功能的行为或修复主线缺陷：只移植，发现问题记为风险。
- 为新状态另出设计稿。

## Technical Overview

- 继续当前停在提交前的合并现场。冲突文件以第二版为底，按「分叉点 → 主线」的差异逐条重放主线行为，不整块采用主线旧结构。
- **系统更新弹窗**：
  - 主按钮按目标版本和下载回执切换为「先检查更新 / 待验证兼容 / 下载更新 / 立即重启 / 安装更新」；
  - 「安装方式」区按动作切换说明：下载时继续接单；立即重启时说明会断开推理、不问等待上限；兼容安装保留在途等待上限；
  - 进度视图的阶段名和维护提示采用主线文案；
  - 新增「账号后台更新」分区，可单项重试；
  - 操作详情增加网关和调度器的健康探测，以及暂停 / 恢复接单的时间。
- 后端 `system_updater.py` 保持主线逻辑，公开操作同时带本分支的步骤记录和主线新字段。

## Context & Decisions

- 合并现场已就绪：11 个冲突文件，其中 `SystemUpdates.vue` 和 `request-design.css` 是「本分支删除、主线修改」。
- 工作区原有的 8 个旧任务归档，与主线 `f7cb9e9c` 逐字节相同。合并前已撤掉本地副本，由合并带入同一结果，备份在 `/tmp/console-ui-pre-merge-backup`。
- **【关键决定】主线的两步更新流程放进第二版弹窗，不恢复整页 `SystemUpdates.vue`。** 新功能的位置：
  - 「下载 / 重启」复用概览里现有的「安装方式」区，弹窗里的安装方式即确认，与现在一致；
  - 「账号后台更新」作为弹窗主视图末尾的新分区。
  - 没有设计稿，沿用弹窗现有的视觉语言。
- **【关键决定】冲突以第二版文件为底重放主线行为。** 主线的文案、字段、接口、默认值和轮询节奏保持不变；只把旧结构和写死的颜色换成第二版组件和 token。
- **【重要限制】合并提交和推送仍需你确认 Push 计划。** 本任务只把合并推到 `feat/console-ui-revamp`，不合回主线、不发版。

## Risks

- **【交付风险】两步更新流程直接影响生产更新。** 移植时要与主线的提交载荷逐字段对照：下载用 `prepare`，重启用 `install` 加 `prepared_operation_id`，兼容安装带等待期限。三条路径都要用夹具断言请求体。
- 冲突以第二版为底重放，可能漏掉主线的个别改动。做法是以「分叉点 → 主线」的差异为清单逐条核对，并在实际结果里列出每个文件的重放项。
- 主线修改过的验证脚本可能仍按旧页面结构断言。改用第二版选择器，业务断言不放宽。

## Acceptance

- 没有冲突残留；两个已删除的文件保持删除，主线其余改动全部带入。
- 前端构建、单测（含静态规则）、原生脚本语法检查、系统更新后端单测都通过。
- 系统更新弹窗用合成夹具验证：下载、立即重启、兼容安装三条路径的载荷，账号后台更新与重试，健康探测详情，远程节点后台入口。
- 账号、调度、请求记录、请求证据、运行环境的移植行为有脚本或定向浏览器检查覆盖。
- 全量 UI 回归只剩基线已登记的失败；浅色、深色截图中，主线未改动的页面与合并前逐像素一致。
- 规范已同步；Push 计划确认后完成合并提交，`feat/console-ui-revamp` 包含主线 `9c80a39a`。
