# 统一项目迭代与养号迭代的自然工作区命名

## Goal

让项目迭代与养号迭代的新工程目录使用能体现项目本身的自然名称，并兼容已有工作区、原 Claude 会话和工程轮次清理。

## Background

- 用户指出养号项目名称带有 `warmup`，确认希望采用自然项目名称，并明确要求项目迭代一并修正。
- 当前两种模式共用 `ProjectsTerminal`；`_workspace_identity` 在 `orchestrator/projects_runtime.py:48` 为普通首轮生成 `workspace-<16位摘要>`，为养号及其他轮次生成 `<namespace>-workspace-<16位摘要>`。
- 目录名决定实际 Claude 工作目录及其主会话位置，见 `orchestrator/pi_terminal.py:83`、`:114`；现有源码、输入注册和轮次清理共同依赖该路径，见 `orchestrator/projects_runtime.py:85`、`:165`、`:178`。

## Requirements

- R1：项目迭代和养号迭代统一使用实际项目英文标识作为新目录名称的主体，以简短中性后缀区分独立工程实例；终端目录不再带 `warmup-workspace`、`projects-workspace` 或纯 `workspace-<摘要>` 的内部标记。不自动翻译或改写项目定义中已有的中文标题。
- R2：账号、任务空间、工程轮次和初始版本之间继续保持隔离。同一工程连续目标和重启恢复沿用同一目录，不覆盖另一空间或轮次的成果。
- R3：已有工作区继续接续原源码、Claude 会话、输入事实与累计进度；同一项目后继目标继续原目录，新名称从新建工作区生效。本轮不迁移目录或修改历史会话正文。
- R4：全量工程通过后的轮次清理兼容新旧命名，仅删除本账号、本空间、指定轮次的已证明工作区；未知归属、篡改和链接保持拒绝。
- R5：不为了改目录名重写真实项目内容、项目 key、账号身份、计划、额度或已保存的工程通过事实。

## Acceptance Criteria

- [x] A1（R1）：两种模式新建工程的目录均能识别项目自身含义，不再包含上述内部前缀。
- [x] A2（R2）：同项目的连续目标共用累计源码；不同账号、空间和轮次分别创建不同目录，不互相覆盖。
- [x] A3（R3）：已有普通项目首轮及旧养号注册均能复用原目录，已有修改及原会话定位保持有效。
- [x] A4（R4）：混合新旧注册的清理可重入，保留其他账号、空间、轮次、历史交付和会话证据；未知或篡改路径先拒绝，再执行任何删除。
- [x] A5（R5）：原命名相关回归与相邻原生终端回归通过，不增加真实模型或 OAuth 请求。

## Non-Goals

- 不批量改名或迁移已有工程目录，不搬迁、重写或重新创建历史 Claude 会话。
- 不重做项目池、工程内容、页面导航和调度规则。
- 本轮先完成源码实现与隔离验证；生产交付不在此次规划范围内。
