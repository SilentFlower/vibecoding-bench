# 构建与发布性能实施计划

## 开工条件

- 读取当前任务三件套、研究记录和平台部署规范，完成完整 Brief 评审后启动任务。
- 保护既有349项工作区内容，核对当前分支 flower2api 与 b553fba0 基线。
- 采用同一流水线性能任务收口缓存、并发和端到端验证。

## 1. 建立可重复测量

- 复用 research/performance-baseline.json 的正式CI原始来源。
- 记录构建及缓存准备/保存步骤、各历史来源及演练总体耗时；度量资料与签名证据分开。
- 明确本地冷/热和串行/并发对照使用同一输入、Docker平台、候选镜像与8个历史来源。

## 2. 接入缓存

- 在本仓 composite action 中统一 Buildx、GHA层缓存和三个 Cargo cache mount 的恢复/保存。
- 引用研究核对的固定 action SHA，复核各输入与 post 顺序。
- manage 的缓存模式保持可选；使用 --load，实际读取镜像身份，普通本地构建沿原入口。
- 校验名称、冷启动、缓存未命中、不可用回退和真实构建错误传播；签名材料继续仅出现在原签名/兼容步骤。
- 测试实际工作流的权限、事件和发布顺序，以及 cache mount id/target 与 Dockerfile 的对应。

## 3. 增加有限并发

- 提取单来源验证，增加 workers=1/2，发布CI使用2。
- 保持独立临时根、UUID、固定镜像与无网络容器；保留原超时和全部验证项。
- 覆盖来源顺序、并发上限、失败取消、运行中任务收口及原错误传播；成功证据仅在全部成功后写入。

## 4. 本地验证

- `PYTHONPATH=services/orchestrator:deploy/v3 .venv/bin/python -m unittest discover -s deploy/v3`。
- `python3 deploy/v3/verify_database_definitions.py`；固定宿主包仓库外独立导入回归。
- actionlint覆盖两个workflow及composite action的调用和表达式；YAML与Shell语法检查。
- 真实隔离Docker：单路/双路验证同一组8个历史来源，核对全部检查、证据等价、资源隔离与故障收口。使用合成密钥和测试数据。
- Buildx模式验证实际加载镜像及联合清单身份；冷/热本地样本记录构建与缓存相关耗时。

## 5. 规范与提交门禁

- 定向验证完成后经 Phase 2.1 completion contract进入 Check-All，检查缓存、并发、固定包及发布门禁的跨层影响。
- 更新权威规范的可执行环境与并发合同，保留单一权威位置。
- 精确Git计划列明业务代码、当前任务记录及推送后的GitHub缓存验收；原有dirty保留。

## 6. 推送后的GitHub实测

- 业务push触发正常只构建CI，记录冷缓存、构建与保存步骤；再手动运行同SHA的 v3-build，核对跨runner缓存命中与热构建总耗时。
- 此阶段只运行构建验证，保持零产品发布副作用。记录真实run、SHA、缓存状态和步骤耗时，分别对照327秒构建与448秒串行基线。
- 远端缓存验收依赖当前代码推送与GitHub runtime，按外部系统验证明确标注。冷/热及串行/并发的可复现收益均需收口；尚有必需验证时保持任务 in_progress。
- 在本任务既有研究路径写入实际结果，全部必要工作完成后按进度owner同步最终状态与Close。

## 恢复点

- 缓存开关关闭与workers=1均可作为对应机制的回退路径。
- 缓存准备失败按明确状态转入正常构建，发布错误继续阻断。
- 并发失败先等待各自资源收口，保留原错误及已完成事实；不清理其他Docker资源。
- 性能不足先依据原始数据调整当前机制；范围变化按增量计划同步，生产变更继续独立授权。
