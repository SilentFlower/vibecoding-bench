# flower2api 构建发布提速与展示名称统一

## Goal

缩短平台构建与手动发布的等待时间，统一 flower2api 对外名称与文档，并完整保留正式发行的来源、签名及历史升级回退验收。

## Background

- 用户在 v1.1.1 发布过程中提出提速需求，随后明确要求实施优化。
- v1.1.1 来源为 `b553fba0bff74b6a094b57f8b9da6b636a5f3ddc`，发布运行 `43210555291`；基础回归39秒、两镜像构建327秒、最近8个历史版本兼容演练448秒。
- 当前两个 workflow 分别在独立 runner 构建；Dockerfile 已有 Cargo 缓存挂载，跨 CI 的外部缓存入口尚待配置。
- 兼容演练按历史目录顺序逐个拉取旧镜像、创建隔离双库、迁移、候选读写、原版读写及快照恢复。

## Requirements

- R1：相同或兼容输入的后续构建能够复用跨 CI 缓存；普通构建和手动发布共同使用经版本、平台及依赖约束的缓存策略。
- R2：首次构建、缓存未命中及缓存不可用时沿正常构建路径完成；依赖或源码变化正确触发对应重新构建。
- R3：以有限并发加快全部8个历史版本的兼容演练，每个来源保留完整验证项、独立数据库与容器生命周期。
- R4：任一演练失败均阻止成功证据与正式发布；并发任务结束时收口各自容器和临时目录，结果按受信来源顺序稳定汇总。
- R5：保留手动发布入口、签名私钥边界、同批 run/attempt/SHA、两类镜像摘要及原 v3 更新/回退合同。自动构建继续具有零产品发布副作用。
- R6：支持复现实测，记录冷/热缓存、串行/并发演练的耗时、命中情况、覆盖版本和执行条件，区分本地结果与 GitHub CI 结果。

- R7：页面、CI及第一方README统一使用小写 `flower2api`。根README和组件README准确说明统一仓库、组件职责与实际来源。历史部署路径、镜像、环境变量、API及签名身份保持兼容。

## Constraints

- 现有349项工作区改动按原归属保留。
- 发布历史、冻结数据库定义及登记、工程库字节与原账号数据身份保持原合同。
- 使用现有 GitHub 托管 runner；缓存属于构建加速材料，正式发行仍从当前受控输入生成并验收。

## Acceptance Criteria

- [ ] 两个 workflow 的缓存接线可复用，实际命中、首次构建及未命中路径均有证据；源码/依赖变化的失效行为正确。
- [ ] 同一输入的冷/热构建及缓存准备/保存相关步骤耗时分别记录，热构建展示含缓存开销的可复现实测提速。
- [ ] 串行与有限并发均覆盖同一组8个来源，升级、候选读写、原版读写及幂等结果一致，证据格式保持兼容。
- [ ] 并发上限、来源隔离、失败传播、资源收口和结果顺序通过定向回归；失败产生的现场和原错误可定位。
- [ ] 手动发布门禁、固定宿主包导入、两镜像来源/内容摘要和双库合同回归通过。
- [ ] 工程规范、SOP及性能验证记录同步实际实现，所有耗时结论附执行条件和原始基线来源。

- [ ] 浏览器标题、登录页、管理页、工程页和CI展示名称使用 flower2api；根README与网关、编排器、运行时组件README按新布局收口，来源与许可证信息可追溯。

## Non-Goals

- 改变自动构建与手动发布的职责，减少受支持历史版本或验收项目。
- 引入付费或长期自托管 runner，正式发版、生产安装及生产数据或账号行为变更。
- 复用旧发行作为当前批次的正式制品，变更签名信任根、更新通道或发布身份。

## 增量决定

- 用户选择统一对外展示名并保留旧升级标识，明确产品名为小写 `flower2api`，要求同步README。
- 用户指出网关README仍是旧介绍，确认其组件说明纳入整理；网关来源已核对与原v3锁定提交7cbf3e35一致。
- 编排器平铺目录已完成盘点。其业务包和测试目录重构作为独立设计事项，本轮提供模块导航文档。
