# Brief — flower2api 构建发布提速与展示名称统一

## Goal

- 缩短 flower2api 构建与手动发布的等待时间，完整保留来源、签名及历史升级回退验收。

## Scope

- 两个 v3 workflow 的共享缓存接线，以及 Docker 层和 Cargo 挂载缓存的跨 CI 复用。
- 最近8个历史版本兼容演练的有限并发、失败收口和稳定结果汇总。
- 冷/热缓存、串行/并发实测与对应规范、SOP和性能记录。

- 页面与CI展示名称，以及根和组件README统一为小写 flower2api。
- 运行时日志页同步品牌；main补齐手动构建入口注册并同步共享缓存action和发行展示名称，main自身跳过产品构建。

## Non-Goals

- 正式发版、生产安装、付费或长期自托管 runner。
- 受支持历史版本和验收项目的缩减，旧发行制品的直接晋级。
- 产品业务功能、账号数据、签名信任根和更新通道变更。
- 编排器业务包和测试目录重构。

## Technical Overview

- 由本仓 composite action 统一 Buildx、GHA层缓存和三个 Cargo 缓存挂载，缓存辅助 Action 固定到已核对的提交。
- 缓存模式仍加载实际镜像并生成原联合清单。普通本地构建沿原入口。
- 演练默认串行，CI显式启用两路并发。每个来源保留独立双库、UUID、容器及完整验证项。
- 首次失败后取消待运行任务，等待已开始任务收口，再传播原错误。全部成功后生成兼容证据。

## Context & Decisions

- 实施分支为 flower2api。v1.1.1 基线：镜像构建327秒，兼容演练448秒，基础回归39秒。
- 自动构建与手动发布职责、run/attempt/SHA绑定、两镜像摘要及固定宿主包合同沿用现有SOP。
- GitHub跨runner缓存通过业务推送后的正常构建和同SHA再次手动构建核验。必要验收完成后关闭任务。
- 现有349项工作区改动按原归属保留。

- 增量决定：用户选择统一展示名，明确为小写flower2api，并要求根和网关组件README收口；编排器补充当前模块导航。

## Risks

- 缓存传输可能抵消编译收益。验收统计缓存准备、构建和保存的完整耗时。
- 并发增加Docker资源负载。执行上限保持为2，支持切回串行。

## Acceptance

- 验证冷启动、未命中、实际命中和源码/依赖失效，热构建展示可复现的净提速。
- 同一组8个来源在串行和双路并发下结果等价，记录实际演练耗时。
- 并发上限、隔离、顺序、失败传播及容器收口通过回归。
- 手动发布门禁、固定包独立导入、镜像来源和双库合同回归通过。

## Next Step

- 收口本地构建、浏览器及隔离Docker验证后进入Check-All与规范更新；精确Git计划覆盖flower2api和默认分支注册文件。推送后验证跨runner缓存，必要验收完成后关闭任务。
