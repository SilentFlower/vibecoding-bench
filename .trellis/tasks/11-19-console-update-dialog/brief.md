# Brief — 系统更新弹窗与步骤记录

## Goal

- 系统更新改为从版本号打开的弹窗：在弹窗里看版本与发布说明、直接安装，安装后按步骤显示带时间的进度。

## Scope

- **入口**：侧栏与移动抽屉的版本号、直接访问 `/updates` 都打开同一个新弹窗，撤掉整页。从版本号打开时地址不变；直接访问 `/updates` 时背后是账号页，关闭后回到 `/`。
- **概览**：
  - 版本摘要与状态标签、兼容性提示。
  - 发布说明，可展开完整原文。
  - 安装方式：暂停新接单，在途等待上限 1～120 分钟，默认 1 分钟。
  - 上一次操作的紧凑记录。
  - 底栏：版本记录与回退、运行组件与维护详情、检查更新、安装更新。
- **进度**：
  - 摘要：当前 / 目标版本、操作 ID、最近更新。
  - 步骤列表：已完成 / 进行中 / 待执行，已完成与进行中带进入时间；含数据库迁移时多两步。
  - 阻塞原因与节点同步进度照常列出；结局沿用现有文案。
  - 底栏：取消等待、恢复操作、操作详情。
- **二级视图**：版本记录与回退、运行组件与维护详情、操作详情与数据库快照在弹窗内切换，带返回，现有信息一项不少。
- **其他状态**：首次接入、读取中、检查中 / 失败、已是最新、暂无发行、断线自动重连都有呈现。
- **新组合组件「提示条」`NoticeStrip`**：用于更新弹窗，并交给子任务 6 的任务与工程页账号卡使用。
- **后端**：更新器在阶段变化时向操作记录追加 `steps: [{phase, at}]`。
  - 覆盖宿主恢复路径写入的「正在恢复数据库」；同一阶段不重复记录，上限 64 条。
  - 状态与操作接口返回 `steps`。
- **验证与文档**：
  - 后端单测；步骤推导纯函数单测。
  - 改写 `verify_update_design.py`（对新设计稿比对）与 `verify_system_update_browser.py`（弹窗流程）；分诊另外 7 个依赖旧更新页的脚本。
  - 同步 `platform-online-update.md`、`ui-guidelines.md`、`SYSTEM-UPDATES.md`。

## Non-Goals

- 更新通道选择、实时日志流（SSE）：进度沿用现有轮询。
- 管理桥、网关和更新器其他字段不改；管理桥原样转发 `steps`。
- 深色配色（子任务 7）；任务与工程页接入提示条（子任务 6）。
- 真实 Docker 端到端 `verify_system_update.py` 本机不跑，与前两个子任务相同；字段变化由单测覆盖。

## Technical Overview

- **步骤记录**：
  - `_record` 是所有阶段写入的唯一落盘口：执行线程、恢复线程和宿主回调都经过它。
  - 在这里比较当前阶段与最后一条步骤，不同才追加，同时截断到 64 条。
  - 旧操作文件没有 `steps`，公开为空。
- **步骤推导**：
  - 纯函数 `updateSteps` 按规范顺序（下载校验 → 等待在途 → [快照 → 迁移] → 切换 → 验证 → 保存 → 回收）把实际步骤排好。
  - 同一阶段只保留最后一次，因此越过取消边界时的第一次「切换」会并入真正的切换。
  - 维护中时补上「待执行」行；没有记录的旧操作按当前阶段推出。
- **弹窗**：
  - `SystemUpdateDialog` 基于 `ModalDialog`，数据、轮询与提交逻辑整体搬自 `SystemUpdates.vue`（之后删除），按视图表切换五个视图。
  - 外壳监听路由：进入 `/updates` 即打开弹窗，关闭时改址回 `/`。
- **样式**：新文件 `system-update.css`（`@layer components`，只取 token）。旧更新样式（`approved-design.css`、`style.css` 中约 100 条）逐条删除。

## Context & Decisions

- 依赖的子任务 1、2 已完成：`ModalDialog`、`NumberInput`、`ConfirmationDialog`、版本号入口都已就位。
- **【关键决定】点「安装更新」直接登记安装最新版本，不再弹确认框。** 这是你本轮的选择：弹窗里的「安装方式」就是确认，与设计稿一致。
  - 提交后等待上限锁定；网络结果不确定时，重试沿用同一操作 ID。
  - 409 时在弹窗内提示，不自动重放。
  - 误点会开始暂停新接单，但在等待在途期间可以「取消等待」撤回。
- **【关键决定】回退到历史版本、从版本记录列表安装（含最新版本，列表视图看不到安装方式区）、恢复操作仍弹二次确认**，等待上限默认 1 分钟、可调整。
- **【关键决定】等待上限从下拉选项（1/5/15/30/60/120）改为 1～120 的数字输入**，与设计稿一致；默认仍是 1 分钟，提交仍按秒。
- **【关键决定】版本记录、维护详情、操作详情三处改为弹窗内的二级视图，带返回**，不再是同页展开区。设计稿只画了底栏入口，这个形态交截图确认。
- **【关键决定】进度视图的出现规则**：
  - 维护进行中、等待对账或清理待重试时，打开弹窗直接显示进度。
  - 本次弹窗里看着完成的操作停在结局，点「完成」回概览。
  - 更早结束的操作只在概览显示一行「上次操作」，可点开查看。
  - 影响：刷新页面后不会再直接看到「更新完成」进度画面，而是概览加一行记录。
- **【重要限制】`/updates` 打开的是模态弹窗，挡住背景页**：直接访问时背后是账号页，必须先关闭弹窗才能操作背景页，关闭后地址变成 `/`。依赖旧整页形态的脚本据此改写。
- **【关键决定】步骤行的说明只用真实数据**：等待在途的阻塞数、快照大小与状态、各库迁移状态，其余为空。设计稿里「镜像签名与摘要已核对」这类示意文字不照搬。设计稿中的「候选已准备」只属于单独的准备动作，安装流程没有这一步，不列出。
- 后端字段只增不改：旧前端忽略 `steps`，新前端兼容旧操作，更新器与控制镜像可以分别发版。

## Risks

- **【交付风险】旧更新样式分散在两个文件约 100 条，删不干净会压过新样式。** 由新 `verify_update_design.py` 的逐项计算样式比对兜底；发现残留就继续删，不加 `!important`。
- **【交付风险】二次确认框叠在弹窗之上，焦点、Esc 与遮罩点击须只关闭上层。** 由浏览器脚本的回退 / 恢复场景断言，依赖 reka-ui 嵌套 Dialog 行为，不手写焦点管理。
- 回归集里依赖旧更新页的脚本要改写或分诊（`verify_design_parity`、`verify_management_ui`、`verify_frontend_navigation` 等）。规则同前两个子任务：样式采样移到新基准，行为断言不放宽；基线已失败的脚本失败点须不变。

## Acceptance

- 有新版本时从版本号打开弹窗，点「安装更新」完成一次安装：步骤按序推进，已完成步骤带时间，结束显示更新完成。
- 直接访问 `/updates` 打开同一弹窗，关闭后回到账号页；从版本号打开并关闭后地址与页面不变。
- 提交后等待上限锁定，双击只登记一次，30 分钟提交 1800 秒；409 弹窗内提示、不重放。
- 取消等待、恢复、回退、完整发布说明、维护与操作详情都可完成，结果与现有页面一致。
- 旧操作（无步骤记录）显示正常；首次接入、检查失败、已是最新、断线重连呈现正确。
- 1440×900 与 390×844 下概览与进度画面与设计稿一致，附截图。
- 后端单测覆盖步骤追加、去重、恢复路径、上限与旧操作；步骤推导单测、前端构建通过；两个改写脚本通过，其余回归与改动前基线一致。
