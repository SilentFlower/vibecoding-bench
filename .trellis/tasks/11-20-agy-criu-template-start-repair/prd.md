# 修复 AGY CRIU 模板启动失败

## 目标

启用 CRIU 的 AGY 环境能够准备并使用当前代次模板。模板失败时保留足以定位原因的受控证据。

## 现场

- US v1.25.1 的 AGY #14 同代发送器报告 `template_failed`、`last_start_source=exec`。被动观察到文件型模板进程在原生监听就绪前很快退出，未见 CRIU dump。
- 同一个线上容器的文件型 account-sender 与 observer-c 在 maps 和 stat 中呈现同 inode、不同设备号。断网 Docker 中用固定 AGY 1.5.9 和合成凭据复现了真实观察器准入失败。镜像文件路径得到 `execution_base_missing_maps_18_inode_8_device_0`，将同一执行体通过只读绑定挂载后原生监听就绪。普通 memfd 启动仍承载线上请求。
- `agy_runtime/supervisor.py:441` 将后台异常投影为通用模板失败，原工作目录随后回收。

## 要求

- R1 用冻结 AGY 制品和合成凭据复现，定位启动、观察器、保存或恢复链的首个失败点并修复。保留执行体身份、完整摘要、指令指纹、同代确认及权限边界。
- R2 诊断保留失败阶段和受控原因。模板失败仍按原请求截止回退普通启动，业务仅提交一次。
- R3 核对普通热进程、当前代次与旧代回收。生产验证沿原发布和部署流程。

## 验收

- [ ] A1 旧版隔离复现，修复后真实当前模板就绪并至少成功恢复一次。
- [ ] A2 核对错误执行体、错映射、跨代和普通 memfd；故障回退保留准确阶段。
- [ ] A3 核对无秘密的诊断、物理池占用、原请求成功和 Claude Code CRIU 回归。
