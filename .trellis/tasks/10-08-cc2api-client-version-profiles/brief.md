# Brief — cc2api 按客户端版本同时适配 260 与 280

## Goal

- 让 cc2api 按客户端版本同时适配 2.1.260 与 2.1.280，默认以 280 为主。

## Scope

- 版本选择贯穿请求头、正文、模型与辅助请求规则、billing/CCH、bootstrap、hello 和原生及自动遥测。
- 隔离同账号两版的遥测与版本相关缓存，补齐设置页、配置热刷新和回归测试。

## Non-Goals

- 293 等待抓包后另行接入；本轮不部署或发布。双仓提交、推送和任务完成记录已获后续 Git 计划确认。
- 不迁移 vm2api 架构，不拆分账号设备身份，不猜测未验证版本画像。

## Technical Overview

- 仅从原始 Claude UA 识别版本：260、280 精确匹配；缺少、非法或未匹配 UA 版本直接使用配置的默认画像，出厂为 280。请求体中的版本字段不参与选择。
- 请求开始时固定画像，改写使用账号副本；换号、401 恢复、签名重试和异步结果沿用该选择。
- 自动遥测按“账号＋画像”保存状态；stateful、hello 和非流式探针缓存加入画像维度。

## Context & Decisions

- 两版画像与脱敏签名样本已经存在，直接复用；主要改造入口是 Gateway、Rewriter、Telemetry 和设置链路。
- 默认启用按客户端版本适配，可切回原账号画像方式；管理员显式默认画像及准入配置保留，回退不绕过访问限制。
- 设备 ID、账号 UUID 和持久环境保持稳定；sticky、RPM、并发与上游 session 池继续共享原账号容量。
- 无版本证据的初始辅助请求使用默认画像；由已识别主请求触发的内部 hello 跟随主请求。

## Risks

- 同账号交错请求可能覆盖后台遥测或延迟缓存提交，需验证固定画像、运行 ID、TTL 清理和账号级聚合。
- 请求级账号副本必须避免写回数据库；两版测试需覆盖实际 beta/CCH 差异。

## Acceptance

- 同账号交错和并发的 260/280 请求分别生成正确 header、body、billing/CCH、bootstrap 和遥测，重试画像一致。
- UA 缺失/非法/未匹配时默认回退，请求体版本不参与选择；访问拒绝、设置校验与热刷新、旧模式、延迟结果及缓存隔离均有覆盖，持久身份、容量限制和未知字段/SSE 保真。
- 使用现有 fixture 验证嵌套模型、fallbacks、工具结果与续轮；通过格式检查、完整 Rust 测试、CCH 专项和前端构建，并完成 Check-All。

## Next Step

- 实现、Check-All、规范同步与双仓业务推送已完成；任务完成记录随本次交付同步。293 待新抓包后另行接入，未部署。
