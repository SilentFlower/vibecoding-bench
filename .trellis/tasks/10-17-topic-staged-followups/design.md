# 技术设计

## 目标与边界

本功能是一个完整交付：600 条可自启动英文题目及两条业务补充、逐次运行的随机消息快照、真实交互 CLI 的有限多轮执行、恢复与页面可见性。既有账号隔离、凭据、代理、额度来源和权限不变。用户明确要求 auto-loop 推进并在代码循环之后自动交付生产；runner 自身仍使用 commit-only。

## 题库与输入契约

- 以 `topics.md` 为权威来源。保留 600 个编号与 21 个分类块；两个 AI 分类改为普通文档/规则工作流类，相关条目及其它不合范围题目逐题替换，分类计数同步。
- 既有条目行继续承载英文 title 和初始 description；拟扩展两条固定缩进的 `Follow-up 1` / `Follow-up 2` 子行。两个解析器必须同源或获得同等严格校验，不能把子行拼进初始描述。历史无子行材料可解析为零补充；正式新题库必须每题恰有两条。
- 初始需求自包含并可独立交付。两条补充是题目专属的新业务能力，顺序递进；不采用催促、伪造观察或单纯随机化措辞。
- 初始和补充都不以用户文件、真实业务数据、账号、API Key、远程服务或硬件为开工前提。导入功能明确自建合成样例；图片/音频/硬件等无法简单自包含的条目改为普通本地应用或模拟器。示例数据不得冒称真实数据。
- 全字段检查英文、完整编号和重复条目，排除生物/医疗、网络协议/代理/扫描、安全、逆向、LLM 客户端/API/训练/微调/蒸馏等用户排除领域。保留经典算法、普通文件操作和课程练习，不能用泛关键词错误删除。
- 同步按 topic.no 原位更新，使用 SQLite backup API 保存包含 WAL 的快照；只更新题库及新补充列，保留 topic ID 和历史 task/run。旧实例需先迁移 schema，不能只复制 Markdown。

## 新数据流（拟新增字段，非既有事实）

1. topics 保存 `followups_json`（默认 `[]`）。Topic API 以最多两条的列表接受和返回业务补充，旧请求缺省保留既有值；可显式清空自建题目的补充。同步正式题库要求两条。
2. tasks 与 task_batch_items 保存 `followup_candidates_json`（默认 `[]`），与创建时的最终 prompt 一起冻结候选正文。自然模式普通任务、批次和养号携带候选；canonical 和非空自定义 prompt 保持零补充。历史缺字段默认零补充，不查询新题库回填。
3. 每个新 run 在同一创建事务中随机选择 0/1/2（等概率），将候选前缀固化为 `followup_plan_json`；必要时另存任务初始 prompt 的版本/摘要以核验。重复运行重新选择；已有 run 的重试、恢复、查看不重抽。批次创建后题库修改不改变冻结候选。
4. Runner 只从已保存的 run 计划下发正文，调度 payload、额度恢复、任务详情使用同一事实来源。旧调用缺值为 `[]`；损坏或超长计划明确拒绝，不静默当零补充。
5. v3 把计划和跨尝试阶段文件放在 `runtime/runs/<run_id>`，在原有目录映射中增加明确路径；旧 worker 使用工作区的受控运行文件。计划不拼进 TASK_PROMPT，也不泄露到别的账号/项目。

## 上一版多轮执行与确认（已部署行为）

- 拟新增小型标准库 Python 阶段模块，供 shell driver 调用；shell 继续复用实际 `inject_tmux_prompt()` 及既有会话 JSONL 完成判定。helper 通过正式镜像 COPY 分发，v3 driver 在 UID1000、原 cwd、原 tmux/CLI 下运行。
- 每个被选阶段均需要原主会话 JSONL 中的对应 user 输入和其后的稳定正常 assistant 回复；记录 run、计划摘要、阶段、session、输入/回复 UUID 或游标。只使用主会话，排除子代理、旧历史、tool_result、synthetic/API 错误及元消息。
- 初始轮完成后，有剩余业务补充才准备并投递下一条；投递前推进当前轮的完成基线，避免重复识别上一条 assistant 造成连续误发。最后一轮完成才允许 completion_done=1。
- 写前记录 pending、投递后核对会话输入，再标记 acknowledged；tmux 返回成功不等于 CLI 已消费。恢复先核对原会话记录：已确认消息不重复；确认后的未完成阶段继续；无法证实是否投递则明确失败并保留诊断，不盲重发。承认 tmux 与会话文件间没有跨进程事务，不承诺未知窗口下的无条件 exactly-once。
- 阶段状态原子替换、权限受限、限定大小，并拒绝符号链接/路径逃逸、错 run/错计划/非法索引、状态回退。计划为持久快照，阶段证据不能通过普通页面改写。
- 首轮和各补充轮均使用同一任务目录和 Claude 主会话，持续保留账号 CLI 租约；不为每条补充启动新任务或刷新凭据。
- 保留停止/永久认证异常/额度暂停/总超时优先级。每次执行的所有轮次共用原 TIMEOUT_SEC/deadline，不为追加消息重置；额度恢复仍沿用现有尝试时限策略。进入收尾窗口后不再开始新的业务补充；剩余补充未完成不能报告完整 success。
- 恢复提示、OAuth retry 和超时控制消息与业务补充独立计数；普通继续对话不重新播放自动补充。兼容零补充的旧 driver 路径。

## 页面/API

- 题目编辑新增两条英文补充内容，题目详情可查看；新增自建 topic 可保持零补充，界面不要求填满以维持旧 API 兼容。
- run 详情展示本次选定 0/1/2 次、初始/补充正文及真实阶段状态；所有内容使用既有 escapeHTML。缺失/损坏状态显示未知/失败，不冒充完成。
- 原有 API 字段、按钮、终端路径保持；旧/空计划无须新增手动流程。可增加简洁列表阶段提示，不增加复杂项目管理。

## 验证

- 解析/同步一致性、600 题语义审查与英文/排除领域、独立开工约束和每题两条实际业务补充。
- 0/1/2 的可控随机、事务快照、重复 run、批次冻结、规范/自定义/历史零补充、quota payload、坏数据拒绝。
- 阶段机覆盖真实 JSONL 结构、输入确认、旧回复隔离、元/子消息排除、pending 崩溃/已确认恢复、停止/额度/认证/超时优先级。
- 实际 tmux + 可控多轮 CLI 替身演练：原目录、原会话、实际收到所选消息、无重复、停止收口、恢复证据。原生 CLI 2.1.293 的本地版本/会话格式只读核对另记；测试替身不能声称真实模型推理通过。
- 相关后端全量、worker shell/Python、部署回归、前端语法和真实浏览器详情；同源正式镜像的 v3 隔离/转发回归。

## 交付与回退

auto-loop 完成实现、完整 Check-All、Spec Update 与精确本地 commit。之后按照用户自动部署指令，使用独立 release 操作记录接续精确推送、Actions 成功批次、同批清单/镜像、空闲窗口备份、schema 与题库同步、健康与原数据核验。等待生产活动任务自然完成，不强停；空间/预算不足时先核实可逆处理，不修改无关服务。

回退同时切换旧联合镜像和配置；新增字段保持兼容。回退代码前收口新多轮执行并保留其快照、阶段和最新凭据，不恢复旧 token。题库需要回退时使用同步前快照定向恢复题库，不能整库覆盖新的运行/凭据。正式生产验收不启动真实模型请求。

## 线上返工：输入传输与收尾

- 证据：`15b4082d2c9d` 计划两条，主会话首条输入为 `\n\n<pasted_content id="316b">\n<原始正文>\n</pasted_content id="316b">\n`，内文与冻结 prompt 完全相同；阶段仍为 awaiting/0。首轮最终回复已出现且完成分类为 complete，helper 的 wait 令 driver 一直等到总超时。
- 输入确认先比较完整正文；仅当完整消息严格符合已观察到的单层、同 ID 粘贴包装时再比较内部正文，不使用子串或模糊匹配，不修改持久正文及摘要。
- `advance --no-next` 在缺少输入或回复证据时返回 incomplete，保留原阶段。observe/init 仍只观察；只有 driver 已确认最终回复或退出后调用 advance，不能在工作仍进行时直接终止。pending 恢复不确定仍拒绝重发。
- `inject_tmux_prompt` 默认逐行使用 tmux literal send-keys，以 Ctrl+J 插入换行，末尾只发送一次 Enter。含 Tab/CR 的既有自定义输入继续括号粘贴以免触发补全或提前提交；快速输入仍可能被 CLI 包装，识别不能依赖输入方式。
- 回归覆盖真实包装的 string/text-block、初始及补充、完成后复核、错误包装/额外文本拒绝、收尾时未知或 pending 阶段，以及真实 driver/tmux 的按键多行和未完成收口。替身明确记录传输方式，并可模拟真实包装、收尾控制与未识别输入。

## 随机时间投递：已实施的新契约

- 原生 2.1.293 离线证据：`/tmp/topic-followups-busy-evidence2/result.json` 与 queued/final JSONL。在首轮合成响应未返回期间，真实按键函数成功投递两条，主会话立即记录 `type=queue-operation, operation=enqueue, content=<完整正文>`；当时尚无这两条普通 user。首轮回复后，分别记录两条 user，下一上游请求将两条拼为一个 user，最后一个正常 assistant 同时回应两条。不能把“一条消息一条独立回复”作为新模式前提。
- 定时发送与业务完成必须解耦。新模式每次循环检查固定的到点计划；发送前保存 pending，入队或普通 user 的精确正文证据确认传输，普通主 user 才确认消费。两条均已消费且最后一条之后出现正常最终回复时核验整体完成，保留旧字节边界/父链/错误保护。
- 时间从初始需求实际投递后的运行计时点计算，不从排队创建任务的数据库时间计算。随机次数、正文及时间计划只生成一次并持久保存；恢复按原计划和既有尝试时限策略对账，不重新抽签、不将未知 pending 当作未发送。
- 新旧模式须有显式快照边界。旧行/活动 run 不回填新时间；schema 1 阶段仍按已部署规则恢复。新增字段、driver 环境与页面 DTO 已按下述已确认窗口实现。
- 默认发送仍为现有按键函数，不发送中断，不添加人工打字节奏。到点可能只是进入原生队列，不能承诺模型当场打断工作或完成业务要求。
- 页面计划列表显示每条目标时间及传输/消费/完成状态；汇总“已完成”不能借用“已入队”数。首轮提前结束但仍有将来计划时，须保留本任务等待后续时间点，不能提前 success。
