# v3 首输出延迟与运行中调度配置热更新

## 目标

让账号智能调度的延迟分反映等待实际输出的时间，避免把只返回响应头而迟迟没有内容的请求判为快速。

## 来源与确认范围

- 用户在比较v3与codex-proxy-rs后明确要求“那我们延迟的逻辑修改下吧”。采用此前建议：首个有效文字、思考或工具输出作为调度延迟，保留响应头时间用于诊断；按已知模型和思考参数区分延迟样本。
- 用户已明确本项目自行提交、推送和部署，无需重复确认。按已确认范围展示最终Brief后继续实现与部署。
- 当前`diagnostics.rs:353`将响应头耗时写入`AttemptDiagnostic.ttft_ms`，终态反馈把它作为调度延迟；`UsageCapture`已有有界SSE/JSON和压缩解码链，可作为唯一输出观察源。

## 需求

- R1：从实际提交开始到首次有效输出被观察到计算延迟；排队、环境准备及平滑等待不计入。
- R2：元数据、心跳、空内容不构成首输出；合法文字、思考和工具输出只记录第一次。复用现有有界解析与解码，不改变客户端响应字节、流式交付和缓存行为。
- R3：仅已确认成功且采到有效输出的请求更新延迟；失败、取消、无输出和观察缺失不伪造零值，不污染成功延迟。健康反馈保持原规则。
- R4：响应头耗时继续保留，诊断明确区分两种时间；历史记录缺少首输出时保留未知，不能用响应头回填。
- R5：调度与管理页面标明首个有效输出口径；模型和思考档位的样本不串用，未知保持中性，不推测未提供参数。
- R6：通过相关测试、完成提交推送及新版部署，检查实际发布、鉴权和健康；不发送真实模型压力探针。

- R7：用户追加指出API运行期间RPM、并发、优先级等无法编辑。普通调度/展示/额度配置允许在活动请求或CLI占用时更新，前端只发送改动字段，后端只更新明确配置列，不覆盖并行轮换的凭据、状态或身份。真正修改代理/认证/凭据/身份的操作保留维护门禁。降低并发不终止在途请求，后续准入等待至低于新上限；RPM变化唤醒等待者，优先级作用于后续新会话。

## 验收

- AC1（R1–R2）：先快速返回响应头和元数据、后延迟输出的流，首输出时间晚于响应头；文字、思考、工具、分块与受支持压缩编码均得到正确首输出，响应字节不变。
- AC2（R3）：失败/取消/空响应/损坏或采样不完整不奖励低延迟，成功样本保留既有平滑公式；健康、绑定、RPM和近优轮换回归通过。
- AC3（R4–R5）：新旧诊断均可读取，两种时间文案准确；模型/思考档位的样本不串用，缺失为未知。
- AC4（R6）：必要检查通过，提交推送及部署收据对应同批新版，当前数据、身份和其他应用保持。

- AC5（R7）：持有活动API和CLI租约时保存RPM/并发/优先级成功，现有流与租约保持；降低并发后不再按旧上限放新请求，真正代理/凭据修改仍被拒绝；只改调度参数不覆盖新令牌或并行状态更新。

## 范围外

不修改5分轮换阈值、调度权重、会话绑定/准入策略、RPM平滑公式；不修RSS同步，不修改codex-proxy-rs，不重登录、迁移或重置账号。
