# 修复 v3 进程指标同步并严格验收 cc2api 容器转发链路

## Goal

让 v3 同步账号的进程指标有可核对的真实来源，并用正式入口和容器网络证据验证 cc2api 请求实际经过目标账号容器及其代理。

## 用户原始要求

> 那我们先把cc2api那个问题修一修，另外你在严格看看cc2api是不是能正常通过容器内去转发出去，之前我感觉都没认真试过

新增要求：首次同步新建的 cc2api 账号使用 Billing 重写、开启上游 session 池、池容量 4、TTL 仅属主刷新、并发 4、RPM 上限 50。

新增交互诉求：用户认为“同步”存在歧义；已明确回复“可以”，确认采用创建、关联已有、更新进程指标、重新授权四个入口，且创建与关联完全分开。

## 已确认事实

- 美国 v3 的 10-15 已绑定 cc2api 账号 2；该账号仍有 account_on_hold 历史，不能用它证明成功推理。线上只读查询时没有 `flows/api/observations.jsonl`，目前没有这条部署的账号 API 发送证据。
- `orchestrator/account_runtime.py:1787` 的 `identity_import()` 只导出已确认设备身份、基础环境和提示词环境；`cc2api/src/handler/router.rs:420` 的 `CliIdentityImport` 没有进程指标字段。
- `cc2api/web/src/components/Accounts.vue:965` 直接展示保存的 canonical_process；`cc2api/src/model/identity.rs:721` 在读取空对象时会使用兼容默认范围。
- `orchestrator/main.py:8007` 的同步入口对已有绑定不会更新进程字段，只修首次创建不足以覆盖已绑定的 10-15。
- `deploy/v3/verify_local.py:55` 的真实网关测试使用合成 RuntimeHandler，仅在收到 ClientHello 后关闭上游并断言 502；`deploy/v3/verify_stack.py:143` 的 SSE 验证针对管理端 runs-stream，不能替代模型 SSE 成功往返。
- `cc2api/src/service/runtime_transport.rs:175` 已有 v3 专属发送入口与失败关闭规则；生产 TLS 客户端在 `cc2api/src/tlsfp/tlsfp.rs:315` 使用公有根，额外信任根仅出现在 cfg(test) 测试客户端。
- 官方 CLI 原生遥测与 cc2api 保存的进程画像是不同路径，不能用账号卡片空白判断 CLI 没有发送真实进程信息。
- 当前工作区已有改动须保留；本轮新增任务已记录主仓/子仓 dirty 基线。

## Requirements

- R1：首次同步携带实际容器内存限制；已有正式 CLI 进程样本时同步其 RSS 及采样时间/来源。没有样本时明确显示“CLI RSS 未采集”，不能把短命 Node 探针、发送器或整个容器的内存占用冒充 CLI RSS。
- R2：已有绑定账号经“更新进程指标”补齐进程数据；身份冲突、样本损坏或来源不符时明确拒绝，不能覆盖设备、代理或凭据。兼容旧普通 cc2api 账号并保持重授权事务。
- R3：v3 实测来源的缺失指标不得被兼容默认值静默补成“实测”；页面区分容器上限、最近 CLI 样本和未知项，转发/遥测只使用有依据的字段。普通旧账号既有画像保持兼容。
- R4：验证正式 cc2api 业务入口 → 实际调度器的传输绑定 → 目标账号发送器 → HTTP CONNECT/SOCKS 代理 → 上游 → 响应的完整路径；覆盖成功 JSON/SSE、取消、账号隔离和失败关闭。
- R5：为成功响应场景提供可关联的网关请求、容器归属、代理连接与上游收包证据；测试信任根和上游替身必须与生产构建隔离，不新增生产跳过证书校验开关。
- R6：用线上现有生产发送器及账号代理核对固定上游的真实公网 HTTPS 往返，不启动 CLI 或发模型请求；实际测试前记录运行状态并在空闲时恢复。此项只能证明传输，无法代替成功推理。
- R7：报告分别列出隔离完整业务链路、生产公网网络和真实 Anthropic 推理状态。真实推理需要可用账号，当前受限账号不自动尝试；不得把替身 200、TLS 握手或上游拒绝计为真实推理成功。
- R8：只清理测试专属资源；日志不包含令牌、代理密码或真实对话。原工作区 dirty 基线与生产 HOME/身份/凭据受保护。
- R9：仅在 bench 首次同步确实创建新 cc2api 账号的分支，显式提交以下六项：`billing_mode="rewrite"`、`upstream_session_pool_enabled=true`、`upstream_session_pool_size=4`、`upstream_session_refresh_policy="owner_only"`、`concurrency=4`、`rpm_limit=50`。用户所说“仅主属性刷新”对应当前页面“仅属主刷新”；未要求修改 TTL 时长，沿用当前默认 60 分钟。匹配已有账号、已有绑定重复同步与重授权均不覆盖这六项，也不修改 cc2api 手动创建账号的全局默认值。
- R10：账号页将原“同步”替换成“创建 cc2api 账号”“关联已有账号”“更新进程指标”，并保留独立“重新授权”。未关联时显示创建/关联，已关联时显示指标更新；后端同样限定各自动作。“创建”发现已有匹配时提示改用关联，不自动转换；“关联”必须显式选择目标，不自动创建且不连带修改养号配置；“更新进程指标”仅本地容器 → 原关联账号，不创建、不改绑定、不刷新凭据；重授权继续通过既有事务更新原关联账号并镜像两端，未关联时只保存本地。成功/失败信息明确动作和结果，旧兼容 API 不再作为新 UI 的笼统入口。

## Non-Goals

- 本轮不修改地区策略、代理线路、账号注册/支付流程，也不自动开关遥测。
- 不追溯恢复历史未采集的 CLI RSS，不为填满页面而额外启动真实 CLI 或模型任务。
- 不用测试专用构建替换生产镜像，不擅自切换生产版本；部署交付遵循既有 v3 SOP。

## Acceptance Criteria

- A1（R1–R3）：首次同步、既有绑定补齐、无样本和有效样本的 API/SQLite/UI 三层一致；错误来源和身份冲突拒绝且原数据不变。
- A2（R2–R3）：普通旧账号画像与已绑定重授权回归通过；未知 v3 指标不静默变成默认实测值。
- A3（R4–R5）：成功 JSON 和完整 SSE 场景各有相同关联标记的入口、账号容器/代理与上游证据；不得只断言 502 或 runs-stream。
- A4（R4–R5）：HTTP CONNECT 与 SOCKS、双账号隔离、共享 CLI/API、取消收口及代理/绑定/发送器故障分别满足场景表；无管理端直连回退和不安全重放。
- A5（R6–R8）：线上 HTTPS 传输测试记录部署批次、发送器归属、非模型目标、结果摘要及恢复状态；报告明确当前未完成真实推理验收，不暴露秘密。
- A6（R9）：首次创建的请求载荷、cc2api 响应、SQLite 与账号卡片均为六项指定值，新账号 TTL 时长为默认 60 分钟；匹配已有账号、重复同步及重授权后管理员原配置保持。
- A7（R10）：实际浏览器点击四个入口，验证可用状态、独立后端请求及明确结果；创建冲突不会自动关联，关联不会创建，指标更新不会刷新凭据/改变配置，养号设置不再承担隐式关联操作。后端直接调用错误状态的动作同样拒绝，不能仅靠前端隐藏按钮。
