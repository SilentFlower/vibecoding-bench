# Native 系统设置兼容总体实施计划

## 实施顺序

- [ ] 完成五项规划材料与来源交接，由首个子任务R1进入实现。
- [ ] R1：修复完整429决策传递，补齐native重试并验证原有PassThrough。

- [ ] R4：默认关闭的最小thinking兼容、双版本原生回环及独立证据，真实上游效果后续核对。

## 验证原则

各子任务先运行其implement.md中的必要定向验证，再进入对应Check-All。仓库当前已有大量工作区改动，开工时重新读取实际定义和diff；每次修改及验证只归属本项精确文件。重复构建仅在新改动或证据失效时执行，复用证据须记录对应实际源码与命令。

最终集成覆盖429换号后的账号身份、缓存/TTL/thinking同次应用、峰值后台按账号归属、零模型准备、预热记录以及Rust连接池说明。gateway常规cargo fmt --check/cargo test --locked、runtime类型/单元/隔离native、web构建和浏览器检查按实际影响执行。源版本280/293和真实二进制证据单列。

## 评审门禁

父任务负责规划及集成，实施从子任务开始。各子任务开工前读取三件套并展示对应brief，按trellis-task-brief执行实际确认分支。实现按trellis-route，代码完成后进入Check-All→Spec→精确Git计划。R4以双版本原生构造和实际TLS发送验收，真实上游效果按后续验证项交接；最终父任务完成依赖全部当期验收证据。

## 回滚点

按子任务独立补丁和已观测状态处理回退。R2双库兼容与共享runtime候选配套单独核对，正式发布/部署/激活由独立SOP执行。
