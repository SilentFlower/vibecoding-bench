# 280/293 原生运行时与网关自动选择设计

## 现状与边界

`version_profile.rs` 已将版本准入与画像选择分开，并在请求开始时冻结客户端画像。`gateway.rs:2413` 的原生分支直接使用账号进入 `forward_native_messages`，当前私有信封缺少明确的 CC 源版本。`NativePool` 在 `native_runtime.rs:249` 仅保存一组当前 key、映像和模板，key 变化会退役整组空闲进程。`native_sender.py`、`native_release.rs`、恢复模块与签名工具均固定 293。

本轮按一个完整端到端交付任务推进。运行时适配、网关选择及池隔离共同构成验收闭环。

## 选择与数据流

1. 复用请求入口的准入检查及冻结画像。客户端模式精确识别原始 Claude UA 的 280/293，默认画像出厂为 293。账号模式在每次选中账号后沿该账号画像解析。普通 API 的其它既有画像保留当前 293 原生兼容路径。
2. 在进入原生传输前冻结受支持的 `source_version`，作为私有 `NativeSubmission` 及准备合同的明确字段。历史信封省略值表示 293。字段仅由受信网关赋值；公开正文中的控制字段继续受原白名单约束。
3. 原始账号继续承担 sticky、并发、RPM、凭据和环境绑定。软件画像副本及运行时版本用于请求构造、诊断及版本选择。完整原生 billing 的版本必须与选定运行时一致，冲突在模型发送前返回受控错误。
4. sender 从受信版本表中解析精确路径、来源摘要、发行引用及执行体身份，再完成版本化准备、进程取得与唯一投递。缺失指定版本或核验失败时报告该版本错误。
5. 响应内容与生命周期沿既有单次发送、背压、取消及终态加 idle 合同返回。诊断记录实际源版本、执行体及出站观察来源。

## 版本适配与构建

- 新增版本专属 280 来源、模块绑定、原生接口及构建断言。先获取并核对官方固定文件，再读取其实际模块和函数定义；293 混淆符号与 ICU 偏移保持版本归属。
- 将现有构建入口扩展为明确选择 280/293 配方，共用经过确认的提取、闭包、打包和加载器机制。版本差异留在版本适配模块；实际可复用范围以定义和回环证据为准。
- 保留普通 API 与原生正文两条适配语义、原生 FetchSession/CCH、实际 CLI 上下文、缓存和遥测策略。每版实际 TLS 行为以官方固定来源为基线。
- 每版分列官方源、分发体及执行体摘要。产物通过完整准入后登记消费身份。签名仍使用原有部署信任根；本轮本地验收使用测试密钥。
- Docker/安装快照同时携带两版准入产物，固定不同安装路径。旧版单文件配置按 293 解释，多版本配置由受信编排端生成。公开发行和生产安装由后续发布流程承担。

## 池、容量与生命周期

- 保留每账号唯一容量所有者。账号身份/凭据/代理/环境代次形成公共身份；源版本、发行摘要和内核代次形成版本子身份。
- 将暖进程、映像FD、核验缓存、补位和模板按版本子身份保存。两版切换保持各自可复用状态；公共身份失效统一撤销旧代准入。
- 物理 live/starting 及 lease 归还由账号统一计数，两版合计遵守 `max_workers`。普通/Haiku 权重仍沿原账号 admission。取消、退役和恢复失败均等实际退出后归还容量。
- 额外映像与模板计入同一账号内存预算，有限预算按真实两版需求准入。容量紧张时可退役其它版本空闲进程，优先满足当前已取得账号槽位的请求。预算错误通过版本状态呈现。
- 预热沿已有显式唤醒、只读巡检和300秒备用进程回收规则；首轮预热默认版本，其它版本按需准备。进程总量和最低保留数按账号控制。

## CRIU、TLS与升级

- 模板 key 包含源版本及实际执行体。280 的 Bun/revision、熵恢复接口和共享映像需单独验证；准入完成后才启用该版模板。恢复能力未接纳时按既有受限 exec 路径启动同版运行时，并显示原因。
- TLS观察按实际执行体、版本和物理PID归属。辅助验证画像依照每版实际官方握手校验，293 画像继续绑定293。受影响能力在验收矩阵中分别记录。
- 发行清单已有 `source_version/source_sha256`，按受支持版本表核验。升级与准备状态增加明确版本维度，旧接口省略版本继续指向293；单版准备、激活、取消或回退只影响自身子状态，账号维护与公共身份变更统一排空。
- `request_backend=native293` 作为历史原生后端键保持可读，原生 UI 使用自动匹配文案，并展示各版可用性。持久配置沿既有存储合同兼容，接口新增字段提供旧消费者缺省行为。

## 风险与实施期研究

- 280 的实际官方文件身份、Bun布局、混淆符号与资源结构待固定；实施第一步形成研究记录。内部接口定位失败需要回到设计阶段修订技术路径。
- 双映像及模板可能提高有限账号的基础内存，需结合实际产物修订准入公式，并验证旧有限布局的受控准备行为。
- 当前池的单key失效规则、准备协调器及升级记录均可能相互驱逐，版本化时需一并覆盖公共身份失效、迟到回执和在途旧进程。
- 280 恢复能力属于独立技术准入；现有受限 exec 是同版可靠启动路径。最终报告分别列出实际通过的启动与恢复能力。

## 回退

保留293原制品与默认映射。可撤回280版本表和对应子状态，并沿既有维护/退役合同收口在途280进程。旧配置与省略版本的私有合同继续解析为293。回退仅撤销新版本准入，实际在途请求沿原终态合同处理。
