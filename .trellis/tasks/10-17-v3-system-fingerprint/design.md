# 技术设计：固定账号的常规系统信息画像

## 目标与边界

实现 PRD R1～R7：每个固定账号首次生成一次内核画像与 CPU 型号文本，覆盖 CLI 角色的常规动态读取。采用镜像内编译的轻量 libc 覆盖库与只读文件，保留现有 Docker 运行时和资源/网络边界。

明确不覆盖直接 uname syscall、静态程序、CPUID、自定义原始读取及所有 sysfs 信息；这些路径继续显示真值，并在覆盖报告中列出。不会修改真实内核、CPU 指令能力或任务目录。

## 持久化与生命周期

- `account_environments.fingerprint_json` 增加嵌套、独立版本的 `system_profile`，不重新生成现有 profile v2 的任何身份字段，不增加新的设备标识。
- 结构包含 `schema`、`kernel_template_id`、完整内核 release/build/proc_version，以及 CPU 模板 ID 与型号文本。模板 ID 可追溯到镜像内的有限候选表；字符串必须长度受限、无换行/NUL，并符合当前 Linux/x86_64 与发行版/CPU 代际约束。
- 模板 ID 及其内容不可在后续升级中重新解释；保留已有版本模板，新增候选只影响尚未生成画像的账号。
- CPU 模板只改变 `/proc/cpuinfo` 的型号文本；实际厂商、family/model/stepping、flags、数量和拓扑保留。实现时先核验同代候选的资料与实际宿主匹配，不跨架构随机、不随机添加指令。
- 账号首次建立或老账号首次补齐，在现有环境锁与所有权门禁内选择一次并持久保存。缺字段只能补齐一次；已有对象损坏时拒绝启用，不自动换模板。
- 不在活动任务、登录、续聊或 API 请求中补齐/重建。需更新的旧容器进入现有待重建/对账流程，空闲时按受控生命周期应用，不能为了画像打断在途任务。
- 重启、重建、账号改名及不同 run 都读取已保存对象。回滚时忽略新增字段，保留对象供重新启用复用；不自动重写已有关联账号的上游画像。

## 画像文件与 CLI 边界

由管理端按保存的结构生成 root 所有的画像目录，以只读 bind 方式挂入 CLI，不能放在 UID1000 可修改的 HOME 内。配置与渲染文件的内容/权限/模板校验在创建前完成，读入拒绝 symlink、非法类型及过大输入，沿用现有安全文件机制。

镜像新增一个 C 共享库，以及覆盖库的源码/编译步骤。CLI 单独只读挂载 `/etc/ld.so.preload`，其内容为镜像内固定共享库路径；网络和 Rust sender 不挂载这个文件，不加载覆盖库。这样动态子进程自动继承覆盖，不要求分别修补每个任务入口。

| 读取入口 | 处理 |
| --- | --- |
| libc `uname` | 先调用原接口，再覆盖 release/version，保留 hostname、machine、domain 等现有字段 |
| `/proc/cpuinfo` | CLI 只读 bind 生成文件，保留实际非型号字段；Node cpus 长度与真实拓扑仍一致 |
| `/proc/version`、`/proc/sys/kernel/osrelease`、`/proc/sys/kernel/version` | 用精确路径的 libc 文件 API 重定向到对应只读画像文件；不放宽 Docker 对 proc 挂载的限制 |
| Node `os.release()` / CPU 型号 | 通过以上真实运行接口获得，身份导入继续实际执行 Node 探针 |
| 官方 Bun 原生 CLI | 其动态 uname 由覆盖库处理；其它读取按无账号离线证据逐项验收 |
| cgroup、RSS、CPU quota、CPU 能力 | 原路径、原值，不参与替换 |
| raw syscall、静态程序、CPUID、未覆盖 sysfs | 保留真值；在报告中明确列出 |

文件 API 最小集合依据实际动态符号与行为验证确定，至少检查 open/open64/openat/openat64 和 fopen/fopen64；必须处理常规绝对路径及已支持的相对路径解析，不能只靠字符串后缀匹配。仅重定向列出的目标，不改变写入语义或其它文件。覆盖库自身读取固定配置要避免递归调用 hook，初始化应线程安全并保持 errno。新增更复杂的路径/API 必须有实际需要与单独证据。

失效处理分两层：管理端发现缺失、损坏或应用不完整则不标记 ready，返回明确的画像校验错误；运行中的库遇到已声明字段配置不可读时返回可辨识错误，不能静默用另一套随机值。不能让诊断文件错误阻断管理端的停止、对账与回滚入口。

## 数据流与兼容性

账号环境门禁 → 生成/读取一次性 system_profile → 校验模板与画像文件 → 只在 CLI 创建时挂载 → 启动后无账号探针确认 → 按原流程执行登录/任务/续聊/指标读取。

`identity_import` 继续执行容器内 Node，得到覆盖后的内核；`canonical_env.linux_kernel` 与 `canonical_prompt.os_version` 使用相同实际探针结果。`process_import` 保持真实 cgroup/procfs 指标。已绑定 cc2api 不自动迁移设备、凭据、策略或已保存 canonical_env；此次功能不扩张成新的同步按钮或批量绑定操作。

测试必须覆盖 start_run、登录 tmux、exec_cli、begin_continue 与工具子进程；覆盖库不要求改变这些入口的参数协议。CPU 文件在 CLI 容器创建时快照真实非型号字段，跨重建的固定画像是替换字段，实际拓扑随真实资源变化，不伪造硬件能力。

## 取舍与性能

- 轻量动态覆盖符合本轮常规读取范围，比新增 ptrace 层少一个生命周期管理点；不是新的安全沙箱。
- `/etc/ld.so.preload`、画像挂载和替换结果本身可观察。改写 CPU 型号后 CPUID 仍真，不能描述为无指纹环境。
- PRoot 已做可行性探针，但默认只改 release、需要可执行临时文件，完整任务/性能未验证，本轮不引入。
- 按当前宿主提供兼容候选表，CPU 型号只随机文本；若检测到不支持的宿主组合，应明确报错并保持既有环境可管理，不随机拼凑或悄悄宣称成功。

## 发布与回滚

本次实施和验收不自动触发生产部署、真实账号授权或模型请求。上线使用现有干净源码 GitHub Actions 双镜像流程，先核对 release、源提交与镜像，再在授权的空闲窗口受控重建；旧配置及原画像留存用于回滚。

回滚到旧镜像/配置时去掉 CLI 专属 preload 和画像挂载，保留新增 JSON 对象、HOME、项目文件和身份；不能只替换动态库而让旧容器仍引用不兼容配置。具体命令归部署 SOP 与当次上线范围所有。
