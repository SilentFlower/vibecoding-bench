# 设计

## 宿主准备和固定项目版本

1. 由 `SystemUpdater._execute` 的现有 `backend.prepare` 路径承接。下载后使用已核验的候选控制镜像 ID，镜像声明可运行项目库准备入口时才调用。保留独立「准备更新」和直接「安装」两个入口，候选选择及操作身份继续由现有签名目录和 CAS 控制。
2. 候选入口复用 `ProjectLibrary` 的树摘要、文件类型、种子和离线制品校验与不可变注册。一次性容器只读根、断网、无 Docker socket，读镜像内内容根，写入限定的项目内容目录。项目目录指向原 `BENCH_DATA/project-library/releases/<digest>`，业务 SQLite、账户 HOME 与节点目录不挂载，准备过程不登记业务数据库行。原进程可继续读取历史冻结版本。
3. 复用现有内容寻址、临时目录与原子发布语义。候选返回有限的目录证明和各注册清单的逻辑摘要。宿主核对镜像、部署、有效内容根和冻结版本后，原子保存私有准备记录。以候选控制镜像摘要、部署及内容身份绑定记录。只推送由宿主确认的结果。重试复用完整且仍匹配的记录，清理局限于本次临时产物。应匹配部署实际配置的库来源，包内路径与显式挂载内容不可互相替代。
4. 候选通过已有受控只读更新挂载获取记录。宿主在准备时复核记录，切换时核对实际候选镜像身份。候选启动复核版本、路径、标准目录及注册清单之身份，加载被冻结和已校验的项目索引。启动只读元数据，免去再次遍历种子树与大离线制品。沿已有不可变版本与消费端校验边界，核对种子及环境制品在实际使用时的完整性。项目管理器消费已注册库对象，沿原数据库事务登记发行 ID，消除第二次安装扫描。
5. 新记录损坏或绑定不符时在关闭门禁前重做准备或报出准备错误。切换后发现准备证明无效沿原健康失败和版本恢复路径处理。历史镜像的原流程、普通启动、历史项目版读取继续可用。旧宿主无法生成准备证明，提供 v2 同协议源码刷新和实施顺序，采用实测的旧版首次切换而不伪造快速换版能力。

## 候选与恢复探测

- 复用已验证的管理鉴权，保留网关 `/admin/runtime/system-update/status` 及调度器 `/internal/v3/system-updates/snapshot`。每端保存最后成功或失败观测、耗时、实际收到的 HTTP 状态和固定失败类别，未探测时明确标记。当前 180 秒窗口和每探测约束沿原合同，遵守同一操作时间预算。
- 在切换持久操作中保存受控探测字段。原候选失败先持久记录，再启动恢复。恢复探测单独保存，不能覆盖候选失败。复用公开操作投影和更新页「操作详情与数据库快照」，展示两端的结果。原版旧记录缺字段仍可读。凭据、认证头、原始任意错误正文和完整快照不写进公开记录。
- 继续由现有状态机判断恢复和开放前后边界。首次 v1.24.0 兼容切换按原节点准备与恢复顺序取证，不能把后台快切的中央快照结果作为首次兼容通过。
- 旧编排服务在下一次兼容安装时会误读 `platform_restored` 为原现场。宿主在兼容维护已核对旧节点就绪且确认上一次操作已恢复后，归档该节点的完整终态日志。新编排服务把此阶段视为终态。两条路径都保留原租约、远程数据、备份及未完成作业。

## 已核对的入口与风险

- `deploy/flower2api/system_updater.py` 的 `SystemUpdater._execute` 在完成准备操作或进入排空和关门禁之前调用 `backend.prepare`。
- `HostDeployment.wait_controls` 吞掉两端错误，旧更新器的故障注入证明只能得到通用超时。生产现场已自动恢复，源探测无法从操作原记录找回。验收用受控失败与实际现场复现各自记录结果。
- `services/orchestrator/project_library.py` 既全量验证源目录，也重读冻结目录。`ProjectIterationManager.__init__` 再对传入库调用 `install`。现有历史路径仍依赖数据根下的相对目录和固定内容摘要。
- 安装包外置的宿主执行器需要刷新到支持准备证明和探测记录的版本。沿 `deploy/flower2api/SYSTEM-UPDATES.md` 的同协议源码刷新 SOP 核对确切源码、守护进程、策略和原状态。不将刷新等同于安装或回退。
