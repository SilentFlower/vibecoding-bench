# 实施与验证

1. 按 v1.24.0 安装宿主对应的历史源码和签名发行分别取得旧控制和账号镜像身份。复用 `verify_system_update.py` 的独立部署和合成 SSH 夹具，创建首次兼容升级场景。项目库分支需明确启用镜像打包目录或有内容的可控夹具。现有空库测试维持原目的。基线记录项目库参与时两个健康端点的实测表现和捕获范围，说明线上上次异常是否再现。
2. 实现受限项目库准备入口和宿主调用，使用已核验的候选 ID，承接现有显式和隐式准备。复用项目验证与冻结目录发布，记录受信准备证据。验证退出失败、中断、同版本并发及缓存失效都能按已有准备路径返回或重试。
3. 接入候选启动的已验证元数据加载和项目管理器安装复用。回归普通启动、旧宿主和历史镜像、不同内容版本、被篡改的校验记录、文件或目录身份异常、旧项目读取和实际使用边界。
4. 在 `system_update_host.py`、`system_updater.py` 记录候选及恢复的真实双端探测。为旧记录保留缺省读取。在 `apps/web/src/api.ts` 和 `SystemUpdates.vue` 使用受控字段展示，不引入新的健康常量或错误正文格式。测试两个端点独立失败、HTTP 错误、连接超时、返回无效、最终恢复。
5. 执行宿主 `test_system_host`、`test_system_updater`，编排 `test_system_update_snapshot_lock`、项目库和项目场景相关回归、Web 类型和构建检查。验证真实 Docker 的旧版首次升级、合成 SSH、关闭接单前准备、回退及继续健康服务，确保快速换版和旧记录沿原边界。同步权威规范和既有运维 SOP。
6. 汇总两个控制端探测、项目库准备及门禁时序的隔离证据。打包记录明确首次生产安装前需要的宿主同协议刷新和实际线上验收边界。
