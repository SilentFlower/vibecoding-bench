# 构建与发布解耦，延续 v3 原地升级

## Goal

将自动构建验证与显式发布分离，让现有 v3 实例沿原系统更新入口逐步原地升级。

## Background

- 用户要求先处理构建发布，后续按小步推进品牌、源码融合与界面改造。
- 当前 v3 的 push 会依次构建镜像、推送 GHCR、发布 GitHub Release 并更新签名目录；main 的旧镜像工作流也在 push 时发布。
- 当前部署已有签名发行、系统更新、双库兼容验证和恢复机制，应继续沿用。
- 本任务是 `../11-12-flower2api-unification` 的首个实施子项，工作分支 flower2api，基线 v3。

## Requirements

- R1：v3 与 flower2api 的 push、目标分支 PR，以及手动构建均执行验证与构建。构建阶段的发布操作次数为零。
- R2：正式平台发布由独立手动入口触发，来源限定本仓 v3 或 flower2api 的实际提交；明确选择发布并通过同批验证后才发布镜像、签名发行和更新目录。
- R3：旧 main 镜像入口改为显式手动发布，避免日常 push 继续触发其它自动发布链。
- R4：现有 v3 使用原仓库、信任根、镜像标识、目录、发行身份和数据合同获取新发行。管理员继续从原系统更新页面准备、安装和回退。
- R5：新的发布入口保持目录序号严格递增，能承接旧工作流已签发的历史序号；失败保持原目录可用。
- R6：每个发布批次固定来源 SHA、run/attempt、镜像和附件摘要。原版本递增、兼容演练、完整附件后推进目录及失败恢复规则继续生效。
- R7：分步推进；本阶段交付构建/发布修复、离线验收证据及分支生效说明。

## Constraints

- 保留现有功能、数据库、账号身份、HOME、环境、项目成果和运行历史。生产安装继续由管理员触发。
- 已接入当前系统更新能力的 v3 使用原地升级；更早底座依既有 SOP 原地补齐能力，沿用原部署与数据根。
- 全仓源码迁移、Logo、界面、功能删除以及生产发行/安装留待后续阶段。
- 本次在 flower2api 开发；旧 v3/main 分支的工作流需要同步修复后才改变各自远端触发行为。分支合入与推送使用后续精确 Git 计划。

## Acceptance Criteria

- [ ] 自动构建路径具备只读仓库权限；GHCR 推送、GitHub Release 写入和签名目录更新次数均为零。
- [ ] v3 与 flower2api 手动发布通过来源校验；push、PR、其它分支、错误仓库/SHA及脏来源在发布副作用前被拒绝。
- [ ] main 旧工作流的自动 push 发布入口关闭，手动原交付方式仍可使用。
- [ ] 旧目录序号高于新工作流计数时，新发行仍能正确生成更高有效序号；目录并发冲突和部分失败保持保护。
- [ ] 新发行可由现有 v3 严格验签及兼容校验读取；镜像、信任根、数据合同与目录引用继续沿用。
- [ ] 发布流水线保留实际旧库→候选→原程序读写、幂等迁移与恢复演练作为发布前置条件。
- [ ] 定向测试和工作流静态检查通过，文档明确构建、发布、管理员安装及分支生效步骤。

## Non-Goals

- 三仓源码迁移、数据库重构、品牌/UI 改造及功能退役。
- 本轮直接创建远端发行、推送镜像、改动生产数据或执行线上安装。
