# Brief — 构建与发布解耦，延续 v3 原地升级

## Goal

- 将自动构建验证与显式发布分离，让现有 v3 实例沿原系统更新入口逐步原地升级。

## Scope

- v3/flower2api 的自动及手动构建验证。
- 独立手动平台发布入口、发布来源校验和连续发行序号。
- main 旧镜像流程调整为手动发布。
- 后继补丁版本 v1.1.1 的元数据、回归测试及操作文档。

## Non-Goals

- 源码归并、Logo、界面重构与功能精简留到后续步骤。
- 远端正式发行和生产安装由后续明确操作执行。

## Technical Overview

- 构建入口使用只读权限，产出验证结果、镜像和本地清单。
- 手动发布冻结所选分支的实际提交，通过同批验证及旧库兼容演练，再发布完整附件并推进原签名目录。
- 新发行序号承接已验签历史目录；原地更新继续使用原镜像标识、信任根、数据合同和安装恢复流程。

## Context & Decisions

- 当前 v3 构建与发布共用一条自动流程，两个 Python 发布入口也限定 v3 来源。
- 新工作流的运行计数从 1 开始，需要独立处理历史序号衔接。[GitHub 变量文档](https://docs.github.com/en/actions/reference/workflows-and-actions/variables)
- 用户明确要求小步演进，既有账号、环境、项目成果和历史记录持续保留。

## Risks

- v3/main 的旧触发规则需同步修复后生效；新手动入口还需注册到默认分支 main。[GitHub 工作流文档](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)
- 更早的更新底座可能需要按既有 SOP 原地补齐能力，继续沿用原部署和数据根。

## Acceptance

- push/PR/手动构建产生的发布操作次数为零。
- 正确来源的手动发布通过；错误事件、分支或来源在外部写入前被拒绝。
- 旧目录高序号、版本递增、完整附件发布、部分失败和目录并发保护通过回归。
- 现有 v3 验证器能够读取候选发行，正式发布保留真实旧库兼容演练。
- 定向测试和工作流检查通过，明确记录分支生效与原地升级步骤。

## Next Step

- 进入实现，先补发布边界回归，再拆分工作流。
