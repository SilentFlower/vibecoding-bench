vibecoding-bench 项目原理说明

这个项目把 topics.md 里的题目变成可调度的运行任务，让真实的 Claude Code 在隔离容器中完成题目，并通过账号级并发、透明代理、TLS MITM、SQLite 和 SSE 把执行过程记录下来。

300 题库题目来自 topics.md
2 / account 默认单账号并发上限
2 containers 每个 run 启动 sidecar + worker
0 build WebUI 是静态 HTML + 原生 JS

一句话原理

题目进入系统

README 和代码显示，题库从 topics.md 初始化到 SQLite；WebUI 可以维护 topic，并把选中的 topic 组成批次任务。

topics.md SQLite task_batches

任务被调度

Orchestrator 使用 FastAPI 提供 API，用 Docker SDK 启动容器，并用每账号信号量限制并发，避免单账号被同时挤爆。

FastAPI Docker SDK Semaphore(2)

流量被观测

worker 共享 sidecar 的网络命名空间，出口先进入 mitmproxy，再经 SOCKS5 上游；摘要写入 stats.jsonl。

sidecar mitmproxy stats.jsonl

整体架构

01 WebUI

静态 HTML、CSS、原生 JS。提供账号、题库、任务、运行四个主要页面。

/webui
02 Orchestrator

FastAPI 服务，负责 CRUD、批次调度、Docker 容器生命周期和 SSE 推送。

orchestrator/main.py
03 Sidecar

透明代理容器，运行 hev-socks5-tunnel、mitmproxy 和 unbound DNS 桥。

images/sidecar
04 Worker

运行 Claude Code、tmux、Stop hook 和题目工作目录，最终输出 transcript。

images/worker

  1. WebUI 不直接跑模型

    前端只调用 /api/...，创建账号、topic、批次和运行；运行状态通过 /api/runs-stream 订阅。

  2. Orchestrator 是控制面

    它持有 SQLite 状态、Docker socket 和调度线程；真正执行题目的进程不在后端进程内，而在 worker 容器里。

  3. Sidecar 是网络面

    每个 run 都有独立 sidecar，worker 使用 network_mode=container:<sidecar> 共享网络命名空间。

  4. Worker 是执行面

    worker 复制账号 profile，安装 MITM CA，启动 tmux 中的 claude，粘贴题目 prompt，并等待完成或超时。

一次任务的生命周期

1. 题库入库

topics.md 在 topics 表为空时作为 seed 来源。之后 WebUI 可以编辑 topic，已有实例要用同步脚本把新版题库写进 SQLite。

2. 批次创建

用户选择账号和多个 topic 后，后端创建 task_batches 和 task_batch_items。创建时会随机打乱选中题目，后续按 item id 固化顺序。

3. run 排队

调度器为每个 item 创建兼容旧表的 task 和 run。每个账号由 threading.Semaphore(PER_ACCOUNT_CONCURRENCY) 控制并发，默认值是 2。

4. 容器启动

Orchestrator 先启动 sidecar，等待 /tmp/sidecar-ready 和 DNS 可用，再启动 worker 并让 worker 共享 sidecar 网络命名空间。

5. Claude 执行

worker 用 tmux 启动交互式 claude，通过 bracketed paste 注入题目。Stop hook 只表示 Claude 停过一轮，最终成功仍要看 session JSONL 中的稳定 assistant 回复。

6. 结果归档

worker 写出 .bench-transcript.log 和状态文件；sidecar 记录 API 摘要；后端根据退出码和 worker 状态把 run 标为 success、failed、timeout、auth_failed 或 stopped。

透明代理与 TLS MITM

Worker

Claude Code 进程认为自己在正常访问网络；DNS 被 worker entrypoint 改到 127.0.0.1。

->

Sidecar netns

worker 与 sidecar 共用网络命名空间，所以 127.0.0.1:53 和默认路由都落在 sidecar 内。

->

SOCKS5 出口

mitmproxy 接收本地 SOCKS5 流量，proxychains 再把它送到账号配置的上游 SOCKS5。

为什么要 sidecar

worker 不能只设置环境变量代理，因为需要尽量保证流量必经代理并能被 MITM 观测。sidecar 把默认路由切到 tun0，并用 hev-socks5-tunnel 把透明流量转成 SOCKS5。

worker
  DNS: 127.0.0.1:53
  default route: sidecar tun0
  CA: /etc/mitm/mitmproxy-ca-cert.pem

sidecar
  unbound: UDP 53 -> TCP DNS
  hev-socks5-tunnel: tun0 -> 127.0.0.1:8080
  mitmdump: socks5 inbound -> proxychains -> upstream SOCKS5

数据如何落盘

路径 内容 为什么存在
data/db.sqlite accounts、topics、tasks、runs、task_batches 等状态 让 WebUI、调度器和详情页共享同一份持久状态。
data/profiles/<acc>/ 每个账号的 Claude OAuth profile 白名单文件 账号隔离；运行前复制到 worker，运行后只回写配置，不用旧 token 覆盖刷新后的凭据。
data/flows/<acc>/<task>/<run>/stats.jsonl mitmproxy recorder 写出的 API 请求、响应、usage 摘要 详情页 token 统计优先从 sidecar 摘要聚合；没有 usage 时回退读 Claude session JSONL。
data/workspaces/<run>/ Claude 工作目录、产物、.bench-transcript.log、.bench-status.json 保留每次 run 的可检查现场，供 WebUI 详情页展示文件树和 transcript。
data/ca/ mitmproxy 首次生成并持久化的 CA 让后续 worker 信任同一个 MITM CA，避免每次 run 使用不同证书。

状态观测链路

SSE 实时列表

/api/runs-stream 每秒读取最近 100 条 run。如果 payload 变化，就以 runs 事件推给浏览器。

Transcript

worker 周期性或结束时抓 tmux pane，写入 .bench-transcript.log。详情页直接请求文本文件。

Token 统计

优先读取 sidecar 的 stats.jsonl；如果 MITM 没拿到 usage，则扫描 Claude session JSONL 聚合。

关键设计决策

交互式 Claude

项目使用交互式 claude 和 tmux 驱动，而不是简单的 claude -p。这样更接近真实 Claude Code 使用路径。

账号指定派发

任务创建时绑定账号；运行中撞限或认证失败不会自动切换账号，避免结果归因混乱。

固定并发上限

默认 PER_ACCOUNT_CONCURRENCY=2。总并发等于账号数乘以单账号并发，而不是全局无限投放。

零构建 WebUI

前端是 index.html、style.css、app.js 三个静态文件，FastAPI 使用 StaticFiles 托管。

MITM 摘要优先

默认不保存完整 flow，只保存 stats.jsonl。需要完整流量时再用 SAVE_FULL_FLOWS=1。

超时前收尾

worker 默认会在超时前 TIMEOUT_WRAPUP_SEC=600 秒注入收尾提示，让 Claude 尽量停止扩展并输出结果。

关键文件索引

orchestrator/main.py

后端主文件。包含配置、SQLite schema、API、调度器、Docker runner、SSE 和静态 WebUI 托管。

images/sidecar/start.sh

sidecar 入口。配置 proxychains、启动 mitmdump、创建 tun0、启动 hev、配置 unbound，并写 readiness 标记。

images/sidecar/recorder.py

mitmproxy addon。筛选 Anthropic / Claude API 流量，把请求、响应和 usage 摘要追加到 stats.jsonl。

images/worker/entrypoint.sh

worker 入口。准备 Claude profile、注入 CA、处理启动门禁、启动 tmux、注入 prompt、处理超时和认证恢复。

webui/app.js

原生 JS 前端逻辑。管理 hash 路由、全局 state、账号登录、题库维护、批次创建、运行详情和 SSE。

docker-compose.yml

本地启动入口。定义 orchestrator 服务和三个镜像的构建关系，并把 webui/、topics.md、data/ 挂入后端。

已知限制与排查重点

宿主路径必须绝对

HOST_BENCH_DATA 要给宿主 Docker daemon 使用，不能写 ./data。

题库不会自动覆盖

topics.md 只在 topics 表为空时 seed。已有实例同步题库要运行 scripts/sync-topics-db.py --apply。

首次 CA 有窗口期

sidecar 首次生成 CA 后 worker 才能注入；当前用 SIDECAR_BOOT_WAIT 和 readiness 兜底。

证书固定风险

当前 Claude Code 未做 certificate pinning；如果后续版本 pin 证书，MITM 会失败。

OAuth 刷新竞态

orchestrator 后台刷新 profile；运行中的 worker 定期单向同步新的 .credentials.json。

磁盘占用控制

默认不保存完整 MITM flow，并在 run 结束后清理 workspace 中的依赖目录。

最小启动路径

cd bench

cp .env.example .env
# 编辑 HOST_BENCH_DATA 为 data/ 的宿主绝对路径

docker compose --profile build build
./scripts/init-account.sh main
docker compose up -d orchestrator

open http://localhost:8000

阅读顺序建议：先看 README 的启动方式，再打开 WebUI 跑一次账号登录和批次创建；遇到运行失败时，从 run 详情页的 transcript、文件树、token 统计和后端 run 状态开始排查。
